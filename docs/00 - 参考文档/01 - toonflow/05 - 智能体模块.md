# Toonflow 智能体模块

> 分析对象：`refer/Toonflow-app`（后端，版本 v1.0.6）+ `refer/Toonflow-web`（前端，新版）
> 分析日期：2026-08-09
> 文档说明：本文档全面深入地分析 Toonflow 的 AI 智能体（Agent）模块。**重要版本说明**：本地后端仓库 `Toonflow-app` 是 **v1.0.6 旧版**，仅包含 `OutlineScript`（大纲）与 `Storyboard`（分镜）两个 Agent；而前端仓库 `Toonflow-web` 是**新版**，配套的新版后端智能体生态更完整，额外包含**剧本智能体（scriptAgent）**、**制作智能体（productionAgent/导演台）**、**技能（skill）体系**、**Agent 部署配置（agentDeploy）**与**记忆管理**。本文档 A~J 章分析本地旧版两个 Agent 的实现，K~N 章补充新版完整的智能体生态（基于新版前端源码推导），避免遗漏。

## A. 模块概览（旧版 v1.0.6）

Toonflow 旧版的智能体模块位于 `src/agents/`，是两个通过 WebSocket 与前端实时交互的多 Agent 协作系统，分别承载生产流水线的「大纲生成」与「分镜生成」两大核心环节：

| 文件 | 类名 | 生产环节 | 子 Agent |
|---|---|---|---|
| `src/agents/outlineScript/index.ts` | `OutlineScript` | 小说→故事线→分集大纲→资产抽取 | AI1(故事师)、AI2(大纲师)、director(导演) |
| `src/agents/storyboard/index.ts` | `Storyboard` | 剧本→片段→分镜(镜头提示词)→宫格图→分割单张 | segmentAgent(片段师)、shotAgent(分镜师) |
| `src/agents/storyboard/generateImageTool.ts` | - | 分镜宫格图生成（含资产过滤/提示词润色/压缩拼接） | - |
| `src/agents/storyboard/imageSplitting.ts` | - | 宫格图按布局分割为单张镜头图 | - |
| `src/agents/storyboard/generateImagePromptsTool.ts` | - | 用 AI 优化宫格布局提示词 | - |

两个 Agent 类结构高度同构（均由 `src/utils/ai/text/index.ts` 的 `ai.text.stream` 驱动），形成一套**「主 Agent 调度 + 子 Agent 执行 + Tool 操作数据库 + EventEmitter 推送」**的统一模式。

## B. 核心架构模式

### B.1 主 Agent 调度（`call` 方法）

两者 `call(msg)` 流程完全一致：

```
history.push(user消息)
      │
      ▼
buildEnvironmentContext()  ── 组装 <环境信息>（项目/小说/资产/可用工具）
      │
      ▼
读取 t_prompts.code=xxx-main 的提示词（customValue 优先，fallback defaultValue）
      │
      ▼
读取 t_aiModelMap 对应模型的 AI 配置（getPromptAi）
      │
      ▼
u.ai.text.stream({ system, tools, messages: history, maxStep: 100 })
      │
      ├─ tool-call 事件 ──▶ emit("toolCall")
      ├─ text-delta 事件 ─▶ emit("data")（逐 token 推给前端）
      ▼
history.push(assistant响应) → emit("response") → 返回完整响应
```

- **多轮对话**：`messages` 直接使用 `this.history`（完整对话历史），支持持续交互与追问
- **maxStep=100**：单次 agent 循环最大工具调用步数上限
- **提示词兜底**：若 t_prompts 无配置，回退到硬编码 `"不论用户说什么，请直接输出Agent配置异常"`

### B.2 子 Agent 协作（`invokeSubAgent`）

主 Agent 将「AI1 / AI2 / director / segmentAgent / shotAgent」作为**可调用的 Tool** 暴露给 LLM（`createSubAgentTool`），LLM 自主决定何时委派任务给哪个子 Agent，形成两级嵌套调用：

```
主 Agent（main）
  ├─ createSubAgentTool("AI1")        ──▶ invokeSubAgent → 子 Agent 独立 stream
  ├─ createSubAgentTool("AI2")
  ├─ createSubAgentTool("director")
  └─ ... 基础 Tool（getChapter/saveStoryline 等）
```

- 子 Agent 用**专属 system prompt**（`t_prompts` 中 `outlineScript-a1/a2/director` 或 `storyboard-segment/shot`）
- 子 Agent 只获得**限定工具集**（见 C/D 各 Agent 的工具清单）
- 子 Agent 的 token 流经 `subAgentStream`、结束经 `subAgentEnd` 事件推给前端
- 子 Agent 的完整响应会被 `history.push` 记录，作为上下文延续
- **委派工具的参数**：统一为 `taskDescription`（字符串描述）

### B.3 Tool 体系（统一约定）

所有工具用 Vercel AI SDK 的 `tool({ title, description, inputSchema: z.object(), execute })` 定义：
- `title` + `description`：供 LLM 理解工具用途与何时调用
- `inputSchema`：zod 校验入参，保证参数结构稳定
- `execute`：真正执行业务（操作数据库 / 调 AI / 上传 OSS）

## C. OutlineScript 大纲智能体

### C.1 数据模型（EpisodeData）

单集大纲的结构化 schema（zod 强约束，`episodeSchema`）：

| 字段 | 类型 | 约束 | 业务含义 |
|---|---|---|---|
| episodeIndex | number | 从1递增 | 集数 |
| title | string | 8字内 | 标题，疑问/感叹句含爆点 |
| chapterRange | number[] | - | 关联章节号 |
| scenes / characters / props | AssetItem[] | 按出场顺序 | 场景/角色/道具（name+description） |
| coreConflict | string | - | 核心矛盾：A想要X vs B阻碍X |
| outline | string | 100-300字 | 剧情主干（**剧本生成的唯一权威**） |
| openingHook | string | - | 开场镜头（必须作为剧本第一镜头） |
| keyEvents | string[4] | length=4 | 起承转合四个节点 |
| emotionalCurve | string | - | 情绪曲线 |
| visualHighlights | string[] | 3-5个 | 标志性镜头 |
| endingHook | string | - | 结尾悬念（勾引下集） |
| classicQuotes | string[] | 1-2句≤15字 | 金句，须从原文提取 |

### C.2 子 Agent 角色分工

| 子 Agent | 提示词 code | 工具集 | 职责 |
|---|---|---|---|
| AI1 故事师 | outlineScript-a1 | getChapter、getStoryline、saveStoryline | 分析原文→生成故事线→保存 |
| AI2 大纲师 | outlineScript-a2 | getChapter、getStoryline、saveStoryline、getOutline、saveOutline、updateOutline | 基于故事线→生成分集大纲→保存 |
| director 导演 | outlineScript-director | 同上 | 审核故事线与大纲，可改 saveStoryline/updateOutline |

### C.3 主 Agent 可用 Tool（完整清单）

| Tool | 输入 | 作用 |
|---|---|---|
| AI1 / AI2 / director | taskDescription | 委派子 Agent |
| getChapter | chapterNumbers: number[] | 批量获取章节原文 |
| getStoryline | - | 读取故事线（**注意：description 是占位文案"Get the weather"**） |
| saveStoryline | content | 保存/覆盖故事线 |
| deleteStoryline | - | 删除故事线 |
| getOutline | simplified: boolean | 获取大纲（简化或完整详情） |
| saveOutline | episodes[], overwrite, startEpisode | 保存大纲（覆盖或追加） |
| updateOutline | id, data | 更新单集大纲 |
| deleteOutline | ids[] | 删除大纲（级联删关联剧本） |
| generateAssets | - | 从所有大纲抽取角色/道具/场景写入 t_assets |

### C.4 大纲保存逻辑（saveOutlineData）

```
saveOutline
  ├─ overwrite=true ─▶ clearOutlinesAndScripts()：删 t_script(按outlineId) + 删 t_outline
  ├─ 计算起始集数：覆盖=1，追加=getMaxEpisode()+1
  ├─ insertOutlines：批量插入 t_outline（data 存 EpisodeData JSON，episode=序号）
  ├─ 取最新插入的 N 条 → createEmptyScripts：为每集创建空 t_script（name="第N集"）
  └─ refresh("outline")
```

### C.5 资产生成逻辑（generateAssetsFromOutlines）

```
遍历所有大纲 data → 汇总 characters/props/scenes
  → uniqueByName 去重
  → 对每个资产 upsertAsset(type, item)：
       不存在 → insert（name+intro+prompt=description）
       存在但 intro 不同 → update
       相同 → skipped
  → refresh("assets")
```

**特点**：只做新增和更新，不做删除；用「项目ID + type + name」唯一判断。

## D. Storyboard 分镜智能体

### D.1 内存数据模型（运行期状态）

```typescript
Segment { index, description, emotion?, action? }        // 片段
Shot    { id, segmentId, title, x, y,
          cells: [{src?, prompt?, id?}],                  // 镜头数组，一格一镜头
          fragmentContent, assetsTags[] }                 // 镜头提示词
```

Storyboard 类在**内存**维护 `segments`、`shots`、`shotIdCounter`、`generatingShots(Set)` 四份状态，分镜数据不直接落库，而是经 WS 推给前端由前端持久化。

### D.2 子 Agent 角色分工与工具隔离

| 子 Agent | 提示词 code | 限定工具集 | 职责 |
|---|---|---|---|
| segmentAgent 片段师 | storyboard-segment | getScript、getAssets、updateSegments | 读剧本/资产→切片段→保存片段 |
| shotAgent 分镜师 | storyboard-shot | getScript、getAssets、getSegments、addShots、updateShots、deleteShots、generateShotImage | 读片段→生成分镜镜头提示词→存分镜→生成图 |

**关键设计**：通过 `getSubAgentTools(agentType)` 实现**工具按角色隔离**——片段师不能操作分镜，分镜师不能改片段，约束 LLM 行为边界。

### D.3 主 Agent 可用 Tool

| Tool | 作用 |
|---|---|
| segmentAgent / shotAgent | 委派子 Agent |
| getScript | 读取当前剧本内容 |
| getAssets | 从关联大纲 data 提取角色/道具/场景列表，**强制要求原样使用资产名** |
| getSegments / updateSegments / addShots / updateShots / deleteShots | 片段与分镜的增删改查（内存） |
| generateShotImage | 异步生成分镜宫格图 |

### D.4 分镜图生成（generateShotImage + executeShotImageGeneration）

该流程是**异步非阻塞**的，是 Storyboard 最复杂的部分：

```
generateShotImage(shotIds)
  ├─ 过滤：已存在/已生成中/不存在
  ├─ 标记 generatingShots
  ├─ emit("shotImageGenerateStart") → 后台执行（不阻塞 Agent）
  ▼
generateSingleShotImage(shotId) —— 每个分镜独立 Promise.all 并发
  ├─ 取该分镜所有 cells 的有效 prompt
  ├─ emit(progress: generating)
  ├─ generateImageTool(prompts, scriptId, projectId)  → 生成整张宫格图(Buffer)
  ├─ emit(progress: splitting)
  ├─ imageSplitting(gridImage, prompts.length)        → sharp 按布局分割成单张
  ├─ emit(progress: saving) 逐张上传 OSS 并 emit 进度百分比
  ├─ 更新每个 cell 的 src = 图片 URL
  ├─ emit("shotImageGenerateComplete") + emit("shotsUpdated")
  └─ catch → emit("shotImageGenerateError")
```

**并发控制**：`generatingShots: Set<number>` 防止同一分镜重复触发；多个分镜用 `Promise.all` 并发生成。

## E. 图片生成管线（generateImageTool）

`generateImageTool` 是一个**独立函数**（非 tool），被 Storyboard 的 generateShotImage 调用，串起完整的分镜图生成链路：

### E.1 流程

```
generateImageTool(cells, scriptId, projectId)
  ├─ 读取 t_script → t_outline（data JSON）→ 提取 characters/props/scenes 资源
  ├─ 从 t_assets 按资源名查图片（按 角色>场景>道具 排序，过滤无 filePath）
  ├─ filterRelevantAssets：用 AI 从可用资产图里筛选与分镜直接相关的（结构化输出 relevantAssets）
  ├─ buildResourcesMapPrompts：生成"资产名=图片N"的对照映射提示词
  ├─ generateImagePromptsTool：AI 优化宫格布局提示词（读 t_prompts.code=generateImagePrompts）
  ├─ processImages：控制图片数量与大小
  │     ├─ ≤10张：逐张压缩到≤3MB
  │     └─ >10张：前9张压缩 + 其余 sharp 横向拼接成一张
  │     └─ ensureTotalSizeLimit：保证总大小≤10MB（按大小降序逐张压缩）
  ├─ u.ai.image({ systemPrompt: 资源映射, prompt: 宫格提示词, size:4K, aspectRatio, imageBase64[] })
  └─ 解析 base64 → 返回 Buffer
```

### E.2 关键控制参数

| 参数 | 值 | 作用 |
|---|---|---|
| 单张图片上限 | 3MB（compressImage） | 供 AI 生成的质量/大小限制 |
| 图片数量上限 | 10（processImages） | 超限合并拼接 |
| 总大小上限 | 10MB（ensureTotalSizeLimit） | 多图输入总预算 |
| 分辨率 | 4K / 项目 videoRatio | 生成尺寸与比例 |
| 参考图 | 资产图 base64 数组 | 保证角色/场景一致性 |

## F. 宫格布局与分割（imageSplitting / generateImagePromptsTool）

### F.1 宫格布局规则（两处一致，calculateGridLayout）

| 图片数 | 布局 |
|---|---|
| 1 | 1x1 |
| 2 | 2x1 |
| 3 | 3x1 |
| 4 | 2x2 |
| 5-9 | 3x3（占位） |
| ≥10 | 3列 × ceil(n/3) 行 |

### F.2 分割逻辑

```
计算 cols/rows → cellWidth=W/cols, cellHeight=H/rows
对前 length 个格：sharp.extract({left: col*cellW, top: row*cellH, w, h}).png()
```

只提取前 `length` 格，忽略占位格。与提示词生成端**共享同一布局算法**，保证「生成时占位 → 分割时跳过」一致。

### F.3 提示词润色

`generateImagePromptsTool` 读 `t_prompts.code=generateImagePrompts` 提示词，将「布局 cols×rows、比例描述、风格、可用资产、每格原始提示词」交给 AI 优化为最终宫格生成提示词。若未配置则降级为硬编码兜底。

## G. WebSocket 通信协议

### G.1 连接与生命周期

| 路由 | 参数 | Agent | 初始化事件 |
|---|---|---|---|
| `WS /outline/agentsOutline` | projectId | OutlineScript | init |
| `WS /storyboard/chatStoryboard` | projectId + scriptId | Storyboard | init |

**事件绑定**：路由层为 `agent.emitter` 逐一绑定监听，映射为 WS 消息；连接关闭时 `removeAllListeners()` 并 `saveHistory()`。

### G.2 服务端 → 客户端事件（type）

| type | 来源事件 | 内容 |
|---|---|---|
| init | 建连即发 | { projectId } / { projectId, scriptId } |
| stream | agent.data | 主 Agent 逐 token 文本 |
| response_end | agent.response | 主 Agent 完整响应 + 保存历史 |
| subAgentStream | subAgentStream | 子 Agent 逐 token |
| subAgentEnd | subAgentEnd | 子 Agent 结束 |
| toolCall | toolCall | 工具调用（agent=main, name, args=null） |
| transfer | transfer | 委派子 Agent（to） |
| refresh | refresh | 数据刷新（storyline/outline/assets） |
| segmentsUpdated | segmentsUpdated | 片段更新（Storyboard） |
| shotsUpdated | shotsUpdated | 分镜更新（Storyboard） |
| shotImageGenerateStart/Progress/Complete/Error | 同名 | 分镜图生成状态机（含 progress 百分比） |
| notice | - | 提示（如清空历史） |
| error | error / 异常 | 错误信息 |

### G.3 客户端 → 服务端消息（type）

| type | 服务端处理 |
|---|---|
| msg | 若 msg.type=="user"，调 agent.call(prompt) 触发主流程 |
| cleanHistory | 清空 agent.history + 删 t_chatHistory |
| generateShotImage | 仅清空历史（Storyboard） |
| replaceShot | 调用 agent.updatePreShots(segmentId, cellId, cell) 局部替换镜头 |

**注意**：`agentsOutline` 每次收到消息都会重新 `setNovel`（从 t_novel 按 chapterIndex 读取），保证章节数据最新；`chatStoryboard` 的 `generateShotImage` 分支目前实现为清空历史（疑似占位/未完成逻辑）。

### G.4 历史保存（saveHistory）

连接关闭或 response_end 时，将 `agent.history`（ModelMessage[]）与 `agent.novelChapters` 序列化 JSON 存/更新 `t_chatHistory`，按 `projectId + type(outlineAgent|storyboardAgent)` 唯一。断线后可恢复多轮上下文。

**差异**：`chatStoryboard` 在读取历史后又强制 `agent.history = []`（L35），说明分镜会话当前**不做历史恢复**。

## H. AI 模型配置解析（getPromptAi）

```sql
SELECT t_config.model, apiKey, baseUrl AS baseURL, manufacturer
FROM t_aiModelMap
LEFT JOIN t_config ON t_config.id = t_aiModelMap.configId
WHERE t_aiModelMap.key = ?   -- 如 outlineScriptAgent / storyboardAgent / storyboardImage
```

- 业务场景通过 `t_aiModelMap.key` 映射到 `t_config` 模型配置
- 大纲 Agent 用 `outlineScriptAgent`，分镜 Agent 用 `storyboardAgent`，分镜图用 `storyboardImage`，提示词润色也用 `storyboardAgent`
- **注意**：getPromptAi 直接 join 表，若 `configId` 为 null（首次 init 时 t_aiModelMap 全 null，见数据模型文档问题1）则查不到配置，此时 ai 层按空配置兜底

## I. 设计特点总结

1. **两级 Agent 嵌套**：主 Agent 把子 Agent 作为 Tool 委派，LLM 自主编排流程，兼顾整体调度与专业分工
2. **结构化输出强约束**：大纲用 zod EpisodeData、资产生成用结构化 relevantAssets，配合 best-effort 容错解析保证稳定
3. **提示词可配置化**：所有 agent 提示词（main/a1/a2/director/segment/shot/generateImagePrompts）都存在 `t_prompts`，支持 customValue 覆盖，无需改代码即可调 prompt
4. **工具按角色隔离**：Storyboard 的 segmentAgent/shotAgent 拿到不同工具集，约束行为边界
5. **异步非阻塞图片生成**：分镜图生成不阻塞 Agent 对话流，通过事件推送进度，前端可实时查看
6. **内存态 + WS 推送**：Storyboard 的 segments/shots 存内存，通过事件推前端落库，保证实时交互
7. **统一基座**：两 Agent 复用相同的 `buildEnvironmentContext / buildConversationHistory / buildFullContext / invokeSubAgent / createSubAgentTool / call` 模板

## J. 潜在问题与改进点

1. **`getStoryline` 工具的 description 是占位文案**（`"Get the weather in a location"`），误导 LLM，应改为真实语义描述
2. **`chatStoryboard` 历史恢复被注释/强制清空**（L35 `agent.history = []`），断线后无法恢复分镜会话上下文，与 saveHistory 的目的矛盾
3. **`generateShotImage`（WS 消息）分支逻辑异常**：实现为清空历史而非触发生成，疑似未完成
4. **内存态分镜易丢失**：segments/shots 仅存内存，若 Agent 会话中途断开，已生成的分镜丢失，前端需自行持久化兜底
5. **`args` 恒为 null**：toolCall 事件上报 `args: null`，前端无法看到工具调用参数，调试受限
6. **子 Agent 每次重建上下文**：invokeSubAgent 用 `buildFullContext` 拼接环境+历史+任务，但**不带 t_novel 原文全量**（仅 getChapter 按需取），依赖 LLM 主动调用
7. **硬编码兜底提示词**：多处 `"不论用户说什么，请直接输出Agent配置异常"`，配置缺失时交互不友好
8. **代码冗余**：storyboard 顶部注释掉的 SYSTEM_PROMPTS、大量 console.log 调试输出、重复的 gridLayout 算法（imageSplitting 与 generateImagePromptsTool 各实现一份）可抽公共模块
9. **并发图片生成资源消耗**：`Promise.all` 同时生成多个分镜图，多个 4K 宫格图 + sharp 分割对内存/GPU 压力大，无队列限流
10. **`getSubAgentTools` 与 `getAllTools` 工具重复注册**：getAllTools 中同时展开 segmentAgent/shotAgent 的全部工具，与顶层独立注册重复，工具集边界可能被打破（子 Agent 之外主 Agent 也能直接用 addShots 等）

### K.2 剧本智能体（scriptAgent）真实实现

`src/agents/scriptAgent/index.ts` 采用**决策层 + 执行子 Agent** 双层结构：

**决策层 `runDecisionAI`**：
1. 读取技能文件 `skills/script_agent_decision.md` 作为 system prompt（**从技能目录按文件名读取**，非硬编码）
2. 组装项目信息（名称/类型/简介/画风/画幅/章节数）+ 记忆 `buildMemPrompt`
3. `u.Ai.Text("scriptAgent:decisionAgent", think, level).stream()` 流式调用
4. 工具集 = `memory.getTools()`（deepRetrieve）+ `useTools()`（4 个业务工具）+ `createSubAgent()`（4 个执行子 Agent）
5. onFinish 时把去 XML 标签后的完成结果写入记忆

**执行子 Agent（createSubAgent 返回 4 个工具）**：

| 子工具 | 技能文件 | 子 Agent key | 名称 | 记忆 key | 输出 XML |
|---|---|---|---|---|---|
| run_sub_agent_storySkeleton | script_execution_skeleton.md | scriptAgent:storySkeletonAgent | 编剧 | assistant:execution:storySkeleton | `<storySkeleton>` |
| run_sub_agent_adaptationStrategy | script_execution_adaptation.md | scriptAgent:adaptationStrategyAgent | 编剧 | assistant:execution:adaptationStrategy | `<adaptationStrategy>` |
| run_sub_agent_script | script_execution_script.md | scriptAgent:scriptAgent | 编剧 | assistant:execution:script | `<scriptItem name="剧本名称">` |
| run_supervision_agent | script_agent_supervision.md | scriptAgent:supervisionAgent | 编辑 | assistant:supervision | 无 |

- 每个子 Agent 独立 `u.Ai.Text(key, ...).stream()`，用 `consumeFullStream` 消费，支持 reasoning（思考流）、text-delta、error、finish 分块
- 子 Agent 完成后通过 `removeAllXmlTags` 剥离 XML 存入记忆
- **剧本子 Agent 特殊性**：会先查 `o_script` 现有剧本列表（`id:名称`）提供给 LLM，避免覆盖已有剧本
- **决策层 → 子 Agent 的消息切换**：`ctx.msg.complete()` 后 `resTool.newMessage("assistant", name)` 新建消息，实现单 socket 上的多消息流

**业务工具（`src/agents/scriptAgent/tools.ts`）**：

| 工具 | 输入 | 作用 |
|---|---|---|
| get_novel_events | chapterIndexs: number[] | 查 `o_novel` 章节事件（含 thinking 进度） |
| get_planData | key: "storySkeleton"\|"adaptationStrategy"\|"script" | 经 socket.emit("getPlanData") 反向取工作区数据 |
| get_novel_text | chapterIndex: string | 查章节原文 chapterData |
| get_script_content | ids: string[] | 查剧本内容，拼 `<scriptItem name="">` |

**工作区数据（`o_agentWorkData` 表）**：`getPlanData.ts` 按 `{projectId, key: "scriptAgent"}` 读取，缺省时插入 `{storySkeleton:"", adaptationStrategy:""}`，并动态附上 `o_script` 列表。

### K.3 技能体系（skill）真实实现 —— 核心被遗漏能力

技能体系由 `src/utils/agent/skillsTools.ts` 实现，是**可插拔的 Agent 能力层**，分三部分：

**① frontmatter 解析（parseFrontmatter）**
- 技能需以 `---` 包裹 frontmatter，含 `name`（技能名）与 `description`（描述）字段，缺失即报错
- 支持 `>`/`|` 折叠块、多行值、引号剥离

**② 技能工具（createSkillTools）**——最核心：
- **`activate_skill` 工具**：列出现有技能，LLM 按 description 匹配后调用，把技能文件正文（去 frontmatter）+ 关联资源列表打包成 `<skill_content name="...">` 注入上下文；`activated` Set 防重复激活
- **`read_skill_file` 工具**：读取已激活技能目录下的**资源文件**（.md），返回 `<skill_content>` 包裹内容
- 两者均带**路径穿越防护**（`isPathInside`），资源文件相对 `skillsRoot` 的安全校验

**③ 技能加载（useSkill / createArtSkills / useProductionSkills）**
- `useSkill({ mainSkill, workspace, attachedSkills })`：主技能文件 + 二级 workspace 资源 + 三级 attachedSkills 递归资源
- **productionAgent 的动态技能绑定**：`createArtSkills(artName, storyName)` 与 `useProductionSkills(artName, storyName)` **按项目的 `artStyle`（画风）与 `directorManual`（导演手册）**，从 `skills/art_skills/<画风>/driector_skills/*.md`、`skills/story_skills/<手册>/driector_skills/*.md`、`skills/production_skills/*.md` 扫描技能，经 frontmatter 解析后注入 `activate_skill` 工具
- **scriptAgent 的技能绑定**：各子 Agent 直接 `readFile(skills/<固定文件名>.md)` 作为 system prompt

**技能管理路由（`src/routes/setting/skillManagement/`）**——经核对仅 3 个：
- `POST /setting/skillManagement/getSkillList`：fast-glob 扫描 skills 目录下所有 `**/*.md`，返回相对路径数组
- `POST /setting/skillManagement/getSkillContent`：按 path 读取技能内容（有 `isPathInside` 越界校验）
- `POST /setting/skillManagement/saveSkillContent`：按 path 写回内容（有越界校验 + 文件存在校验）

### K.6 向量化记忆系统（Memory）—— 被遗漏的重点

`src/utils/agent/memory.ts` 是**基于向量嵌入的长期记忆**，与旧版简单的 chatHistory 完全不同：

- **存储**：`memories` 表，字段含 `id(uuid)/isolationKey/type(message|summary)/role/content/embedding(JSON)/relatedMessageIds/summarized/createTime`
- **写入 add()**：插入 message + 计算 embedding；每累积 `messagesPerSummary=3` 条未总结消息，用 AI 生成摘要并存 summary，标记已总结
- **读取 get()**：返回三部分
  - `shortTerm`：最近 5 条未总结消息
  - `summaries`：最近 10 条摘要
  - `rag`：对当前输入做 embedding，`cosineSimilarity` 向量搜索 top 3 相关消息
- **deepRetrieve()**：三级召回——向量搜摘要 → AI 判断相关性（judgeSummaryRelevance）→ 展开 relatedMessageIds 拉原始消息
- **工具**：`deepRetrieve`（memory.getTools() 返回），供 Agent 主动深度回忆
- **可调配置**：存 `o_setting` 表（messagesPerSummary/summaryMaxLength/shortTermLimit/summaryLimit/ragLimit/deepRetrieveSummaryLimit）
- **隔离**：`isolationKey`（如 `${projectId}:scriptAgent`）隔离各 Agent 记忆

| 工具 | 输入 | 作用 |
|---|---|---|

| add_deriveAsset | assetsId/id/name/desc | 新增或更新衍生资产（写 `o_assets` + `o_scriptAssets`，再 emit addDeriveAsset 同步前端）；**容错**：id 传 "null"/"" 时规范为 null |

**串行队列（createSocketQueue）**：`delayMs=800` 的串行 Promise 链，确保多个 socket 写操作排队执行，**避免并发过高导致 socket 假死**（generate_storyboard / add_flowData_storyboard 使用）。

**flowDataSchema 数据模型**（productionAgent 工作区的 zod schema，也是前端画布数据结构的权威定义）：

```typescript
{
  script: string,                              // 剧本内容
  scriptPlan: string,                          // 拍摄计划
  storyboardTable: string,                     // 分镜表
  assets: [{ id, name, type: role|tool|scene|clip,
             prompt, desc, derive: [{id, assetsId, prompt, name, desc, src, state, type}] }],
  storyboard: [{ id, duration, prompt, associateAssetsIds[], src, index? }],  // 分镜面板
  // （workbenchData 含 name/duration/resolution/fps/cover/gradient；posterItem 含海报）
}
```

**productionAgent 子 Agent**：derive_assets / generate_assets / director_plan / storyboard_gen / storyboard_panel / storyboard_table / supervision（详见 K.5）

### M.4 通用基础设施

**① `src/utils/ai.ts`**：`u.Ai.Text(key, think?, level?)` 统一文本模型入口，按业务 key（如 `scriptAgent:decisionAgent`）分配模型，支持思考模式

**② `src/socket/resTool.ts`** —— 完整的 Socket 流式消息协议（AI 消息 → 前端渲染的核心）：
- **消息生命周期**：`newMessage()` 建消息（emit `message`，status=pending）→ `content:add` 加内容块 → `content:update` 流式更新 → `message:update` 标记完成/停止/错误
- **内容块类型**（`chatMessagesData.d.ts`）：`text` / `markdown` / `thinking` / `search` / `image` / `suggestion` / `toolcall` / `activity` / `reasoning`
- **thinking 自动解析**：`AutoThinkingTextStream` 扫描模型输出的 ` 思考内容` / ` 回答内容` 标签，自动把思考段拆为独立 thinking 内容块（含耗时统计）
- **ToolCallStream**：工具调用的参数/结果流式（appendArgs/appendResult/setResult/updateEventType）
- **ReasoningBuilder**：reasoning 子内容流式

**③ `src/utils/agent/embedding.ts`** —— 记忆向量化的底层：
- 基于 **@huggingface/transformers + onnxruntime-web**，本地 ONNX 模型（默认 `all-MiniLM-L6-v2`，fp16），`transformersEnv.allowRemoteModels=false`（纯本地）
- `getEmbedding(text)`：feature-extraction + mean pooling + normalize → 返回 Float32Array 向量
- `cosineSimilarity(a, b)`：点积计算余弦相似度
- 模型文件路径/量化类型从 `o_setting`（modelOnnxFile/modelDtype）读取

### M.5 Socket 路由层（`src/socket/routes/`）

scriptAgent 与 productionAgent 路由结构一致，实现 `socket.io` 命名空间处理器：

- **鉴权**：`handshake.auth.token` 用 `o_setting.tokenKey` 做 JWT 校验，无效即 `socket.disconnect()`
- **上下文**：`handshake.auth.isolationKey` 必需；productionAgent 额外带 `projectId/scriptId`
- **入站事件**：
  | 事件 | 处理 |
  |---|---|
  | chat | 调用 `runDecisionAI(ctx)`，含 abortController 取消、错误隔离 |
  | updateThinkConfig | 更新 `thinkConfig.think + thinlLevel(0-3)` |
  | stop | `abortController.abort()` 停止生成 |
  | updateContext（仅 productionAgent）| 动态切换 isolationKey/projectId/scriptId，重建 ResTool（导演台切集数用）|
- **出站事件**：message / message:update / content:add / content:update（由 ResTool 产生）

## N. 审视结论（已据 master 源码修正）

对照真实源码，此前文档的几点**需要修正**：

1. **修正**：`skillManagement` 后端**只有 getSkillList/getSkillContent/saveSkillContent 三个路由**；前端 `scanSkills.ts` 调用的 `POST /setting/skillManagement/scanSkills` **在后端 master 中不存在**（返回 `{totalFiles, insertedCount, ...}` 的接口实际是缺失的，前端会报错或走 catch）——这是前后端接口不一致的 bug
2. **修正**：scriptAgent 的"技能"实现方式是**决策层 + 4 个执行子 Agent 各自读固定名技能文件**，而非单一技能注入；productionAgent 才是**按画风/导演手册动态扫描技能**注入
3. **确认**：技能体系确实是**可插拔 markdown 能力层**，frontmatter（name/description）驱动 + activate_skill/read_skill_file 工具 + 路径穿越防护，设计成熟
4. **新发现（被遗漏的重点）**：**向量化记忆系统 Memory**（embedding + rag + deepRetrieve + 自动摘要）是旧版完全没有的核心能力，本应单独成章
5. **确认**：新版数据表统一 `o_` 前缀，记忆存 `memories` 表，与旧版 `t_` 前缀差异显著

> 因此，用户最初"缺技能、缺工具"的直觉，在**新版 master** 中得到印证：技能体系（skill）、更丰富的工具面（get_novel_*/get_planData/子 Agent 委派）、向量化记忆、agent 部署等能力均已补齐。旧版 v1.0.6 仅是这些能力的早期简化形态。
