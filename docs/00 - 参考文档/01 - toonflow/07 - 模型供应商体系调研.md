# Toonflow 模型供应商体系调研

> 分析对象：`refer/Toonflow-app-master/data/vendor/*.ts`（11 个供应商适配模板）+ `src/utils/vm.ts`（沙盒加载）+ `src/utils/vendor.ts`（模型装配）+ `src/routes/setting/vendorConfig/*`（供应商配置接口）
> 分析日期：2026-08-09
> 核心问题：**这些供应商的"接口"是否一致？**

## A. 结论先行

**分两层看，结论不同：**

1. **供应商对平台暴露的适配器接口 —— 完全一致（统一契约）。**
   所有供应商都遵循**同一套适配器接口**：必须导出 `vendor`（配置对象）+ 4 个能力函数（`textRequest / imageRequest / videoRequest / ttsRequest`），并由同一套沙盒（vm2）统一加载、同一批全局工具注入执行。正是靠这套统一契约，平台才能对任何厂商"即插即用"、无缝切换。

2. **厂商真实的第三方 HTTP API —— 完全不一致。**
   每个厂商的**鉴权方式、请求端点、请求/响应结构、参数格式、异步模式（同步 vs 异步轮询）、结果获取方式**都不同。这些差异全部被**封装在各自适配器内部消化**，对上层不可见。

> 一句话概括：**"平台内部接口统一、厂商外部 API 各异"，差异由适配器抹平。**

## B. 统一适配器契约（Vendor Adapter Contract）

### B.1 供应商文件结构

每个供应商是一个独立的 `.ts` 文件，`data/vendor/{id}.ts`，**必须导出**以下字段（`src/routes/setting/vendorConfig/addVendor.ts` 第 70-73 行会强制校验）：

| 导出字段 | 类型 | 说明 |
|---|---|---|
| `vendor` | `VendorConfig` | 供应商配置（必导） |
| `textRequest` | `(m, think, tl) => any` | 文本模型调用，返回 Vercel AI SDK 的 chat model 实例 |
| `imageRequest` | `(c, m) => Promise<string>` | 图片生成，返回**有头 base64** 字符串 |
| `videoRequest` | `(c, m) => Promise<string>` | 视频生成，返回**有头 base64** 字符串 |
| `ttsRequest` | `(c, m) => Promise<string>` | 语音生成（暂未开放），返回有头 base64 |
| `checkForUpdates?` | `() => Promise<{...}>` | 可选：检查适配器更新 |
| `updateVendor?` | `() => Promise<string>` | 可选：拉取最新适配器代码 |

> 未实现的能力函数保留空实现 `return ""`，**不可省略导出**。这是"接口一致"的硬约束。

### B.2 VendorConfig 统一结构

```typescript
interface VendorConfig {
  id: string;        // 唯一 ID，作文件名，禁止冒号/特殊符号
  version: string;   // 语义化版本 "x.y"
  name: string;      // 供应商名称
  author: string;
  description?: string; // 支持 Markdown
  icon?: string;     // base64 图标
  inputs: { key; label; type: "text"|"password"|"url"; required; placeholder? }[];
  inputValues: Record<string, string>; // 用户在界面填写的密钥/地址
  models: (TextModel | ImageModel | VideoModel | TTSModel)[];
}
```

### B.3 四类模型能力（由 `type` 区分）

| 类型 | 接口 | 关键字段 |
|---|---|---|
| `TextModel` | `textRequest` | `think: boolean`（是否支持思考）、思考等级 `thinkLevel: 0-3` |
| `ImageModel` | `imageRequest` | `mode: ["text"\|"singleImage"\|"multiReference"]`、`associationSkills?` |
| `VideoModel` | `videoRequest` | `mode: VideoMode[]`、`audio: "optional"\|false\|true`、`durationResolutionMap` |
| `TTSModel` | `ttsRequest` | `voices: {title, voice}[]` |

### B.4 视频模式统一抽象（VideoMode）

跨厂商共用的视频输入模式，是"接口一致"的典型体现：

```
"text"                纯文生视频
"singleImage"         单张首帧图
"startEndRequired"    首尾帧（两张必填）
"endFrameOptional"    首尾帧（尾帧可选）
"startFrameOptional"  首尾帧（首帧可选）
["imageReference:9", "videoReference:3", "audioReference:3"]  多模态参考（数字为数量上限）
```

### B.5 参考图统一抽象（ReferenceList）

所有厂商的图/视频/音频引用统一为：

```typescript
type ReferenceList =
  | { type: "image"; sourceType: "base64"; base64: string }
  | { type: "audio"; sourceType: "base64"; base64: string }
  | { type: "video"; sourceType: "base64"; base64: string };
```

平台侧统一以 **base64** 形式传入；适配器内部决定如何上传/引用。

## C. 加载与执行机制（同一套沙盒）

### C.1 加载链路

```
用户保存适配器代码 (tsCode)
  → sucrase transform(TS→JS)          （addVendor.ts / vendor.ts）
  → vm2 沙盒 runCode(jsCode)           （src/utils/vm.ts）
  → exports 暴露统一对象（vendor + 4 函数）
```

### C.2 沙盒注入的全局工具（各厂商共用，接口一致）

`src/utils/vm.ts` 第 21-43 行向每个适配器注入**同一批**工具：

| 注入 | 来源 | 用途 |
|---|---|---|
| `axios` / `fetch` | 原生 | 发 HTTP 请求 |
| `logger` | 内置 | 日志 |
| `jsonwebtoken` | 库 | JWT 签名（可灵等用它鉴权） |
| `crypto` | Node | 加密 |
| `FormData` | 库 | 文件上传 |
| `zipImage` / `zipImageResolution` | sharp | 图片压缩/改分辨率 |
| `mergeImages` | sharp | 多图拼合 |
| `urlToBase64` | axios | URL → base64 |
| `pollTask(fn, interval, timeout)` | 内置 | **统一异步轮询** |
| `createOpenAI` / `createDeepSeek` / `createZhipu` / `createQwen` / `createAnthropic` / `createOpenAICompatible` / `createXai` / `createMinimax` / `createGoogleGenerativeAI` | Vercel AI SDK | 文本模型统一封装 |

> **关键**：文本模型统一走 Vercel AI SDK 的工厂函数；异步生成统一用 `pollTask` 轮询。这让"调用方式"在平台层完全一致，厂商差异只在适配器函数体内部。

### C.3 模型装配（vendor.ts getModelList）

模板内 `models` 与数据库 `o_vendorConfig.models` 字段**合并去重**（按 `modelName`），即用户可手动在数据库里追加模型，平台自动聚合。

## D. 各供应商逐一分析

| ID | 名称 | 版本 | 能力 | 鉴权 | 说明 |
|---|---|---|---|---|---|
| openai | OpenAI标准接口 | 2.0 | text | apiKey + baseUrl(`/v1`) | 纯文本，`createOpenAI`，无图/视频 |
| deepseek | DeepSeek | 2.1 | text | apiKey + baseUrl(`/v1`) | 纯文本，`createOpenAICompatible` + 思考注入，思考强度映射 |
| volcengine | 火山引擎(豆包) | 2.4 | text/image/video | apiKey + baseUrl(`/v3`) | 能力最全，text 走 AI SDK，image 走 `/images/generations`，video 走 `/contents/generations/tasks` |
| klingai | 可灵AI | 2.0 | video | accessKey + secretKey + baseUrl | 纯视频，JWT(HS256) 鉴权，多端点（omni/text2video/image2video/multi-image2video） |
| minimax | MiniMax(海螺AI) | 2.1 | text/image/video | apiKey + baseUrl | 视频三阶段（提交→查询→取文件） |
| toonflow | Toonflow官方中转 | 2.x | text/image/video | apiKey | **聚合平台**，内置多厂商模型路由 |
| atlascloud | AtlasCloud MASS | 2.x | text/image/video | apiKey + chatBaseUrl + mediaBaseUrl | 聚合平台，双基地址，模型名带命名空间 |
| grsai | Grsai | 2.x | text/image/video | apiKey + baseUrl | Google Gemini 风格适配 |
| vidu | Vidu开放平台 | 旧版 | image/video | apiKey + baseUrl(`/ent/v2`) | **旧版模板**（见 E） |
| volcengineSd2 | 火山引擎sd2.0真人 | 2.x | video | apiKey + baseUrl + ak/sk + groupId + tos | 专用真人视频，需 TOS 上传参考图，6 个配置输入 |
| null | 空模板(开发模板) | 2.0 | text | apiKey + baseUrl | 开发/引导模板，含完整 AI 生成规范注释 |

### D.1 OpenAI 标准接口（openai.ts）
- 纯文本，模型 `gpt-4o / gpt-4.1 / gpt-5.x` 系列。
- `textRequest` 直接 `createOpenAI({ baseURL, apiKey }).chat(model)`。
- `image/video/tts` 均为空实现。
- 定位：**标准 OpenAI 格式入口**，可改地址接任意 OpenAI 兼容服务。

### D.2 DeepSeek（deepseek.ts）
- 纯文本，`deepseek-v4-pro / deepseek-v4-flash`，支持思考（思维链）。
- 用 `createOpenAICompatible` + 自定义 `fetch` **注入 thinking/reasoning_effort**。
- 思考强度映射：`0/1/2 → high`，`3 → max`（DeepSeek 仅支持 high/max）。
- `image/video/tts` 空实现。

### D.3 火山引擎·豆包（volcengine.ts）— 能力最全
- **text**：`createOpenAICompatible`，注入 `thinking:{type:"enabled"}` 与 `reasoning_effort`（minimal/low/medium/high）。
- **image**：`POST /images/generations`，含像素尺寸表（1K/2K/4K × 多种比例），`response_format:url`、`watermark:false`，单图/多图参考；按模型版本（seedream-3.0/4.0/4.5/5.0-lite）差异化处理尺寸与参数。
- **video**：`POST /contents/generations/tasks` 提交 → `GET .../tasks/{id}` 轮询（`pollTask`，间隔 10s，超时 30min），`succeeded/failed/expired/cancelled` 状态机；支持 `generate_audio`。
- 参考：多模态参考模式（`imageReference`/`videoReference`/`audioReference`）映射到 `content[].role`。

### D.4 可灵AI（klingai.ts）— 纯视频、JWT 鉴权
- **鉴权**：`accessKey + secretKey`，用 `jsonwebtoken` 生成 **HS256 JWT**（`iss/exp/nbf`，30 分钟），每次提交/轮询重新生成。
- **视频**：按模型与模式选择端点：
  - Omni 模型（kling-video-o1/v3-omni）→ `POST /v1/videos/omni-video`
  - 文生视频 → `POST /v1/videos/text2video`
  - 图生/首尾帧 → `POST /v1/videos/image2video`
  - 多图参考 → `POST /v1/videos/multi-image2video`
- 统一 `submitAndPoll`：提交返回 `data.task_id` → 轮询 `task_status`（`succeed/failed`）→ `task_result.videos[0].url` → `urlToBase64`。
- 无文本/图片。

### D.5 MiniMax 海螺（minimax.ts）— 视频三阶段
- **text**：`createOpenAI`，走 MiniMax 的 OpenAI 兼容地址。
- **image**：`createOpenAI` + OpenAI 图片接口封装；`海螺图像V1`/`Live版`。
- **video**：三阶段：
  1. `POST /v1/video_generation` 提交（`base_resp.status_code===0`）
  2. `GET /v1/query/video_generation?task_id=` 轮询（`status: Success/Fail`）
  3. `GET /v1/files/retrieve?file_id=` 取下载地址 → `urlToBase64`
- 参考图先用 `zipImage` 压到 20MB 内。

### D.6 Toonflow 官方中转（toonflow.ts）— 聚合平台
- 单 apiKey，**内部按模型名路由**到不同厂商适配逻辑：
  - Gemini/nano 系 → `POST /chat/completions`，从 markdown 提取图片（`extractFirstImageFromMd`）
  - 豆包/seedream 系 → `POST /image/generateImage` + `GET /image/getImageStatus` 轮询；`POST /video/generateVideo` + `GET /video/getVideoStatus` 轮询
  - GPT/全能图片 → `POST /image/generateImage`
- 内置模型：Seedance 2.0/1.5、Wan2.6、ViduQ3、Kling-Video-O1/V3-Omni、Seedream 5.0/4.5、全能图片G-2.0 等。
- 定位：**官方统一出口**，一个 Key 访问多厂模型。

### D.7 AtlasCloud MASS（atlascloud.ts）— 聚合平台
- 双基地址：`chatBaseUrl`（文本）+ `mediaBaseUrl`（媒体），均固定不可改。
- 模型名带命名空间：`deepseek-ai/deepseek-v4-pro`、`openai/gpt-image-2/text-to-image`、`bytedance/seedream-v5.0-lite/sequential`。
- text 走 `createOpenAICompatible`；image/video 走异步轮询（`pollTask`）。
- 无 tts。

### D.8 Grsai（grsai.ts）— Google Gemini 风格
- **text**：`createGoogleGenerativeAI`。
- **image**：`POST /v1/draw/nano-banana`（nano-banana 系）或 `POST /v1/draw/completions`，`POST /v1/draw/result` 轮询。
- **video**：`POST /v1/video/veo` + `/v1/draw/result` 轮询。
- 无 tts。

### D.9 Vidu 开放平台（vidu.ts）— 旧版模板
- **注意**：这是**旧版模板**，`textRequest` 签名与 v2 不同——返回 `{ url, model }` 而非 AI SDK chat 实例，且抛"仅支持视频大模型"。
- image：`POST /reference2image`，`Token` 鉴权，`checkTaskResult(task_id)` 轮询。
- video：`POST /video_generation` 类接口。
- 定位：**历史遗留适配器**，与新版 v2 契约不完全兼容（但平台仍能加载）。

### D.10 火山引擎 sd2.0 真人（volcengineSd2.ts）— 专用真人视频
- 6 个配置输入：apiKey + baseUrl + **火山 ak/sk + groupId + TOS Endpoint + TOS Bucket**。
- 仅 video，支持 Seedance 2.0/1.5 音画同生；**需上传参考图到火山 TOS**（对象存储）以构造签名 URL。
- text/image/tts 空实现。

## E. 新旧两代模板差异（重要发现）

| 维度 | 新版 v2 模板 | 旧版模板（vidu） |
|---|---|---|
| `textRequest` 签名 | `(model, think, thinkLevel) => chat实例` | `(model) => {url, model}` |
| 统一注入工具 | `pollTask` / `createOpenAI*` / `ReferenceList` | `checkTaskResult` / `imageBase64[]`（自定义） |
| 参考图 | `referenceList: ReferenceList[]`（base64） | `imageBase64: string[]` |
| 视频模式 | 统一 `VideoMode[]` | 各自实现 |

> 说明：`null.ts`（空模板）是**官方开发模板**，内含 14 条 AI 代码生成规范（禁止外部包、命名规范、结构分区、返回值规范、异步处理、错误处理等），用于引导用户/AI 生成新的合规供应商适配器。

## F. 对"接口一致性"的最终总结

**一致的部分（平台层契约）：**
1. 每个供应商 = 1 个 `.ts` 文件，统一 7 个导出字段、统一 `VendorConfig` 结构。
2. 四类模型能力（text/image/video/tts）统一抽象，`mode`/`audio`/`durationResolutionMap` 字段统一。
3. 统一 `ReferenceList`（base64 引用）与 `VideoMode`（视频输入模式）。
4. 统一沙盒加载（vm2）、统一注入工具（axios/pollTask/urlToBase64/Vercel AI SDK 等）。
5. 统一异步轮询（`pollTask`）、统一结果形式（文本→chat 实例、媒体→有头 base64）。
6. 统一模型装配（模板 models 与数据库 models 合并去重）。
7. 统一校验（addVendor/updateCode 强制导出 + zod 校验 vendor 结构）。

**不一致的部分（厂商真实 HTTP API，被封装在适配器内）：**
1. **鉴权**：Bearer Key（OpenAI/豆包/中转）、JWT HS256（可灵）、ak/sk + TOS 签名（火山sd2）、Token（Vidu）等。
2. **端点**：`/images/generations`、`/contents/generations/tasks`、`/v1/videos/omni-video`、`/v1/video_generation`、`/image/generateImage`、`/v1/draw/completions`、`/reference2image` 等各不相同。
3. **请求/响应结构**：状态码字段（`code`/`status_code`/`base_resp.status_code`）、状态枚举（`succeeded`/`Success`/`succeed`）、结果字段（`data[].url`/`task_result.videos[].url`/`file.download_url`）各异。
4. **同步 vs 异步**：部分图片同步返回，部分与视频一样需轮询；轮询间隔/超时不同。
5. **能力覆盖**：有的纯文本（openai/deepseek）、有的纯视频（kling/volcengineSd2）、有的全能力（volcengine/minimax/中转）。

## G. 设计价值与可借鉴点（对自研短剧平台的启示）

Toonflow 用"**统一适配器契约 + 每厂商一适配器 + 沙盒动态加载**"实现了极强的扩展性与开放性：
- **即插即用**：新增厂商只需写一个 `.ts` 模板，平台无需改代码，且支持在线编辑/热更新。
- **能力抽象**：把视频千奇百怪的输入模式收敛为 `VideoMode`，把图/音/视频引用收敛为 `ReferenceList`，上层业务（分镜/资产/导演台）完全不感知厂商差异。
- **结果归一**：统一以"有头 base64 / chat 实例"返回，业务层拿到的是同构数据。
- **可控开放**：用 zod 校验 + 沙盒隔离 + 模板规范，兼顾扩展性与安全性。

> 自研平台若采用类似"供应商适配器"模式，建议：① 统一能力契约（text/image/video/tts + mode 抽象）；② 统一参考图/结果格式；③ 提供空模板与生成规范引导第三方接入；④ 用沙盒或插件机制隔离第三方代码。
