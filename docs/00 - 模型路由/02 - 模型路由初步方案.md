# 模型路由中心方案

> 模型端：模型路由、异步任务、主机管理、存储管理、Key 管理
> 定位：独立部署的通用模型调度层，对外提供 API，供短剧平台等系统通过密钥接入。

---

## 一、背景与目标

**背景**
- 部署多台大模型执行机（图片生成 / 视频生成），每台机器同一时刻只能执行 **单个** 任务（单任务并发）。
- 因此需要多台机器组成主机池，并需要一个统一的 **路由中心** 负责任务分发、调度与状态管理。
- 每台执行机使用独立镜像，启动后 **主动自动连接** 路由中心。

**目标**
1. 统一接入多台异构执行机（图片 / 视频模型）。
2. 任务自动路由到空闲机器，做到负载均衡与并发调度。
3. 支持 **异步任务**：提交即返回 taskId，通过轮询或回调获取结果。
4. 主机自动化接入、心跳监控、上下线管理。
5. 统一存储（输入 / 输出文件）与模型 Key 安全管理。

---

## 二、总体架构

```
┌────────────┐  提交任务/查结果   ┌──────────────────────┐
│  业务系统    │◄─────────────────►│      路由中心 (Go)      │
│ (短剧平台等) │      REST API     │  ┌──────────────────┐ │
└────────────┘                    │  │ 调度器 / 任务管理   │ │
                                  │  │ 主机注册/心跳       │ │
                                  │  │ 存储管理           │ │
                                  │  │ Key 管理          │ │
                                  │  └──────────────────┘ │
                                  └─────────▲────────────┘
                                            │ 心跳 + 拉取任务 (Pull)
                        ┌───────────────────┴───────────────┐
                        │             执行机集群              │
                        │  ┌────────┐  ┌────────┐  ┌──────┐ │
                        │  │ 图片执行机 │  │ 视频执行机 │ ... │ 每台独立镜像
                        │  └────────┘  └────────┘  └──────┘ │
                        └───────────────────────────────────┘
```

**核心交互模型（Worker 拉取）**
- 执行机启动后携带自身元数据（机型、能力、模型、token）向路由中心 **注册 / 心跳**。
- 执行机空闲时主动向路由中心 **拉取** 任务（Pull）。
- 路由中心根据任务类型与机器能力、负载进行路由，把可执行任务下发。
- 执行机完成 / 失败后上报结果，路由中心落库并触发回调。

## 三、核心模块

### 1. 模型路由（调度）
- **能力注册**：每台机器声明支持的能力（image / video）与对应模型。
- **路由策略**：
  - 按任务类型（图片 / 视频）过滤主机池。
  - 选择空闲机器（当前无任务）。
  - 多空闲时负载均衡（轮询 / 最少任务）。
  - 可选优先级队列（紧急任务插队）。
- **任务状态机**（参照豆包）：`queued → running → succeeded / failed / expired / cancelled`
- **进度上报**：执行机执行期间周期性上报进度（0~100%），路由中心落库，调用方可通过查询接口实时查看。
- **失败重试**：机器失败、超时、断连后重排队（可配置最大重试次数）。
- **超时控制**：通过 `execution_expires_after` 设置任务过期时间，超时置为 `expired` 并回收主机。

### 2. 异步任务
- 提交任务返回 `task_id`，任务异步执行（参照豆包：提交即返回 id，不阻塞）。
- **结果获取**：通过 `task_id` 轮询状态；或提交时注册 **callback_url（Webhook 回调）**，任务状态变化时主动推送。
- **回调格式**：回调请求内容结构与查询任务 API 返回体一致，包含 task_id、status、进度、结果地址（预签名 URL）等。
- 任务包含：输入（文件地址 / 参数）、模型、优先级、回调地址、幂等键（可选）、过期时间 `execution_expires_after`。
- **进度上报**：任务带 `progress` 字段（0~100）；回调支持 `queued / running / succeeded / failed / expired` 等状态变化推送。
- 支持任务取消（机器在线时可下发取消指令）。

### 3. 主机管理
- **注册 / 心跳**：执行机启动上报能力与 token，周期性心跳维持在线。
- **状态监控**：online / offline / busy / error；超时未心跳自动置离线并回收其任务。
- **上下线管理**：手动禁用、摘除；扩容即新机器接入，缩容即摘除。
- **镜像化**：每台机器独立镜像，含 agent 客户端 + 模型运行时，启动后自动完成注册。

### 4. 存储管理
- 任务输入 / 输出文件统一存储，采用 **S3 协议**（兼容 MinIO / AWS S3 / 腾讯 COS 等），路由中心下发预签名 URL 供执行机读写。
- 生命周期管理：任务结束后按策略保留 / 清理中间文件；结果文件通过预签名 URL 返回给调用方（可带有效期）。

### 5. Key 管理
- 管理各模型厂商 / 各执行机的 **API Key / Token**，集中加密存储。
- 调用方使用独立的接入 Key（调用方鉴权），执行机使用独立的机器 Token（机器鉴权）。
- 密钥脱敏展示、支持轮换、权限隔离。

---

## 四、数据模型（核心表）

- **host**：机器信息（id、名称、ip、能力、模型、状态、心跳时间、token）
- **model**：模型定义（名称、类型 image/video、参数模板）
- **task**：任务（id、类型、模型、参数、输入/输出地址、状态、进度、优先级、机器id、回调、幂等键、过期时间、时间）
- **task_retry**：重试记录
- **key**：接入方 Key / 机器 Token / 厂商 Key（加密）
- **callback_log**：回调投递记录（用于可靠回调重投，含投递次数、下次投递时间、状态）

---

## 五、技术栈

- 语言：**Go**
- API：REST（异步用 task_id 轮询 + Webhook 回调）
- 存储：MySQL / PostgreSQL（任务、主机、key、回调日志）
- 队列：**不引入独立消息队列**；用数据库行级锁 + 定时扫描（调度器）实现轻量任务队列与拉取
- 文件存储：**S3 协议**（MinIO / AWS S3 / 腾讯 COS 等），预签名 URL 交互

## 六、主要 API（示意，参照豆包异步任务设计）

**任务状态**：`queued / running / succeeded / failed / expired / cancelled`
提交任务返回 `task_id`；任务带 `progress`（0~100）与结果字段（预签名 URL）。

**调用方（业务系统）**
- `POST /api/v1/tasks` 提交任务 → 返回 `task_id`
  - 参数：model、content/参数、优先级、callback_url（可选）、幂等键（可选）、execution_expires_after（可选）
- `GET  /api/v1/tasks/{id}` 查询状态 / 进度 / 结果
- `POST /api/v1/tasks/{id}/cancel` 取消任务

**执行机（Agent）**
- `POST /api/v1/agents/register` 注册（能力、模型、token）
- `POST /api/v1/agents/heartbeat` 心跳
- `GET  /api/v1/agents/tasks/pull` 拉取任务
- `POST /api/v1/agents/tasks/{id}/result` 上报结果
- `POST /api/v1/agents/tasks/{id}/progress` 上报进度（0~100）
- `POST /api/v1/agents/tasks/{id}/cancel/ack` 取消确认

**管理端**
- `GET /api/v1/hosts` 主机列表 / 上下线管理
- `GET /api/v1/tasks` 任务列表 / 重试
- `POST /api/v1/keys` 接入方 Key 与机器 Token 管理
- 存储 / 清理策略配置

## 七、执行机（镜像）说明

- 每台执行机 = **基础镜像（模型运行时 + Agent 客户端）**，独立运行。
- Agent 启动步骤：读配置 → 注册 / 心跳 → 空闲拉任务 → 执行 → 周期性上报进度 → 上报结果 → 循环。
- 同一镜像可参数化区分图片 / 视频机型；也可用不同镜像。

## 八、回调可靠性分析与建议

**目标**：调用方通过 Webhook 接收任务状态变化，回调投递需尽量可靠、避免重复与丢失。

**问题点**
1. **丢失**：网络抖动、调用方服务不可用导致回调发不出去。
2. **重复**：重试机制会导致同一事件被推送多次。
3. **顺序**：状态可能乱序到达（如 succeeded 先到、running 后到）。
4. **鉴权**：回调地址被伪造，或收到第三方伪装的回调。

**建议方案**
1. **可靠投递（至少一次）**：
   - 回调写 `callback_log` 表，记录事件、目标地址、投递次数、下次投递时间。
   - 调度器定时扫描未成功投递的记录，指数退避重试（如 5s/15s/60s/5min…），设置最大次数（如 6~10 次）。
   - 超过最大次数进入 **死信（dead-letter）**，标记状态供人工/管理端排查。
2. **幂等（去重）**：
   - 每个回调事件带唯一 `event_id`（或 task_id + status + revision），调用方按 `event_id` 幂等处理，丢弃重复推送。
   - 我方在回调日志记录已投递的事件，避免同一事件重复生成。
3. **顺序与幂等消费**：
   - 回调体携带任务完整状态（含进度、结果），调用方以收到的**最新状态**为准，不依赖到达顺序。
4. **鉴权与签名**：
   - 回调请求头携带签名（HMAC-SHA256，用调用方密钥对 body 签名）或 token，调用方校验后处理，防伪造。
5. **超时确认**：
   - 调用方需在限定时间内（如 5 秒）返回 2xx；否则视为失败进入重试（对齐豆包"5 秒未成功即重试"的语义）。
6. **兜底**：
   - 即使回调全部失败，调用方仍可随时通过 `GET /tasks/{id}` 主动查询，保证最终一致性。
