# 短剧平台系统架构

> 基于《短剧平台初步方案》设计
> 技术选型：后端 Go ｜ 前端 React（管理端 Ant Design，用户端自定义）｜ PostgreSQL + Redis + S3 ｜ 平台内置任务调度

---

## 一、架构目标与原则

- **模块化单体起步**：以清晰分层的单体应用交付，后续按需拆分为微服务，避免过早分布式复杂度。
- **用户端 / 管理端分离**：逻辑上分用户端与管理端两大业务面，共享同一套领域模型与通用能力。
- **任务异步化**：一切 AI 生成任务（图/视频/分镜等）异步执行，提交即返回，通过轮询 / 状态查询获取结果。
- **空间协作模型**：以"空间"为资源归属与权限边界，贯穿所有创作资源。
- **可观测、可审计、可计费**：关键操作留痕；任务与资源消耗可计量、可对账。

## 三、分层与模块划分

### 3.1 表现层（前端）
- **用户端 Web**：面向创作者，自定义设计，追求美观大方的视觉体验。
- **管理端 Web**：面向运营/管理员，采用 Ant Design 中后台组件。

### 3.2 接入层
- **API 网关**：统一入口，负责身份鉴权、限流、路由、请求日志、跨域、静态资源托管。

### 3.3 后端领域模块（按业务拆分）
| 模块 | 职责 |
|------|------|
| 认证/用户 | 注册登录、账号安全、用户资料、游客 |
| 空间/权限 | 空间、成员、角色、协作权限、RBAC |
| 创作 | 通用设置、剧本拆分、资产（含衍生资产）、视频制作（含分镜图/多轨合成/配音）、Agent 配置、自由画布、剧集操作台 |
| 作品/发布 | 作品管理、草稿、回收站、发布审核流 |
| 任务与接单 | 任务发布、意向登记（仅信息与意向，客服线下撮合） |
| 发现/互动 | 信息流、详情、评论、点赞、收藏、关注、举报 |
| 消息 | 通知中心 |
| 商业化/计费 | 套餐（多版本、月付/年付）、积分包、订阅、订单、积分、计费计量 |
| 智能体 | 双层 Agent、技能体系（画风库/导演叙事技能库）、记忆系统、思考等级、流式结构化输出、TTS 配音 |
| 管理端 | 概览、用户管理、内容管理、算力任务、智能体模型、平台配置、运营 |
| 教学/帮助 | 课程、FAQ、工单 |

### 3.4 核心引擎（跨模块公共能力）
| 引擎/服务 | 职责 |
|-----------|------|
| 任务调度引擎 | 异步任务队列、并发控制、失败重试、进度上报（覆盖分镜/图/视频/配音等生成） |
| 模型接入与调度治理层 | 统一封装四类模型 API（llm / t2i / i2i / t2v / i2v / audio）；厂商/模型/Key 三级管理、每 Key 并发限制、路由负载均衡、429 切换重试 |
| 资源/资产服务 | 素材上传/下载/存储管理、预签名 URL、生命周期清理、衍生资产生成 |
| 智能体引擎 | 双层 Agent 决策、技能激活（画风库/导演叙事技能库）、记忆检索（RAG/向量化）、思考等级、流式结构化输出、TTS 配音 |
| 图片/视频合成引擎 | 图片编辑（原图+参考资产图）、多轨时间线（视频/图片/音频）合成 |
| 审核服务 | 作品/内容/任务信息审核流，驱动状态流转 |
| 计费计量服务 | 记录任务与资源消耗，统一按积分扣减，生成流水与对账 |
| 消息服务 | 站内信/通知生成与送达 |

### 3.5 数据层
- **PostgreSQL**：业务主库（用户、空间、创作、作品、订单、任务元数据等）。
- **Redis**：缓存（热点数据、会话）、任务队列、分布式锁、限流计数。
- **S3 兼容存储**：图片/视频/音频等文件对象存储，预签名 URL 直传直读。

## 四、关键交互流程

### 4.1 登录与空间初始化
```
登录成功 → 检查是否存在默认空间 → 无则自动创建个人空间 → 返回会话与默认空间信息
```

### 4.2 生成任务（以"生成资产图/视频"为例，统一异步模式）
```
提交生成请求
  → 校验权限/额度/参数
  → 创建任务（状态 queued），扣费/冻结额度
  → 写入任务队列（Redis）
  → 返回 task_id
调度器消费队列
  → 分配并发额度，状态 → running
  → 模型适配层调用对应厂商模型
  → 周期性回写进度（0-100）
  → 成功：结果写入 S3，回填结果地址，状态 → succeeded
  → 失败：按策略重试，超限则 failed
前端通过 GET 轮询任务状态/进度，完成后展示结果
```

### 4.3 作品发布审核流
```
作品 → 提交发布（可选）→ 状态 待审核 → 管理端审核
  → 通过：已发布（进入发现流）
  → 驳回：已驳回（返回作品，可修改后重新提交）
```

### 4.4 空间协作
```
空间所有者/管理员 → 邀请成员 → 成员加入空间 → 按成员角色授权访问空间内资源
```

## 五、架构决策记录（ADR）

| 决策 | 选择 | 理由 |
|------|------|------|
| 服务形态 | 模块化单体 | 团队小、启动快、事务简单；模块边界清晰便于后续拆分 |
| 任务调度 | 平台内置 | 需求明确、可控；以 Redis 队列 + 调度器实现，不依赖外部系统 |
| 与"模型路由中心"关系 | 平台内置调度为现状；路由中心方案可作为后续调度能力增强/拆分的参考（调度策略、状态机、重试、回调可靠性的设计可直接复用） | 避免重复开发，保留演进路径 |
| 语言 | Go | 并发与调度友好，部署简单，团队已有 Go 基础 |
| 存储 | PG + Redis + S3 | PG 能力全面、JSON/检索友好；Redis 做缓存与队列；S3 做对象存储 |
| 鉴权 | JWT + RBAC + 空间角色 | 无状态、可水平扩展；两级权限（平台角色 + 空间角色） |

## 六、非功能性设计

### 6.1 安全
- 密码加盐哈希；敏感字段加密（密钥、密钥对）。
- 接口鉴权：用户 JWT、管理端独立权限校验。
- 支付/账单防重放、幂等键。
- 操作审计日志。

### 6.2 性能与扩展
- 热点数据 Redis 缓存；读多写少走缓存。
- 任务并发受额度控制，削峰填谷。
- 无状态服务，可水平扩展；静态资源与文件走 CDN/网关。

### 6.3 可靠性与容灾
- 任务失败重试、超时回收；幂等键防重复提交。
- 数据库主从、定期备份；文件对象存储高可用。
- 日志与告警，异常可追溯。

### 6.4 可观测性
- 结构化日志、指标、慢查询监控、任务成功率/耗时监控。
