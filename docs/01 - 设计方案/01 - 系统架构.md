> **文档版本**：v1.0

## A. 架构目标 + 范围声明 + 四阶段分期路标

### A.1 架构设计目标（5 项铁律）

| 维度 | 目标值 | 设计原则 |
|------|--------|---------|
| **模块化单体起步** | 2026年底前不拆微服务 | 清晰分层、模块边界明确，PostgreSQL CPU > 70% 连续7天为唯一拆分触发条件 |
| **任务异步化优先** | 所有AI生成任务100%异步 | 提交即返回202，WebSocket + 轮询双通道推送进度 |
| **空间协作贯穿全局** | 所有创作资源归属Space | 以「空间」为资源归属与权限边界，替代原始 user_id 扁平归属模型 |
| **可计费可审计** | 每笔积分变动100%可追溯 | 余额快照写入每一行流水，DB事务+行锁+唯一约束防双扣 |
| **竞品差异化能力落地** | 对齐LuxReal 90%核心体验 | 短剧Agent四步流水线、Step3叙事单元5件套、重新规划双Tab、节点式自由画布、多变体parent_id自关联、跨集资产复用不扣费 |

### A.2 全量功能范围声明（30 张表 + 6 大核心域）

本平台全量交付覆盖以下六大业务域，对应PostgreSQL 30张核心业务表（参见08号Schema设计）：

#### A.2.1 短剧Agent创作流水线（核心价值）
- **项目四级结构**：项目Project → 集Episode → 叙事单元Beat → 镜头块ShotGroup → 单镜头Shot（五层一对多）
- **Step1剧本拆分**：LLM自动识别【场景：地点—时间】标记、▲镜头描述、角色对话格式，拆分四级结构
- **Step2资产生成**：五类资产（角色/场景/道具/智能镜头/通用素材）批量出图，**跨集资产复用不重复扣费**（asset_usage_logs判定）
- **Step3视频生产**：叙事单元头部**标准5件套**（名称/时长/历史版本/重新规划/生成视频）、**重新规划弹窗双Tab**（Tab1分镜脚本可编辑 ↔ Tab2重生成分镜参数面板）、8字段专业分镜模板（时长/景别/运镜/视角/主体/背景/台词/环境音）
- **Step4成片预览**：镜头块级时长刻度矩阵（每段独立播放）、合成整片MP4、导出工程文件/全素材ZIP包
- **多变体机制**：角色变体（服装/造型/年龄）parent_id自关联、场景日夜变体（10种time_of_day）

#### A.2.2 空间协作域
- 个人空间 + 团队空间双模式
- 5级角色权限（OWNER/ADMIN/EDITOR/MEMBER/VIEWER/BILLING_ONLY）
- 邀请链接 + 成员管理 + 团队席位配额

#### A.2.3 自由画布域（核心差异化）
- **架构形态纠正**：不是时间线剪辑器，是**节点式可视化工作流编辑器**（对标n8n/LangFlow，前端基于React Flow实现）
- 28种节点类型：输入/LLM分镜/资产生成/视频生成/控制流分支循环/人工审核/注释/画布模板引用等
- 画布9件套全局工具：Add node / Canvas template / Shapes形状 / History历史 / Keyboard shortcuts快捷键 / Help帮助 / 迷你地图 / 重置视图 / 缩放选择
- Agent流水线 ↔ 自由画布双向转换（一键转画布/导回继续合成）
- 画布模板库（官方5套：电商创意短片/IP潮舞迁移/影视运镜/多宫格Pro/80集标准）
- 自动快照（30s/变更防抖5s/Ctrl+S/版本标签）

#### A.2.4 多轨剪辑域
- 镜头块级多轨时间线（视频/图片/音频三轨叠加）
- FFmpeg concat demuxer无损拼接、字幕烧录、水印注入
- 导出矩阵：MP4/GIF/WebM/PNG帧/SRT字幕/FCPXML-Premiere工程/EDL剪辑表

#### A.2.5 发现社区域
- 作品公开分享页 / 广场信息流
- 点赞/收藏/评论/关注作者
- 作品一键转模板（用户→模板市集）

#### A.2.6 任务接单域
- 需求发布、创作者意向登记
- 任务状态流转、客服线下撮合

#### A.2.7 商业化会员订阅域（双轨计费）
- **套餐订阅轨**：4档月卡Basic/Advanced/Premium/Ultimate + 年卡（省2个月）+ 连续包月自动续费
- **积分包轨**：3档积分包（10元1000点/50元6000点/200元30000点）
- **积分冻结解冻扣费流水线**：批量生成前冻结 → 成功扣/失败退（永不倒扣）
- **首购双重加赠**：首月5折 + 限时积分加赠（进阶15%/高级18%/旗舰18%）
- **支付宝当面付**：扫码支付 + 异步回调7步验签
- **跨集复用豁免扣费透明化**：point_transactions.cross_episode_reuse_exempt_amount字段公示

### B.3 四类 Worker 角色详细职责

| Worker角色 | 进程名 | 任务类型（ENUM_TASK_TYPE） | 节点类型 | 并发数建议 |
|-----------|--------|--------------------------|---------|----------|
| **Worker-Split** | `worker -role=split` | SCRIPT_SPLIT剧本拆分、STORYBOARD_PLAN_V1_LUXCHAT分镜规划、PROMPT_REFINEMENT_LUXGEM提示词润色 | CPU节点即可，调用LLM API | 单机4并发 |
| **Worker-Asset** | `worker -role=asset` | CHAR_IMAGE_GEN角色图、SCENE_IMAGE_GEN场景图、PROP_IMAGE_GEN道具图、SMART_SHOT_GROUP_PRE_ANCHOR智能镜头预演抽锚 | GPU节点（8G显存+） | 单GPU 2并发 |
| **Worker-Video** | `worker -role=video` | VIDEO_SEGMENT_GEN单镜头视频、VIDEO_GROUP_CONCAT镜头块拼接、FINAL_VIDEO_COMPOSE整片合成、3DGS_RENDER_*实时渲染 | GPU大显存节点（A100 80G优先） | 单A100 4并发 |
| **Worker-Export** | `worker -role=export` | ENGINEER_FILE_EXPORT工程文件导出、PNG_FRAMES抽帧、SRT_SUBTITLE字幕、FCPXML_PREMIERE工程 | CPU节点，FFmpeg密集型 | 单机8并发 |

**调度器自写设计要点**：
1. **优先级队列**：Redis ZSET，`priority*1e9 + timestamp`做score，支持VIP用户自动提权到7/8
2. **取任务原子性**：`ZPOPMIN + SETNX worker_lock:{task_id}` LUA脚本保证不重复派发
3. **心跳续租**：Worker每30s续lock，超时60s自动回收重排（防进程崩溃丢任务）
4. **指数退避重试**：失败1次15s、2次60s、3次180s，≥3次进FAILED_DEAD死信队列人工处理

## E. ADR 架构决策记录（7 项关键选型）

### ADR-01：后端语言选型 — Go (Gin) vs Python FastAPI

| 维度 | Go 1.22 + Gin | Python 3.12 + FastAPI | 胜出方 |
|------|--------------|----------------------|-------|
| **团队匹配** | 团队已有Go基础；部署简单单二进制无依赖 | AI生态全是Python；模型SDK原生Python | **Go** | 用户明确要求技术栈Go；模型接入通过HTTP SDK调用即可（Python做模型独立服务，不在本单体代码内） |
| **并发性能** | Goroutine原生高并发，单API节点支撑10K+ QPS；Worker任务调度调度密集型Goroutine极轻 | FastAPI asyncio单节点2K QPS；多进程GIL受限 | **Go** | 任务调度+API高并发场景Go优势明显；CPU密集型调度Go无GIL |
| **部署运维** | 单静态二进制文件，Docker镜像<50M；AOT无启动延迟 | 需要Python解释器+venv依赖；镜像~800M；冷启动慢 | **Go** | 极简部署降低运维心智；4类Worker同代码库不同flag=1镜像搞定 |
| **类型安全** | 静态强类型编译期检查，空指针/类型错编译期发现 | Pydantic v2运行时校验，类型错误线上才暴露 | **Go** | 计费/财务代码零容忍类型bug |
| **AI Prompt工程** | 字符串拼接稍繁琐；需自己写JSON Schema校验 | Pydantic+instructor强制LLM JSON Schema输出；调试方便 | 平局 | LLM调用统一封装进model引擎，Prompt工程调一次之后稳定不动 |

> **最终决策**：选Go + Gin。模型SDK封装独立engine/model模块，HTTP调用外部模型服务（Python微服务可后期V2单独拆），不在单体混写Python。

### ADR-02：任务调度选型 — Redis 自写调度 vs Celery

| 维度 | Redis + 自写调度器（Lua+ZSET） | Python Celery 5.4 + Redis Broker | 胜出方 |
|------|------------------------------|--------------------------------|-------|
| **语言一致** | 全栈Go同一语言；无跨语言调试壁垒 | Python生态；但Go→Celery跨语言发任务需JSON协议 | **自写** | 用户明确选Go栈；不想混合Python进程 |
| **可控性** | 状态机/优先级/续租/死信全链路100%可见可控；想加什么字段改什么 | 黑盒较多；Flower面板只能看表面；自定义异常难调 | **自写** | 计费核心链路要求完全透明；幂等/续租机制自写最稳 |
| **生态完善** | 需自己实现：重试退避/死信/ETA/并发池；约800行核心代码 | 开箱即用：retry/backoff/dead letter/ETA/rate limit/Flower面板 | **Celery** | 但这些功能自写工作量可控（800行×1个资深Go开发3天搞定） |
| **运维成本** | 只有Redis一个依赖；4类Worker同进程flag切换 | 多一个Python运维面；Flower单独端口；beat单独进程 | **自写** | 减少技术栈数量 |
| **监控面板** | Grafana面板自定义Redis指标（队列长度/死信数/处理耗时） | Flower自带面板直观但功能少 | 平局 | Grafana指标更灵活可定制 |

> **最终决策**：Redis自写调度。优先级ZSET + Lua原子取任务 + Redlock续租心跳 + 指数退避重试 + 死信队列。800行代码换来全链路透明，计费核心零黑盒。参考09号C3节任务状态机完全对齐。

### ADR-03：前端架构选型 — Vite SPA React19 vs Next.js SSR

| 维度 | Vite 5 + React19 SPA（纯前端） | Next.js 14 App Router SSR | 胜出方 |
|------|-------------------------------|--------------------------|-------|
| **SEO需求** | 发现社区作品页需要被百度/谷歌收录才能获客；SSR首屏HTML有内容利于爬虫 | SPA首屏空壳；SEO需另做预渲染方案或Chromium动态渲染 | **Next.js**？但... |
| **团队熟练度** | Vite + React SPA纯前端无学习成本；路由/状态管理简单 | Next.js 14 App Router Server/Client Component心智重；Server Action调试难 | **Vite** | MVP阶段首要是快；SEO放M2发现社区上线时再切（或加 prerender.io） |
| **自由画布复杂度** | React Flow是纯客户端组件（大量DOM节点拖拽、画布平移缩放、MiniMap），SPA跑在客户端性能好无坑 | React Flow在RSC中不兼容；必须全"use client"；SSR对画布性能0提升反而增加复杂度 | **Vite** | 核心差异化功能是自由画布，客户端渲染体验最佳 |
| **首屏性能** | 代码分割+路由懒加载后首屏<3s；CDN缓存index.html；Vite冷启动比Next快 | Next.js SSR首屏TTPB更高（需等后端渲染）；客户端还要hydrate | **Vite** | 产品是后台工具型非内容站，首屏2.5s完全可接受 |
| **部署架构** | 纯静态文件丢CDN即可；无Node服务端运维成本 | 需要Node.js Runtime；SSR/Edge Function；部署复杂度×2 | **Vite** | M0/M1单机Docker Compose部署，不想再加Node进程 |

> **最终决策**：Vite SPA + React19。发现社区M2上线时，若SEO成为痛点，再加 prerender.io 或Chromium动态渲染，或迁移关键页面到Next.js，不影响核心工作台。

### ADR-04：资源归属模型 — 空间协作贯穿全局 vs 扁平 user_id

| 维度 | Space空间贯穿全局（owner_type=USER/TEAM + owner_id） | 扁平user_id归属，团队后期加 | 胜出方 |
|------|-----------------------------------------------------|--------------------------|-------|
| **团队付费定位** | 旗舰月卡¥4900明确是团队定价；高级/旗舰团队席位member_limit字段；多人协作是核心付费动机 | 先单人→加团队字段要做数据迁移（所有表加space_id回填），风险高易出错 | **空间贯穿** | 商业化驱动，团队是高ARPU客户；4档月卡团队席位设计直接对标04号 |
| **计费隔离** | 团队空间/个人空间分开账户；团队充值走企业发票；point_transactions带owner_type，报表清晰 | 团队和个人积分混在user_id下；分不清团队消耗还是个人消耗 | **空间贯穿** | 财务开票/对账刚需；billing模块设计天然按owner_type双轨 |
| **权限粒度** | 空间5级角色OWNER/ADMIN/EDITOR/MEMBER/VIEWER；作品/画布/资产按空间隔离；协作邀请流程 | 扁平只有自己/管理员两级；协作要单独做共享权限复杂度更高 | **空间贯穿** | M1就要上空间协作，先建好owner_type复合索引=后期0迁移 |
| **M0裁剪成本** | projects建表时加owner_type=ENUM(USER/TEAM)+owner_id复合索引；M0强制owner_type=USER不影响MVP | 只加user_id；但M1加团队时迁移projects/episodes/assets/orders等15+表 | **空间贯穿** | 提前加2字段+复合索引=0成本；避免M1大迁移 |
| **查询性能** | (owner_type, owner_id, deleted_at) PARTIAL复合索引一次回表搞定我的项目/资产列表 | 单user_id BTREE索引也行；但团队场景要UNION个人+团队两次查询 | **空间贯穿** | 单查询比UNION快一倍 |

> **最终决策**：空间协作贯穿全局。所有创作资源表projects/episodes/beats/characters/scenes/props/canvas_*/orders/user_points全部加 `owner_type ENUM('USER','TEAM') + owner_id BIGINT + (owner_type,owner_id,deleted_at) PARTIAL复合索引`。M0阶段owner_type强制=USER，M1加TEAM功能无需改表。

### ADR-06：任务进度推送 — WebSocket + 轮询 双通道 vs 纯轮询

| 维度 | WebSocket实时推 + HTTP轮询降级兜底 | 纯HTTP GET /tasks/{id} 3s间隔轮询 | 胜出方 |
|------|----------------------------------|-------------------------------|-------|
| **用户体验** | WS进度0延迟；百分比实时跳；批量生成每成功一张图立即弹卡片✅（200ms内） | 3s延迟=进度卡顿；用户焦虑会刷新页面；批量生成20张图每3s跳一下体验差 | **双通道** | Step3叙事单元头部5件套的「重新规划」「生成视频」等按钮状态要实时；核心体验是实时 |
| **技术复杂度** | Gin有gorilla/websocket成熟库；Redis Pub/Sub分发；连接池+心跳60s；断线重连+降级；多会话同步 | 纯REST无状态；简单直接；无WS升级握手 | 双通道略复杂但可控 | 封装1个engine/notify模块=约600行代码；一次封装全项目复用 |
| **服务器成本** | 单Go节点撑5000并发WS连接（Gorilla官方基准）；10K用户=2台节点 | 10K用户×3s轮询≈3300 QPS，缓存层Redis顶住也行；成本相当 | 平局 | 1000日活规模两者成本无差 |
| **异常兜底** | WS断连→前端自动降级3s轮询；WS恢复→自动升级回WS；用户无感 | 无兜底问题就是轮询本身 | **双通道** | 弱网环境（电梯/地铁/WiFi切换）体验更稳 |
| **余额/消息同步** | 扣费/充值后余额实时刷新不用手动点；通知中心红点实时+1 | 轮询任务接口不返回余额/消息；要多加2个轮询接口成本×3 | **双通道** | billing模块扣费成功后PUBLISH一条balance_change，多端同步 |

> **最终决策**：WebSocket + 轮询双通道。WS推送主通道，3s轮询兜底断连降级。Redis Pub/Sub做分发中间件，跨API节点/Worker节点解耦。封装engine/notify模块统一调度。

### ADR-07：数据库枚举类型 — PostgreSQL原生ENUM TYPE vs VARCHAR + CHECK约束

| 维度 | PostgreSQL原生CREATE TYPE xxx AS ENUM (...) | VARCHAR(32) + CHECK (col IN (...)) | 胜出方 |
|------|------------------------------------------|----------------------------------|-------|
| **类型安全** | 枚举值在类型系统层强校验；插入非法值直接ERROR；PgAdmin/DBeaver等工具自动补全提示 | CHECK约束运行时校验；也能拒绝非法值但无IDE补全 | **ENUM** | 计费/状态机字段不允许写错状态（比如把'RUNNING'写成'RUNING'上线才爆） |
| **存储空间** | 枚举内部是4字节INT；行存储比VARCHAR省很多（状态机表百万行=省20MB+） | VARCHAR('SUCCESS')=7字节每列；JSON序列化没差 | **ENUM** | generation_tasks表量大状态频繁查询；省空间=更多缓存命中 |
| **schema变更成本** | 加值：ALTER TYPE xxx ADD VALUE 'NEW_STATUS'; （PG9.1+支持事务内加值，无需锁表）；但⚠️不能删值不能改值名；要删需重写类型+全表迁移 | 加值：ALTER TABLE xxx ALTER col TYPE VARCHAR(32); CHECK约束加新值一行ALTER；但删值/改值名简单直接 | **ENUM** | 业务枚举一旦上线基本只加不改不删；ENUM加值一行搞定0风险 |
| **Golang类型映射** | 08号文档ENUM_开头的枚举有40+；Go端定义对应常量+String()方法；sql.Scanner/driver.Valuer接口实现；scan直接成Go枚举类型强类型 | Go端定义string类型别名；CHECK约束=数据库侧保证；Go侧写常量但无编译期检查 | **ENUM** | 双端强类型=双层保险；状态机switch case枚举编译器警告遗漏分支 |
| **08号Schema对齐** | 08号D/E节所有ENUM_*类型完整列出（ENUM_USER_ROLE/ENUM_PROJECT_TYPE/ENUM_PROJECT_STEP/ENUM_PROJECT_STATUS/ENUM_GENERATION_STATUS/...共约30个枚举类型） | 用VARCHAR会丢失08号枚举设计的严谨性；后期类型bug排查难 | **ENUM** | 严格对齐08号Schema设计；ENUM名/取值100%匹配 |

> **最终决策**：PostgreSQL原生ENUM TYPE。golang-migrate的up.sql里先CREATE TYPE所有枚举类型，再建表引用。Go端对应定义每枚举为自定义类型+实现sql.Scanner/driver.Valuer接口，所有取值常量化。
