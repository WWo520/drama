### 二、内容安全审核（三级，必接入官方内容安全 API）

#### 2.1 审核层级

用户提交内容 → 机器自动审核（阿里云/腾讯云文本+图片+视频安全）→ 命中疑似违规 → 人工审核（管理端内容管理）

| 内容类型 | 机器审核 API | 审核通过后才能做的动作 |
|---|---|---|
| 剧本文本（Step1 粘贴上传） | 阿里云 Green 文本检测 | 允许进入 Step2 资产 |
| 生成图（Step2 资产 / Step3 分镜图） | 腾讯云 Yinsuda 图片检测 | 允许展示在作品里 / 发布到发现页 |
| 生成视频（Step3 成片） | 视频审核（抽帧 + 语音转文字审核） | 允许导出 / 发布到发现页 |
| 发现页评论 / 作品简介 | 文本审核 | 正常展示 |

2.1.1 审核 API 调用时机：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（同步阻塞还是异步回调？超时时间？API 宕机时降级为「待审核」入队列，人工审核通过后解锁）
2.1.2 审核分等级别：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（Pass/Review/Block 三档分数阈值？Review 档进人工池、Block 档直接打回并触发用户违规积分）
2.1.3 多厂商容灾：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（主用阿里云、备用腾讯云，主 API 连续失败 N 次自动切备用；审核结果双厂商一致才通过，不一致送人工）

#### 2.2 审核失败处理

命中色情/暴力/政治敏感 → 自动驳回 + 状态=rejected + 驳回原因 + 用户可以申诉 → 管理员人工二审；3 次违规自动封禁账号 7 天，5 次永久封禁

2.2.1 违规分级与处罚矩阵：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（色情/暴力/政治敏感/涉毒涉赌/人身攻击/虚假信息 各类别首次/二次/三次/四次/五次对应处罚、处罚积分计算、封禁期、违规积分清零周期）
2.2.2 申诉流程：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（申诉入口、申诉材料要求、审核 SLA 48 小时、申诉成功恢复内容+违规记录、申诉失败不可二次申诉的情形）
2.2.3 误判补偿机制：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（机器审核误判导致用户被扣违规积分/封停时间/任务被终止的补偿标准、补偿积分数量、用户感知通知文案）

#### 2.3 审核日志保存

所有审核结果（机器+人工）≥ 保存 6 年（网信办要求）

2.3.1 日志字段完整性：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（content_id / content_hash / submit_user_id / audit_type(machine/manual) / audit_api_vendor / request_id / raw_response_json / score / label / decision(P/R/B) / human_reviewer_id / human_decision / audit_time / ip）
2.3.2 日志存储与检索：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（冷存 OSS + 热存 Elasticsearch，90 天内可全文检索、90 天后归档、6 年后经法务审批方可销毁）
2.3.3 抽检与质量回溯：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（每日随机抽取 1% 已审核内容送质检团队复核、审核员准确率 < 95% 触发培训、模型误判样例沉淀微调数据集）

### 三、个人信息保护与等保三级合规（⏳ 安全+法务确认）

#### 3.1 敏感字段加密存储

手机号/邮箱/真实姓名/身份证号/支付宝账号 → 必须 AES-256-GCM 加密存储，密钥用 KMS 或环境变量，代码仓库绝不出现明文密钥

3.1.1 加密分级：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（一般个人信息加密、敏感个人信息（身份证/人脸）使用独立密钥、密钥层级：根密钥在 KMS 永不导出 → 数据密钥加密存储 → 工作密钥内存中解密使用）
3.1.2 脱敏展示规则：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（手机号 138****1234、邮箱 z***@q**、身份证只显示前 6 后 4；后台管理员查看完整信息必须有「敏感数据查看」角色 + 操作审计 + 双人审批 + 录屏）
3.1.3 密钥轮换与应急：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（自动 90 天轮换、轮换期间双密钥并行解密 7 天、密钥疑似泄漏时一键吊销+紧急重加密脚本、演练频率每季度 1 次）

#### 3.2 密码哈希

Argon2id 算法（比 bcrypt 抗 GPU 暴力破解更强），内存参数 64MB / 迭代 3 / 并行 4

3.2.1 算法版本迁移：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（历史 bcrypt 用户登录成功时透明升级为 Argon2id、升级进度看板、90 天未登录用户强制重置密码）
3.2.2 密码策略：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（最小长度 12、必须含大小写+数字+特殊字符、禁止使用 TOP10000 弱口令、密码有效期 90 天、历史密码 5 次不可复用）
3.2.3 登录防护：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（连续输错 5 次锁 30 分钟、异地/新设备登录需邮箱验证码二次确认、半年未登录触发冻结需申诉解锁）

#### 3.3 异地备份

PostgreSQL 主从（同城）+ 每天全量冷备份到另一云厂商 OSS（跨区域 ≥ 1000 公里，RPO ≤ 24 小时 / RTO ≤ 4 小时）

3.3.1 备份加密：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（备份文件落地前 AES-256 加密、加密密钥独立于生产密钥、异地 OSS Bucket 开启服务端加密 SSE-KMS）
3.3.2 备份校验：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（每次备份完成后计算 SHA-256 校验和、每月随机抽取 1 份备份实际恢复到隔离环境验证数据完整性、校验失败告警升级）
3.3.3 备份访问控制：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（备份 Bucket 仅运维备份专用账号可写、读取需双人审批 + IP 白名单 + MFA、所有读写操作写入 OSS Access Log 保存 ≥ 1 年）

#### 3.4 堡垒机+操作审计

所有生产服务器 SSH 必须过堡垒机，禁止直连；DBA 操作数据库必须走审计代理；运维操作日志 ≥ 保存 1 年

3.4.1 堡垒机选型与部署：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（商业堡垒机/开源 JumpServer、公网入口 MFA 二次验证、最大会话时长、闲置自动断开）
3.4.2 操作审计粒度：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（SSH 命令全量记录、SFTP 文件传输记录、RDP 图形操作录屏、SQL 审计所有 DDL/DML 操作、高危命令（DROP / TRUNCATE / rm -rf / GRANT）触发实时告警 + 自动阻断）
3.4.3 审计日志告警与回看：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（命中高危规则立即推 IM + 短信安全值班人、审计日志仅安全审计员可查询、普通运维权限分离不可看、日志删改必须安全总监审批）

#### 3.5 漏洞扫描

每月至少 1 次全量漏洞扫描（Nessus / AppScan），高危漏洞 72 小时内修复；上线前必须过 1 次第三方渗透测试报告（⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填：找第三方公司出具）

3.5.1 漏洞等级定义与 SLA：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（Critical 24h / High 72h / Medium 7d / Low 30d，CVSS 评分映射、SLA 逾期升级机制）
3.5.2 渗透测试报告闭环：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（高危 100% 修复、中危修复率 ≥ 95%、剩余低危出具风险接受声明由 CTO + 安全负责人签字、复测通过后才算验收）
3.5.3 漏洞赏金计划（M1 启动）：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（接入补天/漏洞盒子、赏金等级金额表、报告处理 SLA、白帽隐私保护、上榜致谢名单）

#### 3.6 接口安全

所有写操作 CSRF Token；上传文件类型白名单+大小限制；文件类型头校验不相信扩展名；SSRF 防护（禁止预签名 URL 回调内网 IP 段 10/172.16-31/192.168/127/169.254）；User-Agent/Referer 校验防止简单爬虫

3.6.1 CSRF 防护实现：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（Double Submit Cookie 模式 / SameSite=Lax / Token 有效期、Token 旋转策略、登出立即失效）
3.6.2 SSRF 防护深度：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（DNS 重绑定防护（解析结果缓存比对）、非 80/443 端口禁止、URL Scheme 白名单仅 http/https、302 跳转禁止跳内网、出站请求走独立隔离 VPC + 专用 NAT）
3.6.3 文件上传纵深防御：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（大小限制、扩展名白名单、MIME 头 + 文件幻数双重校验、图片二次压缩重绘去除 EXIF 与 WebShell、独立域名 OSS Bucket 存放 + 签名 URL 有时效 + 禁止执行权限）
3.6.4 接口限流与防刷：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（IP 维度 / User 维度 / API 维度令牌桶参数、验证码触发阈值、429 错误码提示、黑名单 Redis Set 自动解封周期）
3.6.5 SQL 注入与 XSS：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（所有查询参数化 ORM 禁止拼 SQL、HSTS 强制 HTTPS、Content-Security-Policy 白名单、HttpOnly + Secure + SameSite Cookie 属性、输入长度上限）

### 四、上线前安全 Checklist（✅ 全绿才能开生产公网入口）

#### 4.1 水印与版权

- [ ] AIGC 水印：3 张样图/样视频检测数字水印/可见水印有效，截屏/压缩/裁剪 50% 后仍可提取溯源
- [ ] 用户协议三大件（服务协议/隐私政策/UGC 规范）法务签字盖章扫描件存档，版本号 commit hash 记录
- [ ] 版权投诉受理 SOP 测试：模拟权利人投诉 3 类场景（文本/图片/视频），24h 内下架动作符合预期
- [ ] 未成年人模式开关测试：开启后夜间锁号/充值上限/时长控制 10 条用例全通过
- [ ] user_agreement_logs 10 名新用户注册/登录/首次创作三阶段同意留痕记录齐全

#### 4.2 内容安全审核

- [ ] 内容安全 API 接入自测 50 条违规样例（色情/暴力/政治/涉毒/人身攻击各 10 条）命中率 ≥ 98%
- [ ] 误判率测试：100 条合规内容误杀率 ≤ 2%

## 第二篇 · 部署与运维手册（CI/CD + K8s + 备份恢复）

### 一、部署架构拓扑（⏳ 上线前 DevOps 画实际架构图）

```
用户 → Cloudflare CDN（静态资源/图片/视频缓存）
     → Nginx Ingress Controller（限流/WAF/HTTPS 证书）
     → K8s 集群
        ├─ api-server（无状态 HPA 自动伸缩 2~10 副本，CPU>60% 扩）
        ├─ task-workers（4类Deployment：split/asset/video/export，GPU 节点调度 taint）
        ├─ ws-server（WebSocket Hub 有状态，2~4 副本 + Redis Pub/Sub 跨副本消息）
        ├─ PostgreSQL 16 主从（Cloud 托管 RDS 或 Zalando Spilo Operator）
        ├─ Redis 7 哨兵集群 3 节点（Bitnami Helm）
        ├─ MinIO 分布式 4 节点（或云厂商 OSS 托管）
        └─ 监控栈：Prometheus + Grafana + Loki + AlertManager
```

### 二、CI/CD 流水线（GitHub Actions 或 GitLab CI，⏳ 运维选工具后补命令）

#### 2.1 分支策略

main = 生产 / staging = 预发 / develop = 开发；PR 必须过单测 + lint + typecheck 才能合并

2.1.1 分支保护规则：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（main/staging 禁止直接 push，PR 需 1 个 approve + CI 绿灯，admin 也不例外；删除分支、force push 关闭）
2.1.2 Tag 发布规范：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（release/vX.Y.Z 打 tag 触发正式构建、tag 推送前需 CHANGELOG 已更新、tag 消息格式签名）
2.1.3 Hotfix 流程：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（hotfix/xxx 从 main 拉出，合并回 main 和 staging、hotfix 走紧急绿色通道合并审批人数降低到 1 人 + 值班人员验证）

#### 2.2 CI 触发步骤

① 代码静态检查：go vet + golangci-lint / eslint + tsc --noEmit
② 单元测试：go test -cover ≥ 70%（核心事务扣费/幂等/一致性代码覆盖率 ≥ 90%）/ vitest 前端组件测试
③ Docker 镜像构建 + 推送到 Harbor 私有镜像仓库（带 commit hash 标签）
④ DB 迁移测试（staging 环境跑一遍迁移 + rollback）
⑤ 部署 staging（自动）→ 运行 E2E Playwright 15 条用例（03 功能 F 章）→ 失败自动回滚
⑥ 手动审批 → 部署生产（蓝绿发布：先切 10% 流量看错误率，30 分钟无异常全量）

2.2.1 静态检查基线：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（golangci-lint 启用的 linters 列表、.eslintrc 规则覆盖度、CI 失败阻断等级：error 必须 0、warning 允许上限 ⏳ 待填）
2.2.2 单元测试覆盖率门禁：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（总体行覆盖率 ≥ 70%、核心包 billing/payment/auth 单独门槛 ≥ 90%、覆盖率不达标 PR 直接失败）
2.2.3 Docker 镜像安全：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（Trivy 扫描镜像 CVE、Critical/High CVE 阻断构建、基础镜像定期更新、镜像签名 Cosign 防篡改）
2.2.4 蓝绿发布流程细节：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（蓝绿 Deployment 命名规则、Ingress annotation 切权重方式、10%→30%→50%→100% 分步观察点、错误率阈值 > ⏳ 待填 立即回滚）
2.2.5 手动审批人：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（生产发布必须 CTO + 运维值班长 2 人审批、审批有效期 24 小时、审批留言记录归档）

#### 2.3 版本号

Semver 1.0.0 / 1.1.0 / 1.0.1（小修复），每次 release 必须附 changelog

2.3.1 Changelog 规范：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（Keep a Changelog 1.1.0 格式、Added/Changed/Fixed/Removed/Security 五段式、每一条关联 PR 号和 Issue 号）
2.3.2 回滚策略：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（保留最近 N 个稳定版本镜像、kubectl rollout undo / Helm rollback、DB 迁移 revert 脚本与回滚演练频率）

### 三、备份与恢复 SLA（⏳ 上线前填真实 RPO/RTO 指标）

| 资源 | 备份策略 | 保留周期 | RPO（最大丢失） | RTO（恢复时间） |
|---|---|---|---|---|
| PostgreSQL 数据 | 每小时增量 WAL 归档 + 每天凌晨 3 点全量 pg_basebackup | 增量 7 天 / 全量 30 天 / 每月末 1 份永久归档 | ≤ 1 小时 | ≤ 4 小时（从备份恢复+验证） |
| Redis | 每 15 分钟 RDB AOF 混合持久化 + 云盘快照 | 7 天 | ≤ 15 分钟 | ≤ 30 分钟 |
| OSS/S3 视频/图片/素材 | 跨区域复制（CRR）到另一地域 Bucket + 对象版本控制开启 | 永久（用户未删） | 0（CRR 同步） | ≤ 1 小时切流量到副本区域 |
| 配置文件/密钥/证书 | KMS + 密钥托管 + Git 加密仓库同步 | 永久 | ≤ 1 小时 | ≤ 30 分钟重新颁发 |

#### 3.1 PostgreSQL 备份细化

3.1.3 大表分区备份优化：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（日志类表按周分区、老分区只读归档到冷存储、备份时跳过冷分区加速）

### 三、业务看板 Daily Weekly Monthly Report（⏳ 产品+数据确认指标口径后填）

#### 3.1 Daily DAU 看板

新增/活跃/留存(次日/7日/30日)/生成视频数/平均首片时长

3.1.1 指标口径定义：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填
  - 新增用户：当日注册成功且首次登录的去重 user_id
  - DAU：当日有至少一次登录 / 访问 3 个以上页面 / 执行 1 次写操作（三者满足其一）的去重 user_id
  - 次日留存：T 日新增用户在 T+1 日回访（满足 DAU 条件）的比例
  - 生成视频数：Step4 成片导出成功且状态 = success 的任务数（去重 project_id 再 × 集数）
  - 平均首片时长：首次生成的 Step4 成片视频时长（秒）取算术平均
3.1.2 实时刷新频率：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（每 15 分钟聚合一次 vs 准实时 1 分钟、看板历史数据可回溯，支持按日/周/月切换对比）
3.1.3 目标基线：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（M0 上线第 1 月 DAU 目标 / 次日留存目标 / 首片时长目标，未达标周复盘动作）

#### 3.2 Weekly 商业化看板

付费用户数/ARPU/ARPPU/首购率/续费率/积分消耗分布(哪类任务扣最多)

3.2.1 指标口径定义：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填
  - 付费用户数：本周发生至少 1 笔成功支付订单 status=paid 的去重 user_id
  - ARPU = 本周总收入 / 本周 DAU 去重用户数
  - ARPPU = 本周总收入 / 本周付费用户数
  - 首购率 = 本周 first_purchase_flag=True 的用户 / 本周新增注册用户
  - 续费率（M1 才有）= 上周付费用户本周再次付费的比例
  - 积分消耗分布：按 task_type 维度 SUM(points_spent) 占比饼图
3.2.2 同环比与渠道拆解：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（周同比/环比、按 utm_source 渠道拆解付费率 Top3、高 ROI 渠道加投建议自动生成）
3.2.3 异常检测：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填（ARPPU 周环比涨跌 > 20% 高亮红色/绿色标注、首购率下跌自动联动 view_payment_page → payment_success 漏斗拆解定位是哪个环节掉了）

#### 3.3 Monthly 质量看板

各模型成功率/平均生成耗时/失败Top3原因/人工审核通过率/举报处理时效

3.3.1 指标口径定义：⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填
  - 模型成功率 = status=success 的任务 / 任务总数（success+failed+timeout），按 model × task_type 二维表

## 附录 A：生产环境运维 Runbook 速查（按 P0/P1 场景分章）

### A.1 P0-01 全站 5xx 错误率 > 10%

1. 立即：看 K8s api-server Deployment 副本数 + Pod 状态，CrashLoopBackOff 数量
2. 立即：kubectl logs 最近一个 Crash Pod，定位错误栈（OOM / Panic / DB 连接失败 / Redis 挂了）
3. 若新版本刚发布：立即 kubectl rollout undo deployment/api-server 回滚上一版本
4. 若 DB 连接失败：看 RDS 控制台 CPU/连接数，连接打满先 kill 非核心慢 SQL
5. 记录 incident_id，事后 24h 内出 Root Cause + Action Plan

### A.2 P0-02 支付回调漏单（支付宝成功但平台积分未到）

1. 立即：查异常订单工具 `/api/admin/billing/orders/check-missing`，按时间窗拉取单边账
2. 立即：对漏单执行补发脚本 `python3 scripts/fix_missing_payment.py <order_ids>`，事务内补发 + 写 point_adjustments，原因填「P0-02 漏发」
3. 根因查：回调日志 nonce 去重表 / DB 事务提交失败 / WS 推送成功但积分没发？
4. 通知：给所有受影响用户站内信 + 积分补偿（每人额外 ⏳ M0 上线前 1~2 周运营/财务/安全/DevOps 确认后再填 积分作为歉意）

### A.3 P0-03 数据库被误删/全表误更新

1. 立即：停止应用写入 → 切 DB 只读模式，防止脏数据继续写
2. 立即：选择最近一个 PITR 时间点（误操作发生前 N 秒），启动 pg_restore 到临时恢复库
3. 并行：对误更新行用 pg_waldump 解析 WAL 日志反向构造补偿 SQL
4. 恢复完：对比临时恢复库 + 补偿结果一致性，再切回业务，记录 RPO 实际值
5. 事后：DBA 权限 + 审计代理规则升级，DROP/TRUNCATE 命令默认阻断
