## D. 数据一致性 7 大核心要点

### D1. 空间积分归属、生命周期与对账

- **账户选择**：个人空间任务只使用提交者的 `USER` 账户；团队空间任务只使用该团队唯一的 `SPACE` 账户。客户端不得指定扣费账户，也不得在团队余额不足时回退扣个人账户。
- **账户初始化与管理**：创建团队空间或首次启用团队计费时，事务内创建并锁定唯一空间账户；仅 `OWNER`、`ADMIN` 可为团队空间充值或管理其积分。个人默认空间不创建共享账户。
- **任务快照**：提交任务时固化扣费账户、归属类型/ID、空间、项目和操作者。冻结、成功结算、失败/取消/超时解冻以及恢复流程只使用该快照；成员退出、角色变更、空间关闭均不改变历史归因。
- **账务终态**：成功任务仅产生一次实扣；失败、取消、超时和重复/乱序回调仅产生一次原账户解冻。空间余额不足时不创建或投递需冻结的任务，并返回“联系管理员充值”。
- **报表与对账**：成员消耗以空间成功实扣流水中的操作者为准，不维护独立统计副本。任意空间、成员和时间窗的报表必须可回溯为“空间 → 成员 → 任务 → 流水”，其合计与成功实扣流水零差异。
- **空间关闭**：停止接受新任务与新冻结；已冻结任务按既有终态流程结算或解冻。关闭后的余额处理必须保留全量流水与审计，具体退款/迁移政策由商业规则另行定义，不得删除或改写账务。

### D4. 任务幂等：request_id + 唯一索引 + DB 先写再入队

```
[客户端 POST /batch-generate]
    ↓ 客户端必须生成唯一 request_id
[API 层]
  ① INSERT generation_tasks(status='PENDING', request_id, ...)；冲突时读取既有任务
  ② 同一事务内将新任务 CAS 更新为 status='QUEUED'，并写出站投递记录
  ③ 事务提交后由投递器执行 ZADD task:queue:{worker_type} score=ETA
  ④ Redis 不可用或投递失败：保留 QUEUED；补偿器扫描无活动租约的 QUEUED 任务并幂等 ZADD
  ⑤ 返回 task_uuid；重复请求返回同一个任务
```

`request_id` 是客户端提交幂等键；`idempotency_key` 是服务端按“发起者 + 目标资源 + 操作类型”计算的业务幂等键，二者不得互相替代。具体 Redis/Lua/租约实现唯一见 04 D；物理字段与索引唯一见 10。

**反模式**：先入队再写 DB，或将 `SUCCESS` 任务入队。前者会产生幽灵任务，后者违反状态机终态语义。

### D5. 队列：ZSET 原子抢占 + DB CAS + 租约心跳

```
[投递]
  QUEUED 任务 → ZADD task:queue:{worker_type}（score=`eligible_at_ms * 10 + (9 - priority)`；`eligible_at_ms` 与 `next_retry_at` 一致）

[Worker]
  ① Lua 原子：从到期 ZSET 取任务 → 写 task:running → 写 task:lock:{id}(owner, TTL=60s)
  ② DB CAS：仅 UPDATE ... WHERE status='QUEUED' 成功时转 RUNNING，写 started_at 与 heartbeat_at
  ③ 每 30s 以 owner 校验续租至 60s，同时刷新 heartbeat_at；续租失败立即停止提交结果
  ④ 成功：RUNNING→SUCCESS，并在同一计费事务完成扣费
  ⑤ 可重试失败：RUNNING→FAILED_RETRYING，写重试日志与 ETA；到期后 FAILED_RETRYING→QUEUED 并 ZADD
  ⑥ 不可重试或耗尽：RUNNING→FAILED_DEAD，写 DLQ 记录、告警并在同一事务解冻
  ⑦ 仅 owner 可 Lua 释放锁并 SREM running；崩溃后租约失效，由恢复器重新投递
```

**关键保证**：Redis 只负责可恢复投递与租约；数据库 CAS 决定唯一状态迁移；终态回调或迟到 Worker 结果必须因 CAS 失败而被拒绝。同一任务最多产生一次可结算终态。

### D6. S3 对象生命周期：DB 记录与 S3/OSS 双向关联

```
[S3 上传]
  1. 对外接口：POST /uploads/presign，服务端创建 `s3_object_metadata(PRESIGNED, upload_token)`，返回 upload_url + object_key + upload_token
  2. 客户端直传 S3 成功 → POST /uploads/complete(upload_token, object_key, etag, biz_ref_id)
  3. 服务端锁定元数据，HeadObject 校验对象属性和业务对象的空间归属；仅成功后置 `CONFIRMED`，并在同一业务引用事务 `ref_count += 1`

[S3 删除（延迟策略）]
  - 软删作品/资产：仅写业务记录 `deleted_at`，对象继续保留以支持恢复
  - 永久删除或解除最后一个业务引用：同一事务 `ref_count -= 1`；当 `ref_count=0` 时置 `upload_status=DELETE_PENDING`、`delete_after=NOW()+30d`
  - 清理 Worker 到期后幂等删除对象；成功才置 `DELETED`。物理删除元数据前必须再次确认 `ref_count=0`

字段、约束、索引和精确状态迁移以 `10` B3.0/F5 为唯一物理真源；本节不再定义独立删除条件。

[S3 生命周期规则 (对象侧兜底)]
  - /tmp/uploads/ 前缀: 30 天后自动删除 (用户传了但没confirm的)
  - /generated/intermediate/ 前缀: 7 天后自动归档到 Glacier (中间帧/抽锚图)
  - /user-data/{uid}/trash/ 前缀: 30 天后永久删除
```

### D7. 任务失败：解冻积分 + 标记豁免 + 通知用户

```
[Worker任务失败处理 (retry_count >= 3 FAILED_DEAD)]
  BEGIN;
    -- 1. 更新任务状态
    UPDATE generation_tasks SET
      status='FAILED_DEAD',
      error_code=$err,
      completed_at=NOW(),
      thawed_points = frozen_points      -- 失败时 冻结积分全部解冻
    WHERE id=$task_id AND status='RUNNING';

    -- 2. 解冻积分回退账户 (只有之前冻结了的才解冻)
    UPDATE point_accounts SET
      frozen_balance = frozen_balance - $thaw_amount,
      current_balance = current_balance + $thaw_amount
    WHERE id = $acct_id AND frozen_balance >= $thaw_amount;

    -- 3. 写一条解冻流水 (type=UNFREEZE_PARTIAL_FAIL)
    INSERT INTO point_transactions
      (..., txn_type='UNFREEZE_PARTIAL_FAIL', direction='UNFREEZE',
       amount=$thaw_amount, balance_after=..., frozen_after=...,
       description='任务失败解冻退回: 场景图批量4个失败3个, 退回900分')
    VALUES (...);

    -- 4. 对该批次下成功的子任务: 正常扣费 (解冻=0, 扣除成功部分)
    foreach(success_subtask):
      UPDATE point_accounts SET
        frozen_balance = frozen_balance - $subtask_cost;
        -- current_balance 不变, 因为已经冻结了
      INSERT point_transactions (...UNFREEZE_SUCCESS_DEDUCT DEBIT $subtask_cost...)

    -- 5. 发一条站内信通知
    INSERT INTO notifications (user_id, type, title, content) VALUES
      (1001, 'BILLING', '批量生成部分失败', '4个资产中1个成功扣300分, 3个失败退回900分');
  COMMIT;
```

### D8. 跨集资产复用：去重判定 + 豁免明细 + 弹窗透明

```

  输入: project_id=1, episode_id=3, character_variant_ids=[12, 15, 18]
  判定流程:

  5. 用户点"确认生成":

        INSERT INTO asset_usage_logs

        VALUES
          ('CHARACTER_VARIANT', 12, 1, 3, FALSE, TRUE, 0, $task_id, FALSE),  -- 跨集复用免费
          ('CHARACTER_VARIANT', 15, 1, 3, FALSE, TRUE, 0, $task_id, FALSE),  -- 复用豁免
          ('CHARACTER_VARIANT', 18, 1, 3, TRUE,  TRUE, 100, $task_id, FALSE); -- 首次扣费
     c) 入队生成任务 (G3)
     d) 返回结果时前端弹窗大字:
        "本次批量生成预览：总计 300分
         ✅ 跨集复用豁免 2 个 (-200分)
         💰 实际冻结 100分
         任务失败积分自动原路退回"
```

**反模式**：用户看到账单扣了 100分 但不知道为啥少了 → 必须在批量预览弹窗和积分流水中都透明化展示 `cross_episode_reuse_exempt_amount` 字段，用户点进去能展开看是哪 3 个资产复用了、分别是第几集用的。
