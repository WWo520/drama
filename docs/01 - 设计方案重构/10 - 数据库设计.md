## B. 全量数据表逐条字段明细

> **通用约定**：
> - 所有表主键统一 `BIGSERIAL` (自增 64 位整型，性能优于 UUID)
> - 对外暴露 ID 使用 `*_uuid UUID` 字段防遍历
> - 所有表含 `created_at TIMESTAMPTZ DEFAULT NOW()`、`updated_at TIMESTAMPTZ DEFAULT NOW()`、`deleted_at TIMESTAMPTZ NULL`
> - 唯一索引、联合索引均加 `WHERE deleted_at IS NULL` 部分索引条件

### B1. 用户与空间协作层

#### B1.1 users 用户表

| 字段名 | 类型 | Nullable | 默认值 | 约束/索引 | 说明 |
|--------|------|----------|--------|-----------|------|
| id | BIGSERIAL | NOT NULL | - | PRIMARY KEY | 主键 |
| user_uuid | UUID | NOT NULL | gen_random_uuid() | UNIQUE WHERE deleted_at IS NULL | 对外暴露UUID |
| default_space_id | BIGINT | NULL | NULL | BTREE | FK spaces.id 默认空间 |
| email | VARCHAR(128) | NULL | NULL | UNIQUE WHERE deleted_at IS NULL AND email IS NOT NULL | 邮箱登录 |
| phone | VARCHAR(20) | NULL | NULL | UNIQUE WHERE deleted_at IS NULL AND phone IS NOT NULL | 手机登录 |
| password_hash | VARCHAR(255) | NOT NULL | - | - | bcrypt/argon2 哈希 |
| nickname | VARCHAR(64) | NOT NULL | - | - | 显示名 |
| avatar_url | VARCHAR(512) | NULL | NULL | - | 头像 S3/CDN URL |
| bio | VARCHAR(512) | NULL | NULL | - | 个人简介 |
| status | user_status_enum | NOT NULL | 'ACTIVE' | BTREE | 账号状态 |
| vip_level | SMALLINT | NOT NULL | 0 | BTREE | 0免费~4至尊 |
| vip_expire_at | TIMESTAMPTZ | NULL | NULL | BTREE | 到期自动降级为0 |
| language | VARCHAR(8) | NOT NULL | 'zh-CN' | - | 语言偏好 |
| aigc_watermark | BOOLEAN | NOT NULL | TRUE | - | AIGC 水印开关 |
| created_at | TIMESTAMPTZ | NOT NULL | NOW() | BTREE | 创建时间 |
| updated_at | TIMESTAMPTZ | NOT NULL | NOW() | - | 更新时间 (触发器自动维护) |
| deleted_at | TIMESTAMPTZ | NULL | NULL | BTREE PARTIAL | 软删时间戳 |

**关键索引**：
```sql
CREATE INDEX idx_users_status ON users(status) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_vip_level ON users(vip_level) WHERE deleted_at IS NULL;
CREATE INDEX idx_users_vip_expire_at ON users(vip_expire_at) WHERE deleted_at IS NULL AND vip_expire_at IS NOT NULL;
CREATE INDEX idx_users_created_at ON users(created_at DESC) WHERE deleted_at IS NULL;
```

#### B1.3 space_members 空间成员表 (M:N)

| 字段名 | 类型 | Nullable | 默认值 | 约束/索引 | 说明 |
|--------|------|----------|--------|-----------|------|
| id | BIGSERIAL | NOT NULL | - | PRIMARY KEY | 主键 |

| user_id | BIGINT | NOT NULL | - | BTREE | FK users.id |

| joined_at | TIMESTAMPTZ | NOT NULL | NOW() | - | 加入时间 |

## C. 软删约定与唯一索引策略

### C1. 软删字段统一约定

```sql
-- 所有业务表必须包含以下三个时间戳字段
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()                -- 创建时间(永不更新)
updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()                -- 更新时间(触发器自动维护)
deleted_at TIMESTAMPTZ NULL                                   -- 软删时间戳(NULL=未删除, 有值=已删除)
```

### C2. updated_at 触发器自动维护

```sql
-- 全局通用函数
CREATE OR REPLACE FUNCTION trigger_set_timestamp()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 对所有表创建触发器(迁移脚本统一生成)
-- 例: CREATE TRIGGER set_timestamp BEFORE UPDATE ON users
--     FOR EACH ROW EXECUTE FUNCTION trigger_set_timestamp();
```

### C3. 唯一索引加 WHERE deleted_at IS NULL

```sql
-- ❌ 错误：唯一索引包含软删记录，导致删除后无法重建相同唯一值
CREATE UNIQUE INDEX idx_users_email ON users(email);

-- ✅ 正确：部分索引，仅未删除记录参与唯一性校验
CREATE UNIQUE INDEX idx_users_email ON users(email)
  WHERE deleted_at IS NULL AND email IS NOT NULL;

-- ✅ 联合唯一索引同理
CREATE UNIQUE INDEX idx_space_members_unique ON space_members(space_id, user_id)
  WHERE deleted_at IS NULL;
```

### C4. BTREE 索引加 WHERE deleted_at IS NULL

```sql
-- ❌ 错误：索引包含软删记录，膨胀且查询效率低
CREATE INDEX idx_projects_space ON projects(space_id);

-- ✅ 正确：所有业务查询WHERE条件默认带 deleted_at IS NULL
CREATE INDEX idx_projects_space_status ON projects(space_id, status)
  WHERE deleted_at IS NULL;
```

### C5. 不适用软删的特殊表

以下**流水/日志类表永不UPDATE，不使用软删，直接物理DELETE按日期分区归档**：

| 表名 | 原因 | 归档策略 |
|------|------|---------|
| point_transactions | 财务流水不可篡改，写一次永不改 | 按月分区，保留 ≥ 5年 |
| billing_records | 计费明细不可变 | 按月分区，保留 ≥ 3年 |
| audit_logs | 审计日志不可篡改 | 按月分区，保留 ≥ 2年 |
| generation_task_retry_logs | 重试运行日志 | 按季度分区，保留 ≥ 1年 |
| canvas_auto_save_snapshots | 快照按策略清理 | AUTO类保留50条，TAG类永久 |
| asset_usage_logs | 计费流水，写入后不变 | 按月分区，保留 ≥ 3年 |

## E. Redis Key 设计

### E1. 统一命名规范

```
duanju:{env}:{category}:{key}
  ├─ env          = dev / staging / prod  (多环境不串数据)
  ├─ category     = 下列 7 大类之一
  └─ key          = 业务主键，用 : 分层
```

### E2. TTL 策略总览

| Category | 典型 TTL | 清理策略 |
|----------|----------|---------|
| session 会话 | 7~30 天 | 用户主动退出时 DEL + 自然过期 |
| cache 热点缓存 | 5 分钟 ~ 1 小时 | 写操作时主动 DEL 失效 |
| rate 限流计数 | 1 分钟 / 1 小时 / 1 天滑动窗口 | 滑动窗口 EXPIRE 自动过期 |
| lock 分布式锁 | 10 秒 ~ 5 分钟（必须有TTL防死锁） | 释放时 Lua 原子校验 value==owner 再 DEL |
| queue 任务队列 | 持久化(无TTL) | 消费 ACK 后 LPOP / ZREM |
| running 进行中集合 | 任务最长超时时间（如 2 小时） | Worker完成时 SREM / 定期扫描僵尸 |
| ws WebSocket频道 | 连接存活期内无TTL | 连接断开时退订 + Pub/Sub天然清理 |

## F. 数据一致性 7 大核心要点

### F1. 积分扣减：事务内写流水，强一致不超扣

```sql
-- 积分扣减必须在一个DB事务内完成3步
BEGIN;
  -- 1. 悲观锁锁定积分账户(防并发扣减)
  SELECT current_balance, frozen_balance FROM point_accounts
  WHERE owner_type='USER' AND owner_id=1001 FOR UPDATE;

  -- 2. 校验余额充足 (注意:扣减的是frozen_balance里的钱, 不是current_balance!)
  --    如果 frozen<cost 则抛错, 应用层返回"冻结积分不足"

  -- 3. 原子更新余额 + 写入流水(一条都不能少)
  UPDATE point_accounts SET
    frozen_balance = frozen_balance - 1200,        -- 从冻结余额扣
    lifetime_spent_total = lifetime_spent_total + 1200,
    last_txn_at = NOW()
  WHERE id = $acct_id AND frozen_balance >= 1200;   -- 再次校验防并发(SQL级)

  INSERT INTO point_transactions
    (account_id, owner_type, owner_id, txn_type, direction, amount,
     balance_after, frozen_after, related_generation_task_id,
     cross_episode_reuse_exempt_amount, description, idempotency_key)
  VALUES (
    $acct_id, 'USER', 1001, 'GEN_VIDEO_15S_SEEDANCE2_5_VIP', 'DEBIT', 1200,
    8800, 0, 55234,
    300, '第1集-叙事单元2-镜头3生成(跨集复用豁免300分)',
    'txn-unique-key-xxx'
  );
COMMIT;
```

**关键保证**：UPDATE 的 WHERE 条件二次校验 `frozen_balance >= cost`，即使应用层漏检查数据库层也不会负数。

### F2. 订阅/积分包发放：幂等 + 事务内发放

```sql
-- 支付回调处理订单 (必须幂等, 支付宝可能回调3次)
BEGIN;
  -- 1. 幂等检查: 先SELECT订单状态
  SELECT pay_status, idempotency_key FROM orders WHERE order_no='ORD2026081000001' FOR UPDATE;
  --    如果已经是 PAID → 直接返回成功(幂等), 不做后续发放

  -- 2. 标记订单为PAID (更新状态+乐观锁)
  UPDATE orders SET
    pay_status='PAID', paid_at=NOW(), pay_transaction_id='ALI-xxx123'
  WHERE order_no='ORD2026081000001' AND pay_status='PENDING';
  --    若影响行数=0 → 并发已处理, ROLLBACK并返回成功

  -- 3. 事务内发放积分 + 开通会员 (都在同一个事务!)
  INSERT INTO point_transactions (...) VALUES (...SUBSCRIPTION_MONTHLY CREDIT 50000...);
  UPDATE point_accounts SET current_balance = current_balance + 50000, ...;

  INSERT INTO user_memberships (user_id, package_id, ...) VALUES (...)
  ON CONFLICT (user_id) DO UPDATE SET   -- 续期场景
    current_period_end = current_period_end + INTERVAL '30 days', ...;

  -- 4. 首次购买加赠积分 (如果配置启用)
  IF is_first_purchase THEN
    INSERT INTO point_transactions (...) VALUES (...FIRST_PURCHASE_LIMITED_BONUS CREDIT 20000...);
    UPDATE point_accounts SET current_balance = current_balance + 20000;
  END IF;
COMMIT;
```

**关键保证**：订单状态 PENDING→PAID 是单语句原子 UPDATE，天然幂等；发积分和开通会员都在同一事务，绝不会出现"钱扣了但积分没到"。

### F3. 任务幂等：request_id + 唯一索引 + DB 先写再入队

```
[客户端POST /batch-generate]
    ↓ 客户端必须生成唯一 request_id (UUID+时间戳)
    ↓
[API 层]
  ① INSERT INTO generation_tasks (request_id, ...) VALUES ($req_id, ...)
     ON CONFLICT (request_id) DO NOTHING;  -- 唯一索引防重复
  ② 读取 task_id (新插入的 or 已存在的)
  ③ 写 Redis 分布式锁 lock:task:$req_id TTL=60s 防DB唯一索引失效极端情况
  ④ 任务 status=QUEUED → 入队 Redis ZSet（score=priority*10^12+now_ms，Lua 原子 SADD+ZREM 防并发重取，先落库后入队!）
  ⑤ 返回 task_uuid 给前端 (重复请求返回同一个uuid)
```

**反模式**：先入队再写DB → 如果DB写失败队列里多了个幽灵任务，消费时报错找不到。

---

### F4. 队列：落库再入队 + 消费前加锁防重复消费

```
[入队端] 严格 G3 流程：DB写SUCCESS → LPUSH queue
                ↓ 极端情况(入队时Redis挂了)
                定时任务: SCAN generation_tasks
                  WHERE status='QUEUED' AND created_at < NOW()-5min
                  → 补发入队 (至少一次投递)

[消费端 Worker]
  ① BRPOP queue 取到 task_id
  ② SETNX lock:task_consume:$task_id $worker_id EX 600 (加锁)
     获取失败 → 有其他Worker在处理, 跳过
  ③ DB UPDATE generation_tasks SET status='RUNNING', started_at=NOW()
     WHERE id=$task_id AND status='QUEUED';
     影响行数=0 → 已被人抢先, RELEASE锁 + 跳过
  ④ 执行 GPU 推理
  ⑤ 成功: UPDATE SUCCESS + point_cost_final 计算 + 扣冻结积分 (G1事务)
     失败: retry_count<3 → UPDATE QUEUED 重新入队; 否则 FAILED_DEAD 解冻积分
  ⑥ Lua脚本释放锁 (校验value是自己才能删)
```

**关键保证**：DB status 状态机 + Redis 消费锁 双重保险，同一任务绝对不会被两个 Worker 同时跑。

### F5. S3 对象生命周期：DB 记录与 S3/OSS 双向关联

```
[S3 上传]
  1. 预签名URL模式: POST /api/s3/presign 返回 upload_url + file_key
  2. 客户端直传 S3 成功 → 回调 API /s3/confirm(file_key, checksum)
  3. API 写 DB INSERT INTO generated_images(file_url=file_key, ...)
     同时写入 s3_object_metadata 表: {key, bucket, size, checksum_sha256, ref_count:1}

[S3 删除 (延迟策略)]
  - 软删作品/资产: 只 DB deleted_at 标记, S3 不删 (用户可恢复)
  - 永久删除/回收站30天清理:
      1. UPDATE s3_object_metadata SET ref_count = ref_count - 1
      2. IF ref_count == 0 AND deleted_at < NOW()-30d → 异步发送 S3 DELETE 队列
      3. Worker调用 S3 删除(幂等, 重复调用不报错)
      4. 最后 DB DELETE s3_object_metadata 物理删

[S3 生命周期规则 (对象侧兜底)]
  - /tmp/uploads/ 前缀: 30 天后自动删除 (用户传了但没confirm的)
  - /generated/intermediate/ 前缀: 7 天后自动归档到 Glacier (中间帧/抽锚图)
  - /user-data/{uid}/trash/ 前缀: 30 天后永久删除
```

### F6. 任务失败：解冻积分 + 标记豁免 + 通知用户

```
[Worker任务失败处理 (retry_count >= 3 FAILED_DEAD)]
  BEGIN;
    -- 1. 更新任务状态
    UPDATE generation_tasks SET
      status='FAILED_DEAD',
      error_code=$err,
      completed_at=NOW(),
      thawed_points = frozen_points      -- 失败时 冻结积分全部解冻
    WHERE id=$task_id AND status='RUNNING';

    -- 2. 解冻积分回退账户 (只有之前冻结了的才解冻)
    UPDATE point_accounts SET
      frozen_balance = frozen_balance - $thaw_amount,
      current_balance = current_balance + $thaw_amount
    WHERE id = $acct_id AND frozen_balance >= $thaw_amount;

    -- 3. 写一条解冻流水 (type=UNFREEZE_PARTIAL_FAIL)
    INSERT INTO point_transactions
      (..., txn_type='UNFREEZE_PARTIAL_FAIL', direction='UNFREEZE',
       amount=$thaw_amount, balance_after=..., frozen_after=...,
       description='任务失败解冻退回: 场景图批量4个失败3个, 退回900分')
    VALUES (...);

    -- 4. 对该批次下成功的子任务: 正常扣费 (解冻=0, 扣除成功部分)
    foreach(success_subtask):
      UPDATE point_accounts SET
        frozen_balance = frozen_balance - $subtask_cost;
        -- current_balance 不变, 因为已经冻结了
      INSERT point_transactions (...UNFREEZE_SUCCESS_DEDUCT DEBIT $subtask_cost...)

    -- 5. 发一条站内信通知
    INSERT INTO notifications (user_id, type, title, content) VALUES
      (1001, 'BILLING', '批量生成部分失败', '4个资产中1个成功扣300分, 3个失败退回900分');
  COMMIT;
```

### F7. 跨集资产复用：去重判定 + 豁免明细 + 弹窗透明

```
[批量生成前 API /assets/batch-generate]
  输入: project_id=1, episode_id=3, character_variant_ids=[12, 15, 18]
  判定流程:
  1. 开启事务
  2. 逐个资产ID查 asset_usage_logs (按 UNIQUE(asset_kind, asset_id, episode_id))
     → 如果已存在: point_cost_applied = 0 → 豁免, 前端灰显"已复用,免费"
     → 如果不存在:
        a) 查该 asset 在 全 project_id=1 范围内是否存在 asset_usage_logs
           i) 存在(其他集用过): is_first_project_wide=FALSE, cost_applied=0 → 跨集复用,免费
           ii) 不存在(全项目第一次): is_first_project_wide=TRUE, cost_applied=查模型定价表
  3. 汇总预览: gross_total=300, exempt_count=2, net_to_freeze=100
  4. 余额校验: current_balance >= net_to_freeze → 返回预览给用户确认
  5. 用户点"确认生成":
     a) 先冻积分: UPDATE point_accounts SET frozen+=100 current-=100 + INSERT FROZEN流水
     b) 写 asset_usage_logs (一次性, 利用UNIQUE防重复插入并发)
        INSERT INTO asset_usage_logs
          (asset_kind, asset_id, project_id, episode_id,
           is_first_time_use_project_wide, is_first_time_use_episode_wide,
           point_cost_applied, generation_task_id, user_notified)
        VALUES
          ('CHARACTER_VARIANT', 12, 1, 3, FALSE, TRUE, 0, $task_id, FALSE),  -- 跨集复用免费
          ('CHARACTER_VARIANT', 15, 1, 3, FALSE, TRUE, 0, $task_id, FALSE),  -- 复用豁免
          ('CHARACTER_VARIANT', 18, 1, 3, TRUE,  TRUE, 100, $task_id, FALSE); -- 首次扣费
     c) 入队生成任务 (G3)
     d) 返回结果时前端弹窗大字:
        "本次批量生成预览：总计 300分
         ✅ 跨集复用豁免 2 个 (-200分)
         💰 实际冻结 100分
         任务失败积分自动原路退回"
```

**反模式**：用户看到账单扣了 100分 但不知道为啥少了 → 必须在批量预览弹窗和积分流水中都透明化展示 `cross_episode_reuse_exempt_amount` 字段，用户点进去能展开看是哪 3 个资产复用了、分别是第几集用的。
