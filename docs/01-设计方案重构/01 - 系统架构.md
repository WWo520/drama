# 短剧平台系统架构（Go 1.22 + Gin + PostgreSQL 16 + Redis 自写调度）

## 〇、一眼看懂：技术栈与整体架构

### 技术栈总表

| 层 | 技术选型 | 用途说明 |
|----|---------|---------|
| 后端语言/框架 | **Go 1.22 + Gin**（模块化单体） | API + Worker 同代码库；2026 年底前不拆微服务 |
| 数据库 | **PostgreSQL 16**（JSONB + pgvector + 原生 ENUM） | 全量业务表真源见 02；迁移工具开发启动时四选一 |
| 缓存/队列 | **Redis 7** | ZSET 优先级任务队列 + Lua 原子取任务 + 分布式锁续租 + 令牌桶限流 + JWT Refresh 黑名单 |
| 对象存储 | **S3 兼容**（本地 MinIO / 线上阿里云 OSS） | 预签名 URL 前端直传，后端不碰文件带宽 |
| 任务调度 | **自写调度器**（约 800 行 Go） | 优先级队列/心跳续租/指数退避重试/死信；4 类 Worker 进程（Split/Asset/Video/Export） |
| AI 模型调用 | engine/model **多厂商路由** | Seedance/Kling/LuxBanana/LuxChat 等；单 Key 并发控制、429 自动切 Key 兜底 |
| 用户端前端 | **Vite + React 18 + TypeScript + Tailwind + Radix UI 自建组件** | 自由画布用 React Flow；数据层 TanStack Query + Zustand |
| 管理端前端 | **Vite + React + AntD 5 + ProComponents** | ProLayout + ProTable + RBAC 菜单过滤 |
| 实时推送 | **WebSocket 主通道 + HTTP 3s 轮询兜底** | Redis Pub/Sub 跨节点分发，断连自动降级 |
| 认证鉴权 | **JWT 双 Token** | Access 2h 存内存 + Refresh 7d HttpOnly Cookie + Redis 黑名单登出失效 |
| 支付 | **支付宝当面付** | 扫码下单 + 异步回调 7 步验签 + 订单号幂等 |
| 可观测性 | **Zap 结构化日志 + Sentry + Prometheus/Grafana** | Jaeger 链路追踪留 V2 |
| 部署 | **Docker Compose 起步 → V2 K8s + Helm + ArgoCD GitOps** | GPU Worker 按队列长度 HPA 扩缩容 |

### 整体架构一句话

L1 客户端（用户端 SPA / 管理端 SPA / OpenAPI）→ L2 CDN/Nginx → L3 Gin 网关中间件（鉴权/限流/日志）→ **L4 Go 模块化单体**（Router/Middleware/Domain/Engine/Repository 四层，10 大业务模块 + 8 大引擎）+ **L4B 4 类 Worker 进程** → L5 PostgreSQL / Redis / S3 → L6 可观测性基础设施。
所有 AI 生成任务 100% 异步：提交即返回 202 入队 → Worker 消费执行 → WS 实时推进度，失败自动重试/退积分。

| 维度 | 目标值 | 设计原则 |

**分层调用铁律**：

| 层 | 职责 | 铁律 |
|----|------|------|
| Router | URL → handler 映射 | 不含任何业务逻辑 |
| Middleware | 鉴权/限流/日志/恢复/TraceID | 业务无关的横切关注点 |
| Domain（handler/service/dto 三文件） | 90% 业务逻辑在 service | 跨模块调用只能走 Engine 层；禁止直接 import 其他 domain |
| Engine | 跨模块公共能力（≥2 个模块使用即抽出） | 只暴露 interface；禁止 import domain 层 |
| Repository | CRUD + 原生 SQL | 不含业务判断；一个表只能被一个 repository 文件操作 |
| Pkg | 纯工具包 | 绝对不能 import internal 下其他包 |

- 依赖注入用 **Google Wire**（`wire.Build` 代码生成），禁止全局单例（`var GlobalDB *gorm.DB`）。
- migrations/ 设计阶段不固化：Schema 真源 = 02 数据模型 C 章；铁律「合入 master 的迁移脚本绝不回头修改，改表必须新建下一个独立迁移文件」。

### B.3 四类 Worker 角色

4 个独立进程（同代码库同镜像，`-role` 参数区分），好处：独立扩缩容（GPU/CPU 分开）、故障隔离、并发数独立调优。

| Worker角色 | 进程名 | 任务类型 | 节点类型 | 并发数建议 |
|-----------|--------|--------------------------|---------|----------|
| **Worker-Split** | `worker -role=split` | SCRIPT_SPLIT剧本拆分、STORYBOARD_PLAN分镜规划、PROMPT_REFINEMENT提示词润色 | CPU节点即可，调用LLM API | 单机4并发 |
| **Worker-Asset** | `worker -role=asset` | CHAR_IMAGE_GEN角色图、SCENE_IMAGE_GEN场景图、PROP_IMAGE_GEN道具图、SMART_SHOT_GROUP_PRE_ANCHOR智能镜头预演抽锚 | GPU节点（8G显存+） | 单GPU 2并发（信号量硬控防OOM） |
| **Worker-Video** | `worker -role=video` | VIDEO_SEGMENT_GEN单镜头视频、VIDEO_GROUP_CONCAT镜头块拼接、FINAL_VIDEO_COMPOSE整片合成、3DGS_RENDER_*实时渲染 | GPU大显存节点（A100 80G优先） | 单A100 4并发 |
| **Worker-Export** | `worker -role=export` | ENGINEER_FILE_EXPORT工程文件导出、PNG_FRAMES抽帧、SRT_SUBTITLE字幕、FCPXML_PREMIERE工程 | CPU节点，FFmpeg密集型 | 单机8并发 |

各角色工作流程要点：取任务 → 读 task_params_json → 调 model/asset 引擎 → 结果上传 S3 并回写业务表 → billing 引擎成功扣费/失败解冻 → 更新 generation_tasks 状态 → PUBLISH Redis 通知 API 节点推 WS。导出文件 S3 生命周期 30 天自动清理，前端用 24h 预签名 URL 下载。

#### B.3.1 调度器自写设计要点（拒绝黑盒，全链路100%可控）

不选 Celery/Asynq 等现成库的原因：计费核心链路 + 状态机 + 续租 + 死信逻辑现成库要么做不了要么黑盒，自写约 800 行全可控。4 个核心机制：

1. **优先级队列**：Redis ZSET，`priority*1e9 + timestamp` 做 score。priority=0 免费用户、5 普通、7 Advanced、8 Premium/Ultimate；API 侧入队前查 user_memberships 提权，同优先级按 FIFO。
2. **取任务原子性**：不能 ZPOPMIN 之后再 SETNX（两步非原子=极端情况下两个 Worker 拿到同一个任务）。必须把「ZPOPMIN 弹出 → SETNX 加锁（失败则 ZADD 弹回队列）→ EXPIRE 锁 60 秒」封装为一个 Redis Lua 脚本原子执行。脚本参数为 worker_id（UUID），保证要么全成功要么全回滚。
3. **心跳续租**：Worker 每 30 秒 `EXPIRE worker_lock:{task_id} 60` 续租；进程崩溃则 60 秒后锁过期，回收 cron（每分钟）扫描 RUNNING 但无锁的任务弹回队列。**任务永不丢失**是底线。
4. **指数退避重试**：失败依次延迟 15s/60s/180s 重入队，≥3 次转 FAILED_DEAD 死信并全额解冻退积分；管理端「算力任务监控」提供一键重跑。

#### C.2.1 BillingEngine 三阶段扣费的原子性保证

三阶段（冻结→扣费/解冻）必须 100% 原子，任何一步失败完整回滚，不允许「钱扣了任务没发 / 任务发了钱没扣」的中间状态：

- **阶段1 PUBLISH_PRE 冻结（API 侧）**：同一 DB 事务内 SELECT FOR UPDATE 行锁 point_accounts → 校验余额（不足→回滚返回积分不足）→ UPDATE 双余额（current−=总额、frozen+=总额）→ INSERT FROZEN 流水（带 balance_after 快照）→ COMMIT。
- **阶段2 EXECUTE_DONE 扣费（Worker 侧成功）**：frozen 减去实际扣费（预期成本−跨集复用豁免额）→ INSERT DEBIT 流水（记豁免金额）→ INSERT asset_usage_logs（ON CONFLICT DO NOTHING 防重）→ COMMIT。
- **阶段3 PARTIAL_FAIL 解冻（Worker 侧失败）**：预期成本全额退回 current → INSERT UNFREEZE 流水 → COMMIT。失败必全额退回，永不倒扣。

#### C.2.2 ModelEngine 多厂商路由（429 限流与兜底降级）

配置表 platform_model_keys：vendor / model_name / api_key（AES 加密存 DB）/ concurrency_limit（单 Key 并发上限）/ priority（越小越先）/ monthly_quota（月度额度）。

路由逻辑：①按 priority 取适配 Key；②逐 Key 信号量并发控制；③成功记录实际 Vendor/Key 供成本核算；④429/5xx 厂商侧错误自动切下一个 Key，4xx 用户侧错误（如 prompt 违规）直接报错不切；⑤全部失败返回「模型全部维护中」友好错误。效果：背后多厂商 Key 轮换故障时用户无感。

## E. ADR 架构决策记录（7 项关键选型）

| 编号 | 决策主题 | 最终选型 | 一句话理由 |
|------|---------|---------|-----------|
| ADR-01 | 后端语言 | **Go 1.22 + Gin**（弃 Python FastAPI） | 团队基础 + Goroutine 高并发 + 单二进制极简部署 + 编译期类型安全（计费零容忍）；模型经 HTTP 调用，不混写 Python |
| ADR-02 | 任务调度 | **Redis 自写调度器**（弃 Celery） | 计费链路要求全链路透明可控；约 800 行实现优先级/续租/退避/死信，减少一个 Python 运维面 |
| ADR-03 | 前端架构 | **Vite + React18 SPA**（弃 Next.js SSR） | 自由画布 React Flow 纯客户端渲染最优；部署纯静态无 Node 运维；SEO 痛点留 M2 用 prerender.io 解决 |
| ADR-04 | 资源归属模型 | **Space 空间贯穿全局**（弃扁平 user_id） | 团队定价与双轨计费基石；owner_type+owner_id 复合索引 M0 建好，M1 加团队零迁移 |
| ADR-05 | MVP 范围 | **M0 核心 21 组表**（全量 58 表分阶段建） | 先跑通端到端验证付费意愿；防 scope 膨胀，不达标不准开 M1 |
| ADR-06 | 进度推送 | **WebSocket + 轮询双通道**（弃纯轮询） | 实时体验 + 弱网断连自动降级；Redis Pub/Sub 跨节点分发 |
| ADR-07 | 数据库枚举 | **PostgreSQL 原生 ENUM TYPE**（弃 VARCHAR+CHECK） | 类型安全 + 省存储 + 业务枚举只加不改；迁移脚本先 CREATE TYPE 再建表 |

### F.1 安全

| 安全项 | 实施细则 | 落地阶段 |
