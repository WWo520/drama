# 短剧平台后端方案（Go 1.22 + Gin + pgx + Redis 自写调度版 · 全量设计阶段稿）

> 本文是后端**工程实现方案的唯一真源**。枚举真源 → 02 B 章 `CREATE TYPE`（代码由 go:generate 自动生成常量，禁止手写 iota）；接口契约真源 → 05 OpenAPI（handler/dto 从 YAML 生成，禁止手写字段）；表结构真源 → 02 数据模型（模型 tag 严格对齐，unique 索引必须 DB 层建）；排期/里程碑 → [09 - 分期路标.md](./09%20-%20分期路标.md)。扣费一致性（frozen→spent→unfreeze）真源 = 02 号 generation_tasks 三字段 + point_transactions，实现规则见 H 章。

## 〇、一眼看懂：技术栈与整体架构

| 层 | 选型 |
|------|------|
| 语言/框架 | Go 1.22+ · Gin v1.10 |
| 数据访问 | pgx/v5 手写 Repository（不用 ORM） |
| 存储 | PostgreSQL 16 · Redis 7 · MinIO/OSS（S3 协议） |
| 任务调度 | Redis ZSet + Lua 自写调度引擎（4 类 Worker：Split/Asset/Video/Export） |
| 实时推送 | WebSocket Hub（gorilla/websocket）+ SSE 流式 |
| 视频合成 | FFmpeg（concat/overlay/amerge 流水线） |
| 智能体记忆 | pgvector（RAG，按 project_id 隔离） |
| 鉴权 | JWT 双 Token（Access 2h + Refresh 7d HttpOnly Cookie） |
| 支付 | 支付宝当面付（回调 7 步验签） |
| 可观测 | zap 日志 · Prometheus /metrics · Sentry |

**整体架构一句话**：模块化单体 Monolith —— Gin 接入 → 三层权限中间件（用户/平台/空间）→ Domain 领域服务（第一行必调权限校验）→ 积分事务 + 任务入队 → 4 类 Worker 消费执行；Engine 引擎层（调度/模型治理/S3/计费/通知/智能体/视频/审核）提供公共能力；数据落 PG + Redis，文件走 MinIO，进度经 WS Hub 实时推送。

| 关键机制 | 位置 |
|---------|------|
| 认证鉴权（JWT 双 Token + 3 层中间件） | C 章 |
| 任务调度引擎（队列/状态机/重试/并发/超时） | D 章 |
| 模型接入治理（厂商→模型→Key 三级） | E 章 + 附录 C |

| FFmpeg 成片合成 | L 章 |
| WS 9 消息协议 | M 章 |
| 厂商适配坑点清单（⭐ 开发前必看） | 附录 C |

## 二、迁移工具不固化（设计阶段声明）

设计阶段**不指定任何数据库迁移工具**（开发首日由后端团队在 golang-migrate / goose / sqlc / Atlas 四选一），也不固化迁移编号格式与执行方式；仅提供建表依赖顺序参考（02 号 E 章）。02 号中所有 CREATE TYPE/TABLE/INDEX SQL 是 **Schema 结构说明**而非可运行迁移脚本，字段/类型/约束必须 100% 对齐不得修改。

## A. 技术栈与依赖表（选型理由 + 版本 + 与旧参考实现对照）

### A.1 核心依赖库总览

|------|----------------|---------|----------------------|---------|
| **语言** | Go 1.22+ | 原生高并发 goroutine+channel，部署单二进制无运行时依赖，内存占用仅旧脚本语言实现的 1/5~1/10 | 旧方案脚本语言 3.12 | 用 Go 自写任务调度 Worker，避免旧方案的 GIL 瓶颈；goroutine 池比进程池轻量 10x |

| **数据库迁移** | 开发启动时四选一（golang-migrate / goose / sqlc / Atlas） | 设计阶段不提前固化，见第二章说明；无论选哪种，迁移 SQL 严格对齐 02 数据模型 Schema，UNIQUE/PARTIAL 索引一条不能少 | 旧方案自动生成迁移工具 | 放弃自动生成迁移（旧方案工具自动生成常漏索引），手写 SQL 严格对齐 02 号 Schema，禁止工具自动生成后直接提交 |

### B.2 分层原则（铁律：禁止跨层反向调用）

```
HTTP 请求流：
  ┌─────────┐    ┌──────────────┐    ┌──────────────┐    ┌────────────────────┐
  │  Gin    │───▶│ Middleware   │───▶│ Router       │───▶│ Domain.*.Handler   │
  │ Router  │    │ L1/L2/L3     │    │ 分组注册      │    │ 参数绑定+校验+响应  │
  └─────────┘    └──────────────┘    └──────────────┘    └─────────┬──────────┘
                                                                     ▼
  ┌────────────────────────────────────────────────────────────────────────────┐
  │  Domain.*.Service     业务逻辑层（所有权限校验第一行必调）                  │
  │  ├─> space.CheckSpacePermission(spaceID, userID, action)                   │
  │  ├─> engine/billing 积分事务扣减                                            │
  │  ├─> engine/task 提交任务入队                                               │
  │  └─> 其他业务组合逻辑                                                       │
  └────────────┬───────────────────────────┬───────────────────────────────────┘
               ▼                           ▼
  ┌──────────────────────┐     ┌────────────────────────────────┐
  │ Repository 数据访问层 │     │ Engine 公共能力引擎层            │
  │  ├─> pgx CRUD SQL     │     │  ├─> task    任务调度            │
  │  ├─> Redis 缓存读写    │     │  ├─> model   模型接入治理        │
  │  └─> 事务 Tx 封装      │     │  ├─> asset   S3 存储             │
  └──────────────────────┘     │  ├─> billing 积分计费底层       │
                                │  ├─> notify  消息通知/WS Hub    │
                                │  ├─> agent   智能体引擎          │
                                │  ├─> video   FFmpeg 合成        │
                                │  └─> audit   审核流水           │
                                └────────────────────────────────┘
```

> **分层铁律**：
> 1. Handler 层绝不写 SQL，只调用 Domain.Service；绝不出现 pgxpool
> 2. Domain.Service 写业务组合，不写具体 SQL，CRUD 走 Repository；调用 Engine 层公共能力
> 3. Engine 是公共库，被多个 Domain 调用；Engine 绝不反向依赖 Domain，只依赖 Repository/pkg
> 4. Repository 只做单表/联表 SQL，不含业务判断（业务判断放 Domain）
> 5. 所有跨资源操作（扣积分+写任务+写流水）必须走 DB 事务，严禁拆分多个接口

## C. 认证鉴权：JWT 双 Token + 3 层中间件

### C.1 JWT 双 Token 方案设计

| Token 类型 | 存储方式 | 有效期 | 内容 Claims | 刷新策略 |
|-----------|---------|-------|------------|---------|
| Access Token | 前端内存（localStorage 或 Redux） | 2 小时（7200s） | `sub`=user_uuid, `space_id`=当前空间, `platform_role`=user/admin, `vip_level`=0~4, `exp`=绝对时间戳 | 返回 1002 时前端自动 POST /auth/refresh 换新 |
| Refresh Token | HttpOnly Cookie（Secure; SameSite=Lax; Path=/api/v1/auth） | 7 天（604800s） | `sub`=user_uuid, `token_version`=防踢下线版本号, `exp` | refresh 时验证后轮换（发放新 refresh_token），旧 token 立即加 Redis 黑名单 |

### C.2 3 层中间件调用顺序（Gin HandlerChain）

```
请求到达
  │
  ▼
M0: RequestID 注入（写 ctx，打印日志必带）─── 零失败
  │
  ▼
M1: Zap Access Logger（method/path/status/耗时/bytes）+ Recovery（panic→500+Sentry）
  │
  ▼
M2: CORS 预检 / RateLimiter 限流（Redis 滑动窗口）/ Idempotency 幂等缓存
  │
  ▼
M3: UserAuth 中间件 ─────────────────────────── L1 用户认证
  │  ├─> 白名单路径（/auth/register, /auth/login, /auth/refresh, /payments/webhook/*）直接放行
  │  ├─> 解析 Authorization: Bearer <access_token>
  │  ├─> 检查 Redis JWT 黑名单（登出/踢下线）
  │  └─> 通过：解析 claims → 把 user_uuid / space_id / vip_level 写入 gin.Context
  │      失败：code=1002 "登录状态已过期，请重新登录"
  │
  ▼
M4: PlatformRBAC 中间件 ───────────────────── L2 平台权限
  │  ├─> 路由前缀匹配：/api/admin/* 要求 claims.platform_role == "admin"
  │  ├─> 普通 /api/v1/* 路由跳过此层
  │  └─> 失败：code=1005 "平台权限不足，仅管理员可访问"
  │
  ▼
M5: SpacePermission 中间件 ─────────────────── L3 空间角色权限
     ├─> 解析 path 中 space_id / project_id → 反查 projects.owner_space_id
     ├─> 解析 query/header 中 X-Space-ID（用户切换空间）
     ├─> 调用 spaceSvc.CheckSpacePermission(spaceID, userID, action)
     └─> 失败：code=2003 "无权访问该空间资源"

  ┌─> 到达 Domain.Handler，第一行再次显式调用 CheckSpacePermission 做双保险
```

### C.3 统一权限校验入口 CheckSpacePermission（契约级签名）

**契约签名**：`CheckSpacePermission(ctx context.Context, spaceID int64, userID int64, action SpaceAction) error`，位于 `internal/domain/space/permission.go`。返回 err=nil 即通过；否则返回带错误码业务错误（2001 不存在或无权 / 2003 无权 / 9500 未知权限类型）。

**操作枚举 SpaceAction（纯应用层权限动作 Go const，不入库，不在 02 枚举真源范围）× 允许角色**：

| Action | 含义 | 允许角色 |
|--------|------|---------|
| view | 只读 | owner/admin/member/viewer |
| edit | 编辑 | owner/admin/member |
| generate | 发起生成任务 | owner/admin/member |
| manage | 成员管理 | owner/admin |
| delete | 删除项目/空间 | owner |
| billing | 账单/充值查看 | owner/admin/billing_only |

**铁律**：所有 Domain 层资源操作函数第一行必调此函数（与 M5 中间件双保险）；校验失败统一返 2003，不泄露资源存在性。

### C.4 JWT 签发 + Refresh Cookie 要点

- 算法 HS256；Access/Refresh 使用**两把独立 secret**
- Access Claims：`sub`(user_uuid) / `space_id` / `platform_role` / `vip_level` / `token_ver` / `exp`；Issuer=duanju-api，每 token 带唯一 jti
- Refresh Claims：仅 `sub` + `token_ver`（版本号防踢下线）
- Cookie 属性：`Path=/api/v1/auth`（只在 auth 接口发送，防 CSRF）· Secure（生产必开）· HttpOnly · SameSite=Lax · 7 天过期
- refresh 轮换：验证通过后发放新 refresh_token，旧的立即加 Redis 黑名单

## D. 任务调度引擎（重点·Go 自写替换旧方案分布式队列）

### D.1 4 类 Worker 角色定义（对齐 08 号 B3 Worker + F 微服务路标）

| Worker 角色 | Go 结构体 | 处理 task_type 范围 | GPU 需求 | 并发上限（单实例） |
|------------|----------|-------------------|---------|------------------|
| **SplitWorker** | `type SplitWorker struct` | SCRIPT_SPLIT, STORYBOARD_PLAN_V1_LUXCHAT, PROMPT_REFINEMENT_LUXGEM | GPU(A10) LLM 推理 | 16 并发 goroutine |
| **AssetWorker** | `type AssetWorker struct` | CHAR_IMAGE_GEN, SCENE_IMAGE_GEN, PROP_IMAGE_GEN, 3DGS_RENDER_IMAGE/PANORAMA | GPU 图生 | 8 并发（显存占用大） |
| **VideoWorker** | `type VideoWorker struct` | SMART_SHOT_GROUP_PRE_ANCHOR, VIDEO_SEGMENT_GEN, VIDEO_GROUP_CONCAT, 3DGS_SCENE_BUILD | 大显存 GPU(A100 80G 优先) | 4 并发 |

> **M0 部署方式**：4 类 Worker 全部编译进同一个二进制，`cmd/server/main.go` 启动时通过 flag `-workers=split,asset,video,export` 控制启用哪些 Worker。单机部署全部启用，后期可拆成独立 Deployment（F 路标），代码零改动。

### D.2 Redis 数据结构设计（ZSet 队列 + Running 集合 + 分布式锁）

| Redis Key | 类型 | 结构/Score 设计 | 用途 |
|-----------|------|----------------|------|
| `task:queue:split` / `asset` / `video` / `export` | ZSet | `score = priority*10^12 + unix_timestamp_ms`（例：VIP7 优先级=7 → score=70001760000000000） | 按优先级+FIFO 弹出。VIP 用户 priority 自动提权 6~7，免费用户 0~3 |
| `task:running` | Set | member = task_id | 正在执行的任务 ID 集合；用于并发计数、调度器轮询不重复取 |
| `task:lock:{task_id}` | String（SETNX） | value = gocron-node-id:{pid}:{goroutine-id}; EX=30s | 单任务执行幂等锁；守护协程每 10s 续约（EX 重置 30s），panic 未续约自动释放 |
| `task:concurrency:global` / `space:{id}` / `user:{id}` | String（INCR/DECR） | value = 当前运行任务数 | 三级并发计数器。提交任务先 CAS 检查不超上限，成功才 INCR。Worker 完成后 DECR |
| `task:progress:{task_id}` | Hash | 字段 pct / msg / elapsed_ms / node_id | 进度缓存，WS 推送读这里，不读 DB 降低 IO |
| `task:throttle:{task_id}` | String（SETNX+EX） | EX=250ms | 同任务 ID 进度消息节流 250ms，只让一条通过，其余丢弃 |

### D.3 队列弹出原子操作（Lua 脚本行为契约）

`internal/engine/task/pop_queue.lua`：ZSet 原子 POP，防并发重取。

| 项 | 契约 |
|----|------|
| 输入 | KEYS：队列 ZSet（如 task:queue:video）+ Running Set；ARGV：最大 score 截止时间戳（一般 = now_ms） |
| 取数 | ZRANGEBYSCORE 取最高优先级最多 5 条（批量弹出减少 RTT） |
| 抢占 | 逐条 SADD Running Set：返回 1（抢占成功）才 ZREM 移出队列；返回 0（已被他人取走）直接跳过——两步原子，防并发重取 |
| 输出 | JSON 数组 [{task_id, score}]，空则 [] |

**Go 封装**：`redis.NewScript` 加载本脚本，`Queue.PopBatch(ctx, queueKey, maxScore)` 批量原子弹出，解析 JSON 数组返回 `[]poppedTask{TaskID, Score}`。

### D.4 状态机定义（合法转移矩阵）

**任务状态（TaskStatus，枚举真源 → 02 号 CREATE TYPE task_status）**：

| 状态 | 含义 |
|------|------|
| PENDING | 预创建（未入队） |
| QUEUED | 已入 Redis ZSet（提交成功） |
| RUNNING | Worker 已取到执行中 |
| SUCCESS | 成功（扣积分） |
| FAILED_RETRYING | 失败待自动重试（retry_count<3） |
| FAILED_DEAD | 死信（重试≥3 次） |
| CANCELED_USER | 用户手动取消 |
| CANCELED_TIMEOUT | 超时回收（终态） |
| SKIPPED | 跨集复用跳过（M0 不用） |
| PAUSED_USER | 用户暂停（M1 加） |

**合法转移（map[from][]to，非法转移直接拒绝）**：

| from | 允许的 to |
|------|----------|
| PENDING | QUEUED / CANCELED_USER |
| QUEUED | RUNNING / CANCELED_USER / CANCELED_TIMEOUT |
| RUNNING | SUCCESS / FAILED_RETRYING / FAILED_DEAD / CANCELED_USER / CANCELED_TIMEOUT |
| FAILED_RETRYING | QUEUED / FAILED_DEAD |
| CANCELED_TIMEOUT | （终态） |

### D.5 失败重试策略（指数退避 max 3 次）

| 第几次重试 | backoff_seconds | 触发条件 |
|----------|----------------|---------|
| 第 1 次（retry_count=0→1） | 15s | 网络 5xx / 模型超时 MODEL_TIMEOUT / VRAM 溢出 |
| 第 2 次（1→2） | 60s | 同上 + 第一次重试仍失败 |
| 第 3 次（2→3） | 180s | 同上 |
| ≥3 次 | — | 转 FAILED_DEAD，写死信表，发告警，积分全额退回 |

入队时 score = priority*10^12 + (now_ms + backoff_seconds*1000)，这样 ZRANGEBYSCORE 时间没到不会取出，天然支持延迟重试。

### D.6 三级并发控制（全局/空间/用户）— 提交任务前校验

**额度配置**：全局默认 100（单机 4 类 Worker 总和）· 空间默认 20 · 用户默认 3（M0 免费用户）；VIP 1~4 级提权至 5/8/15/20。

**申请流程（TryAcquire）**：按「用户→空间→全局」顺序逐级 CAS（Redis WATCH+MULTI 原子 INCR），任一超限立即回滚已加的计数并返回失败；成功后返回 releaseFunc（任务完成时 DECR 三个 key）。三个计数 key 均带 24h 过期防泄漏。

### D.7 超时回收守护协程（timeout_reaper.go）

每 60s 扫描 generation_tasks：`status IN ('RUNNING','QUEUED') AND updated_at < NOW() - 阈值`（阈值按 task_type：split 5min / asset 20min / video 30min / export 15min）。命中后依次：① status 置 CANCELED_TIMEOUT → ② 从 task:running Set SREM → ③ 调 engine/billing 解冻积分 → ④ 写 generation_task_retry_logs（reason="TIMEOUT_REAPER"）→ ⑤ WS 推 TASK_CANCELLED。

## E. 模型接入与调度治理（厂商→模型→Key 3 级管理）

### E.1 3 级管理表（model_providers / models / model_keys）驱动

表结构真源 → 02 数据模型（此处仅列设计要点，字段不得与 02 冲突）：

### E.2 ModelProvider 统一接口（Submit/Cancel/Progress）

**契约接口**（`internal/engine/model/provider.go`，每个厂商一个 Adapter 实现）：

| 方法 | 职责 |
|------|------|
| ProviderName() string | 返回厂商标识（'LUXCHAT'/'SEEDANCE' 等） |
| Submit(ctx, *GenRequest) (*TaskHandle, *GenResult, error) | 提交生成任务（同步/异步取决于厂商），返回 handle 供取消/查询 |
| Cancel(ctx, *TaskHandle) error | 取消运行中任务（用户点取消时） |
| Progress(ctx, *TaskHandle) (pct, msg, done, err) | 轮询厂商侧进度（不支持回调的厂商用） |

**GenRequest 要素**：TaskID · ModelCode · AbilityType · Prompt/NegativeProm · Params(seed/steps/cfg/resolution/duration) · RefImages[](AssetID/ImageURL/Weight 0.1~1.5) · OnProgress 回调(0~100)。

**GenResult 要素**：Success · OutputURL(S3) · Thumbnails(视频封面 3~6 张) · 宽高/时长 · Metadata(ai_model_actual_used/seed)。

### E.3 Key 加密存储（AES-256-GCM）+ 脱敏展示 + 轮换

- 主密钥 32 字节，从环境变量 AES_MASTER_KEY 读（viper）；非 32 字节启动直接报错
- Encrypt：随机 nonce + GCM Seal → base64 存 key_value_cipher；Decrypt 反解（nonce 前置于密文）
- 脱敏展示 MaskKey：前 6 + **** + 后 4；≤10 字符只显示 ****
- 轮换：key_rotator 每月自动换新 Key，写 last_rotated_at + 审计 MODEL_KEY_ROTATE

### E.4 Key 路由 + 负载均衡 + 429 切换 + 熔断

`Router.SelectKey(ctx, modelCode)` 选 Key 策略：status=正常 → 剩余 RPM% 最大 → priority 最高 → fail_count 最低。流程：① 缓存拿 model_code→model_id → ② 查 model_keys status=1 候选 → ③ 逐个查 Redis "rpm:key:{id}" 令牌桶剩余 → ④ 遇 429 临时移除（缓存标 0，5min 后恢复）→ ⑤ fail_count≥5 写 DB status=0 熔断 + Sentry 告警 → ⑥ 返回 releaseFunc（调用完归还 RPM 令牌）。

## H. 计费与订单（核心计费闭环）

### H.1 下单幂等键防重复（CreateOrder 流程）

`OrderService.CreateOrder(ctx, userID, req)` 流程：

1. **幂等查重**：同一 user_id + package_code 若已有 PENDING 订单未满 5 分钟 → 直接返回旧订单（code=8002）
2. **档位校验**：package_code 不在积分包档位常量表 → 返 8001
3. **写 orders**：order_no = P + yyyyMMddHHmmss + NanoID 6 位；points_granted_total = 档位积分 + 首购加赠；pay_status=PENDING；30 分钟过期；带 idempotency_key（唯一索引防并发双写）
4. **调支付宝当面付**创建二维码；失败返 9001
5. **返回**：order_no / QRCodeURL / 过期时间 / 金额

### H.2 支付宝当面付回调 7 步验签流程

`HandleWebhook`（POST /payments/webhook/alipay）严格按 1→7 顺序执行，任何一步失败返回字符串 `"fail"`（支付宝会重试）：

| 步 | 检查/动作 | 失败处理 |
|----|---------|---------|
| 1 | 验签：支付宝 RSA2 公钥校验 sign 字段 | 写审计 ALIPAY_VERIFY_FAILED（含 client_ip/form）→ fail |
| 2 | 核心字段校验：timestamp 防重放 · nonce+trade_no Redis SETNX 24h 防重复回调（已处理过直接 success）· sign_type=RSA2 · app_id=本商户（防串商户）· out_trade_no=order_no · total_amount 精确到分比对 | fail / 幂等返 success |
| 3 | 订单幂等：查 orders，已 PAID → 直接 success；非 PENDING → fail；金额转分比对防浮点误差 | fail |
| 4 | DB 事务内：orders 置 PAID + paid_at + trade_no | 事务失败→fail 让支付宝重试 |
| 5 | 事务内：point_accounts.current_balance += points_granted_total | 同上 |
| 6 | 事务内：写 point_transactions（CREDIT + PURCHASE_POINTS_PACKAGE，带 txn_uuid/balance_after/关联订单） | 同上 |
| 7 | 用户 WS 在线则推 POINTS_BALANCE_CHANGED（新余额/增量/原因） | — |

最后必须返回纯字符串 `"success"`，否则支付宝 24h 内反复回调。

### H.3 生成任务积分扣减事务（SELECT FOR UPDATE）

**铁律：扣积分必须在同一 DB 事务内，顺序固定**：

1. `SELECT ... FOR UPDATE` 行锁查积分账户（禁幻读/并发双扣）；frozen_balance < 应扣 → 返 4000
2. UPDATE：frozen_balance -= cost，lifetime_spent_total += cost（冻结→扣减，余额不变，冻结的钱本就从余额划出）
3. 写 billing_records（task_id/space_id/cost_points/cost_breakdown/status=DEDUCTED）
4. 写 point_transactions（FROZEN→DEBIT，带 txn_uuid、balance_after、frozen_after、关联 task_id）

**失败解冻策略（UnfreezeOnTaskFail）**：

| 失败原因 | 处理 |
|---------|------|
| USER_CANCEL（用户主动取消） | 不退（占了算力排队时间），冻结清零计收入，流水 FROZEN→DEBIT |
| CONTENT_VIOLATION / NSFW_BLOCKED（违规） | 不退，同上 |
| 其他（超时/模型失败/网络） | 全额退还 frozen→balance，流水 FROZEN→UNFREEZE |

### H.4 套餐订阅到期 + 续期（gocron 定时任务）

每小时扫描 user_memberships：`status='ACTIVE' AND current_period_end < NOW() AND renew_strategy='AUTO_RENEW_CONTINUOUS'` → 调支付宝代扣接口 → 续期 current_period_end + 30 天 → 月积分 monthly_points_grant_balance 重置；代扣失败 → cancel_at_period_end=true + 邮件提醒。

## M. WebSocket 服务（Hub 单例 + 9 消息协议 + 节流 + 心跳）

### M.1 Hub 单例结构（每个连接带 user_id + 订阅主题）

**订阅主题 4 类**：`task:{task_id}` · `points:{user_id}` · `notify:{user_id}` · `sys:broadcast` 全站广播。

**结构设计**：
- Client：ConnID / UserID / Send 下行发送缓冲 chan / Subscribed 已订阅 topic 集合
- Hub：clients 在线连接集 · register/unregister/broadcast 三个 channel · topicIndex（topic → clients 索引，RWMutex 保护）

**关键机制**：
- Run() 主事件循环单 goroutine 处理注册/注销/广播；注销时从所有 topic 反注册并 close(Send)
- 发送用 `select + default`：**Send 缓冲满直接踢下线**，防慢消费者造成 goroutine 泄漏
- Subscribe / PublishToTopic（按索引定向推）/ PublishToUser（多端在线逐连接推）

### M.2 9 种下行消息协议（W1~W9，字段真源 → 05 接口文档 WS 章节）

| 编号 | type | 用途 | 关键 Payload 字段 |
|------|------|------|----------------|
| W1 | WELCOME | 连接确认（第 1 条必发） | server_ts_iso / assigned_conn_id / heartbeat_sec=25 / timeout_sec |
| W2 | PONG | 心跳应答 | — |
| W2.5 | ERROR | 错误通知 | code / message |
| W3 | TASK_PROGRESS | 进度更新（最频繁） | task_uuid / status / progress_pct / stage_message / elapsed_ms / eta_ms / gpu_node_id |
| W4 | TASK_SUCCESS | 任务成功 | task_uuid / point_cost_final / user_new_balance / cross_episode_exempt_points / result{output_type,url,thumbnail_urls,duration_sec,width_px,height_px} |
| W5 | TASK_FAILED | 任务失败 | task_uuid / error_code / 退款信息 |
| W6 | TASK_CANCELLED | 任务取消 | task_uuid / reason |
| W7 | BATCH_PROGRESS | 批量汇总（每完成 1 个发 1 条） | batch_id / total / success / failed / running / queued / total_points_cost_so_far / point_cost_exempt_count / eta_all_done_ms |
| W8+W9 | NOTIFY | 积分变动/系统通知 | new_balance / delta / reason_label |

上行消息：PING（心跳）/ SUBSCRIBE / UNSUBSCRIBE。

### M.3 心跳 25s + 超时断线 15s×2 + 重连策略

- 客户端每 25s 发 `{type:"PING", client_ts_ms:176xxx}`
- 服务端 10s 内回 PONG；超时未发 PING → Hub 主动 unregister
- 客户端 2 次 PONG 未收到（累计 ~40s）→ 指数退避重连：3s / 7s / 15s / 31s / ...

### M.4 进度消息 250ms 节流合并（同 task_id）

progressThrottle 机制：Emit 时把消息按 task_id 写入 pending map（同 task 后来者覆盖前者），首次写入启动 250ms 定时器；到时 flush 一次性取出全部 pending，逐条 PublishToTopic("task:{uuid}") 推送后清空。效果：同一任务 250ms 内多条进度只推最新一条。

## P. 风险与 Go 代码层面解决建议（6 大风险逐一攻破）

### P.1 风险 1：任务调度幂等（同一条任务被多台 Worker/多 goroutine 重复执行）

**场景**：Scheduler ZRANGEBYSCORE 弹出后，goroutine 切换间隙，另一台 Scheduler 也弹出；或用户手抖点 2 次批量生成。

**Go 代码层面解决方案（三层防护）**：

1. **DB 唯一索引（提交幂等）**：`generation_tasks` 建部分唯一索引 `(space_id, idempotency_key) WHERE deleted_at IS NULL`；提交前查幂等键，已有直接返回旧任务；INSERT 捕获唯一冲突（SQLSTATE 23505）后再次查并返回旧任务 ID
2. **Redis 分布式锁（执行幂等）**：`task:lock:{task_id}` SETNX + EX 30s，value = node_id:pid:goroutine_id:start_ts 唯一标识；加锁成功后启动续约协程每 10s 续约（Lua 校验 value=自己才 EXPIRE）；释放用 Lua 判断 value=自己才 DEL，防误删别人的锁
3. **Running Set（弹出幂等）**：Lua 脚本原子 SADD→ZREM（见 D.3），同一任务不会被两个 Worker 同时取走

### P.2 风险 2：计费事务（积分并发双扣、扣了积分任务没记录、订单成功但积分没到）

**场景**：双 goroutine 同时扣同一用户积分 → SELECT 读到余额=100，都 UPDATE 100-10=90，实际应=80（少扣 10）。

**Go 代码层面解决方案**：

- **铁律**：同一账户所有积分变动必须走 SELECT FOR UPDATE 事务（见 H.3），禁止"先 SELECT 再 UPDATE"的双步写法
- **跨账户转账防死锁**：两个账户的加锁顺序必须全局一致（按 user_id 从小到大先锁小号再锁大号），A→B 和 B→A 并发不会死锁
- **对账兑底**：每日 03:00 gocron 跑一次对账——校验 `current_balance = SUM(CREDIT) - SUM(DEBIT)`，不匹配写 billing_alerts 表 + Sentry 告警 + 以流水为准自动修正

### P.3 风险 3：权限覆盖遗漏（越权访问他人空间资产 / 中间件跳过 Handler 没补）

**场景**：新加一个 `/api/v1/assets/export-zip` 接口，开发者忘了在 Handler 第一行加 CheckSpacePermission，中间件也没匹配路由→漏洞。

**解决方案**：

1. **单元测试强制覆盖**：每个 domain Service 方法≥1 个越权测试用例（构造 A 用户调 B 空间资源，断言必返 2003）
2. **CI 代码审计**：正则扫描 `domain/*/service.go`，每个公开方法首 3 行必须包含 `CheckSpacePermission` 调用或显式注释 `// 无需权限：白名单接口`，否则 CI 红
3. **perm_configs 表驱动**：所有路由必须在管理后台配置权限校验规则；未配置的路由在开发环境直接 500「未配置权限规则」，强制开发者补上

### P.4 风险 4：厂商适配（多厂商 API 差异大、429/5xx 无统一处理、Key 泄露）

**解决方案**：见 E 章完整设计：

- `ModelProvider` 统一接口：Submit/Cancel/Progress，每家 Provider 做一层 Adapter（把厂商返回的奇怪字段映射回 GenResult）
- 连续失败 N 次熔断：fail_count≥5 → model_keys.status=0（Sentry + 邮件告警运维）
- Key AES-256-GCM 加密存储：DB 看不到明文 + 展示仅前 6 后 4 + 轮换功能（key_rotator 每月自动换）
- 429 自动切换：Router.SelectKey 遇到 429 → 临时从候选池移除，5 分钟后恢复

### P.5 风险 5：Agent 流式输出与异步任务回填的一致性

**场景**：用户看到 SSE XML 已输出 `<character id=23 name=沈青禾>`，但 DB 里 characters 表 23 号还没插入→前端点生成时报 404。

**解决方案**：J.5 节 `consistency.go` 机制：

1. SSE 每 flush 一段 → 累积 AppendDelta(task_id, chunk)
2. LLM 返回完整结果 → 后台 goroutine 异步解析 XML → 写 characters/scenes/shots 表（同一 DB 事务要么全成要么全回滚）
3. 全部写完前 generation_tasks.status 保持 RUNNING
4. 写全成功 → SUCCESS + WS TASK_SUCCESS 才发 result
5. 中途任一 SQL 失败 → 任务置 FAILED_RETRYING，积分不扣，重跑整个 Agent

### P.6 风险 6：衍生资产追溯（批量生成失败的那几条不知道 parent_id 是谁、无法单独重试）

**场景**：一次 batch 20 条衍生，17 条成 3 条失败，用户要单独重跑失败的 3 条，但 UI 不知道对应 ref_asset_ids 是哪几张。

**解决方案**：K.1 节 generated_images 表 + 任务自关联 parent_task_id：

- `generation_tasks.parent_task_id`：父任务=批量任务，子任务=单条衍生
- `generated_images.ref_asset_ids int[]`：多张参考图数组，按权重排序
- `generated_images.parent_variant_id`：顶层源头（追溯链 parent_id→…→NULL）

**失败重试查询**：`SELECT gt.id, gt.task_type, gt.error_code, gi.parent_variant_id, gi.ref_asset_ids FROM generation_tasks gt LEFT JOIN generated_images gi ON gi.task_id=gt.id WHERE gt.parent_task_id=$batch AND gt.status IN ('FAILED_DEAD','CANCELED_TIMEOUT')` —— 用户 UI 点「重试失败的 N 条」→ 用此查询取出每条的 prompt+ref_asset_ids+parent_variant_id → 重新入队。

### 附录 C · AI 模型厂商适配坑点清单（⭐ 代码实现必看，开发前逐条过一遍）

#### C.1 厂商/模型/Key 三级管理 + 路由架构（02 数据模型 model_providers / models / model_keys 三张表驱动，代码里禁止硬编码模型名）
- **model_providers 表**：定义厂商基础信息（name/display_name/api_base_url/status），代码里不允许写 `if provider == "seedance"` 这种字符串硬编码，必须从 provider_id → model_providers.name 查询映射
- **models 表**：定义每个模型的能力类型（ability_type=LLM/IMAGE/VIDEO/AUDIO）、基准积分成本 point_cost、默认参数 default_params JSONB；新增模型不需要改代码，只需要在管理后台插入 models 记录即可

#### C.3 限流 429 + 熔断降级策略：
- **单 Key 命中 429 后自动切换下一可用 Key**（按 model_keys.priority 降序）：当前 Key 写 Redis "circuit:key:{id}"="429" EX 300s（5 分钟跳过）→ 取下一 priority 的 Key 重走令牌桶检查 → 全部都在临时熔断中则抛 code=90003
- **同一 Key 连续失败 3 次标记不可用 5 分钟熔断**：
  - 失败判定范围：HTTP 5xx / 网络超时（>30s）/ 厂商返回 error_code=SYSTEM_ERROR（非 NSFW/参数错误等用户侧问题）
  - fail_count++（写 DB model_keys.fail_count + last_fail_at），连续 3 次失败 → model_keys.status=0（熔断）+ 写 Redis "circuit:key:{id}" EX 300s
  - 5 分钟后 Redis TTL 到期，Router.SelectKey 下次查询时自动把 status 恢复 1（前提是 DB status 还是 0 且人工没设停用=2）
- **熔断期间路由跳过**：`SELECT * FROM model_keys WHERE model_id=? AND status=1` 直接过滤掉 DB 层面熔断的，Redis 层面临时熔断在内存过滤
- **所有 Key 全熔断 → 抛 code=90003「厂商限流降级，请稍后重试」**（05 接口文档 C 节 9xxx 系统码）+ **写入失败告警 Prometheus Counter**：`duanju_model_circuit_break_total{provider, model}`、`duanju_model_request_fail_total{provider, error_code}`
  同时 Sentry 告警发邮件 + 钉钉群机器人通知运维（model_keys 全熔断=P1 级故障，30 分钟内响应）

#### C.4 Prompt Few-shot 模板版本管理：
- **拆分/分镜脚本/润色 三类 Prompt 模板不允许硬编码在代码里**，统一存数据库 `agent_skills` 表（表结构真源 → 02 数据模型）：skill_code 唯一（'SCRIPT_SPLIT_V2'/'STORYBOARD_PLAN_V1'/'PROMPT_POLISH_LUXGEM_V3'）· version 版本号（改模板就升版）· template_text 正文（含 Few-shot）· default_model · max_tokens · temperature · is_active（同 skill_code 多版本只有一条 active）；`(skill_code, version)` 唯一索引
  管理后台提供编辑界面：改 Prompt → 升 version → 勾选 is_active=true（旧版本 is_active=false 但保留，方便回滚）
- **改 Prompt 不发版即可热更新**：`engine/agent/agent.go` 里用定时（每 2 分钟）从 DB 加载 active 版本到内存缓存，或 Redis Pub/Sub 通知主动失效缓存
- **每次生成任务的 prompt 版本号要写入 generation_tasks.params.prompt_version**（JSONB 字段里的 `prompt_version: "v2.3.1"`）方便回溯「为什么这次输出格式不对」：
  - 用户反馈输出 XML 格式异常时，先查该 task 的 prompt_version → 再去 agent_skills 查对应版本的 template_text → 快速定位是 Prompt 改坏了还是模型本身抽风
  - 新 Prompt 版本上线后前 100 次调用采样记录 `params.prompt_tokens_used` + `params.output_schema_match_rate`，如果 schema_match_rate <90% 自动告警运营考虑回滚旧版本

#### C.5 视频模型异步回调 vs 轮询策略：
- **厂商支持 webhook → 优先 webhook**（`/api/v1/internal/model-callback/{provider}` 鉴权用 provider 的 secret HMAC 签名校验）：
  - 校验流程：从 URL path 取 provider_code → 查 model_providers 取 webhook_secret → 取请求头 `X-Signature: sha256=xxx` → 用 webhook_secret + raw body 计算 HMAC-SHA256 → 和 X-Signature 比对 → 不匹配直接 401 丢弃
  - 白名单 IP：回调接口最好再加一层 Nginx IP 白名单（Seedance/Kling 官方回调 IP 段从厂商文档获取），双保险防伪造回调
- **厂商不支持 → 轮询间隔 15s**（防止 429），超时上限 30 分钟：轮询循环跑在独立 goroutine（不阻塞 Worker），ticker 固定 15s（不要 5s）；收到进度走 OnProgress 回调；连续 3 次错误才放弃；超时 30 分钟回调超时失败
- **无论 webhook 还是轮询，收到结果都要过幂等检查**：收到厂商完成回调/轮询 done 后第一行必查任务状态——`generation_tasks.status` 已是 SUCCESS 或 FAILED_DEAD 则直接返回（可能 webhook+轮询同时到达），不做任何写操作；通过检查后才：写 OSS → 扣积分 → 更新 DB status → WS 通知
  同时 `generation_task_retry_logs` 表记录每次回调的 provider_task_id + raw payload JSONB，方便事后审计重复回调问题。

#### C.6 输出格式校验 + 自动重试：
- **LLM 拆分输出 XML 格式不正确 → 自动重试 1 次**（附加错误位置提示）：解析失败时把错误的 line/column 信息拼进 retry prompt（「上一轮输出 XML 解析失败，错误位置：%s，请严格按照要求格式输出，不要省略闭合标签」）重跑 1 次；仍失败 → 任务置 FAILED_DEAD + 记 error + 解冻积分（UNFREEZE）+ 站内信通知用户简化剧本后重试
- **资产生成图 URL 404/Content-Length 0 → 自动换另一 model_key 重试 1 次**：收到 GenResult.OutputURL 后必须先 HEAD 校验（状态 200 且非空）；404/空文件 → 当前 Key 标记临时黑名单 5 分钟（"404_EMPTY_RESPONSE"）→ 换同 model_code 另一个 Key 重试 1 次 → 仍失败走正常失败流程（解冻积分 + 站内信）
  不要直接把厂商返回的 URL 存 DB，一定要 HEAD 校验通过后再写 OSS + 存 URL，否则用户前端点开图片裂开。

#### C.7 成本监控（每模型积分定价 vs 实际厂商调用成本）：
- **每小时汇总一次「generation_tasks 各 model_key 调用次数 × 厂商单调用实际价格」和「billing_records 总收入积分 × 积分汇率」比值**（gocron 每小时跑，按 model_code 分组统计近 1 小时 SUCCESS 任务：calls_hour / total_points_charged / total_vendor_cost_yuan / cost_revenue_ratio = 厂商成本 ÷ 积分收入折算元），如果 >1.2（成本超过定价 120%）→ 发送告警给管理员，可临时调低并发阈值或暂停该模型：
  - `$exchange_rate` = 积分汇率（1 积分 = 多少元，从 configs/point_exchange_rate.yaml 读，默认 0.01 元/积分 = 1 元=100 积分）
  - `model_keys.actual_cost_yuan_per_call` 字段：每个 Key 对应的厂商单调用实际成本（按厂商官方价目表填，例 Seedance 2.5 VIP 720p = 0.25 元/次），管理后台可编辑
  - 告警规则：`cost_revenue_ratio > 1.2` → P2 级告警（企业微信 + 邮件），运营需要 24 小时内处理（要么上调 models.point_cost 积分定价，要么联系厂商谈折扣把 actual_cost_yuan_per_call 调低）
  - `cost_revenue_ratio > 1.5` → P1 级严重告警（电话 + 钉钉@所有人），自动触发引擎保护：`model_keys.status=0` 临时熔断该模型所有 Key（避免继续亏钱），对外用户端显示 code=90002「该模型临时维护中，请稍后重试或切换其他模型」，管理员在管理后台手动解除（点「恢复模型」按钮）
