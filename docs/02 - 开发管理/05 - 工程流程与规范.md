# 05 - 工程流程与规范（开发执行手册 · 3 周高密度版）

> 🔒 本文档定义开发期间的**执行流程与协作规范**：状态跟踪、Git、CI、环境、每日节奏、Checkpoint、契约冻结、发布。技术规范细节不在此重复定义（引用 04/06/07）。

---

## 一、批次状态与进度跟踪规则

1. **批次状态机**：`[ ]` 待办 → `[~]` 进行中 → `[x]` 完成；受阻标 `⛔` + 状态列备注原因（引用 06 风险编号）。
2. **完成定义（DoD）**：代码提交 + 对应验收勾选 + CI 绿 + 相关测试通过。缺任一不算完成。
3. **进度同步**：每完成一批，同步更新三处——分解文档勾选、00 总览五章速览表、当日节奏记录。
4. **收口检查点**（3 个）：W1 D2（阶段 0）、W1 D5（阶段 1 晋级）、W2 D10（阶段 2 晋级）。检查点未过 → 吞下阶段前 2 天集中补，P2 顺延。
5. **优先级裁决**：P0 欠账 = 阻塞全部；P1 欠账 → 下阶段前 2 天补；P2 欠账 → 顺延/上线后补（仅阶段 3 允许）。

---

## 二、Git 与分支规范

- **分支策略**：`main`（可部署）+ 功能分支 `feat/<批次号>`（如 `feat/S1-B03`）。单人 + AI 场景：**每批次一个分支，合并即完成批次**。
- **提交信息**：`<类型>(<批次>): <动词性描述>`，类型 = `feat|fix|refactor|test|chore|docs`。示例：`feat(S1-B09): billing 三阶段扣费事务`。
- **合入规则**：合并前必须 `git pull --rebase`；禁止直接 push main（除 S3-Q03 上线发布窗口）；提交不 amend（除非明确要求）。
- **变更纪律**：工作区中的非本人改动（用户/其他工具产生）一律不动、不回退；冲突时停下询问。

---

## 三、CI 规范（阶段 0 B08 落地，全程生效）

| 检查 | 触发 | 门槛 |
|------|------|------|
| lint + typecheck | 每 PR / 每 push | 0 error |
| 单测 + 迁移重复执行 | 每 PR | 全绿；迁移空库/基线库无 diff |
| 契约校验 | 每 PR | 路由/字段与 05 接口文档对齐；枚举与 02 A 章生成物一致 |
| build（后端单二进制 + 双前端） | 每 PR | 可复现构建 |

---

## 四、环境（Docker Compose 单机）

- 统一使用阶段 0 B07 的 `docker-compose.yml`：PG16 + Redis7 + MinIO + app；`.env.example` 为唯一配置模板，实际 `.env` 不入库。
- **数据库纪律**：本地库可随时重置；任何 schema 变更必须走 migrations（禁止手改库）；备份脚本每日跑。
- **模型调用**：开发期用 mock provider / 沙箱 Key，费用与稳定性可控；生产 Key 只放服务器环境。

## 五、每日节奏（3 周高密度版）

| 时段 | 动作 |
|------|------|
| 09:00 | 读当日任务清单（对应阶段文档"执行节奏"行）→ 锁定当日批次（后端 2~3 + 前端 2） |
| 上午 | 后端线优先（依赖前置）；受阻项 30min 内判定：能自解→继续；不能→记入 06 并降级做并行任务 |
| 下午 | 前端线 + 联调；当日批次 DoD 收口 |
| 17:30 | 当日复盘：完成批次数 / 受阻项 / 明日计划；更新 00 速览表 |

**高密度纪律**：单日 4~5 批是常态；批次内"先通后美"——主链路先跑通，视觉统一集中到阶段 3 末（01 H.1 T7 铁律 G）。

## 六、Checkpoint 流程（阶段评审）

1. 触发：每个收口检查点日 17:30。
2. 内容：晋级卡逐条核对（00 四章）+ 批次完成率 + 06 风险状态。
3. 裁决：全 AND 满足 → 进入下一阶段；不满足 → 按 00 弹性吸收规则处理，**不放松验收标准**。
4. 记录：结果写入 00 Changelog 与各阶段文档验收卡。

---

## 七、契约冻结流程

1. 新增/修改接口：先在 `01 - 设计方案/05 - 接口文档.md` 登记（路径/字段/错误码/WS 消息）→ CI 契约校验强制。
2. 前后端类型：一律由契约生成（B08 流水线），禁止手写 DTO。
3. 冻结点：阶段 1 结束起，已发布端点改字段必须走评审（按 00 导航 H 章 scope 流程）。

---

## 八、发布流程（阶段 3 S3-Q03）

1. 上线前置：S3-Q02 通过（安全审计 + 压测 + 轧差=0）+ S3-B03 审核流已上线。
2. 灰度：1% → 10% → 50% → 100%，每档观察 ≥30min，监控阈值：错误率 >1% 或 P95 延迟超阈值 → 停止放量。
3. 回滚：一键回滚脚本（上一稳定镜像），目标 ≤15min；灰度期禁止同时发布两个变更。
4. 发布后：对账脚本跑 24h，次日核对；回滚演练在灰度前完成一次 dry-run。
