# 图片生成模型部署方案（开源模型自部署版）

> **文档定位**：本文档是短剧平台图片生成能力的开源模型部署方案，用于替代商业API（LuxBanana2等），降低运营成本并提升可控性。
> **适用场景**：Step2 资产生成（角色图/场景图/道具图），支持 T2I（文生图）、I2I（图生图）、人物一致性生成。
> **部署架构**：独立GPU推理服务 + Go后端集成（`engine/model/provider_*.go`），对齐 `04 - 后端方案.md E章` 模型接入治理架构。

---

## 一、模型选型与准入状态

> **决策原则**：模型名不等于生产准入。许可证、权重来源、官方推理路径、所需显存与产物质量均应由本项目在上线前留档验证。本文不以第三方测评、未复现的速度或成本数据作为承诺。
>
> **已核验入口**：Qwen-Image 官方仓库为 `QwenLM/Qwen-Image`，魔塔权重入口为 `Qwen/Qwen-Image`。仓库描述明确覆盖复杂文字渲染与图像编辑。具体版本、许可证原文及部署依赖须在实际下载版本的模型卡和 `LICENSE` 中再次固化。

### 1.1 候选模型技术特点

#### Qwen-Image（阿里通义千问图像系列）

**核心特点**：
- 原生中文理解与复杂文字渲染（适合短剧海报、角色定妆等场景）
- 支持多图编辑能力：基于参考图的风格迁移、局部重绘、人物一致性保持
- 官方仓库明确说明支持 T2I（文生图）与 I2I（图生图）双模式
- 模型参数规模与显存需求：以 `Qwen-Image-2512` 为主，需在本地压测确认实际显存占用

**适用场景**：
- 角色定妆（需保持脸部特征、服装风格一致性）
- 带文字的海报/宣传图（中文字符清晰度与版式理解）
- 基于参考图的精细编辑（调整光影、更换背景、局部修改）

**待验证项**：
- 具体版本的商用许可证（不能依赖模型系列名推断）
- 9:16、16:9、1:1 多分辨率下的显存峰值与推理耗时
- 参考图数量对显存与质量的影响
- 编辑模式的稳定性与可控性

#### FLUX.1-schnell（Black Forest Labs）

**核心特点**：
- 快速采样（4 步即可生成高质量图像，官方声称 2-4 秒/张）
- 参数规模约 12B，采用 DiT（Diffusion Transformer）架构
- 社区报告许可证为 Apache 2.0（需以具体下载版本的 LICENSE 为准）
- 适合批量生成、草图候选、快速迭代场景

**适用场景**：
- 场景图批量生成（现代/古代室内外场景）
- 道具图快速候选（生成多个候选供后期选择）
- 对中文语义要求不高、以速度为优先的任务

**待验证项**：
- 实际下载版本的许可证文件内容
- 中文提示词理解准确度（与 Qwen-Image、Kolors 对比）
- 12GB/16GB/24GB 显存下的并发能力与稳定性
- 复杂构图与细节表现（人物、建筑、物品精细度）

#### Kolors（快手可图）

**核心特点**：
- 原生中文训练，参数规模约 5B，采用 ChatGLM3 作为文本编码器
- 社区活跃，魔塔社区有丰富 LoRA 资源（人物、场景、风格）
- 官方示例显示支持人物一致性 LoRA 微调
- 显存需求相对较低（官方声称 8GB 可运行，需实测验证）

**适用场景**：
- 中文提示词精准理解（古装美女、现代职场、特定服装描述）
- 配合 LoRA 实现角色一致性（训练特定角色后批量生成）
- 显存受限环境下的中文图像生成

**待验证项**：
- 与 Qwen-Image 在中文语义、编辑能力上的差异
- LoRA 加载对显存与推理速度的影响
- 不同分辨率下的质量表现与稳定性
- 人物细节（手指、五官、服装）准确度

### 1.2 三层模型职责

| 层级 | 服务职责 | 当前候选 | 准入状态 | 不承担的职责 |
|------|----------|----------|----------|--------------|
| 高质量层 | 中文角色定妆、关键场景、海报、基于参考图的编辑 | Qwen-Image 系列（优先评估 `Qwen-Image-2512`） | 候选；待许可证、显存、I2I 与多图编辑实测 | 不承担全部批量草图任务 |
| 高吞吐层 | 场景/道具草图、批量候选图 | FLUX.1-schnell 或 Kolors | 候选；按实际许可证和压测结果二选一或并存 | 不作为角色一致性的唯一保障 |
| 一致性层 | 参考图约束、姿态/构图控制、修图与重绘 | Qwen-Image 编辑能力；或经兼容性验证的 LoRA、IP-Adapter、ControlNet | 方案待验证 | 不独立生成业务资产 |

`Wan2.1` 属于视频生成方向，可作为后续视频能力调研对象；不纳入本次静态图片服务的主模型或降级链。

### 1.3 性能预期与验证指标

以下为官方文档与社区报告的典型性能范围，**实际性能以本项目压测为准**：

| 模型 | 参数规模 | 典型推理时间 | 显存需求（参考） | 并发能力（参考） | 中文理解 | 编辑能力 |
|------|----------|--------------|------------------|------------------|----------|----------|
| Qwen-Image-2512 | 待确认 | 待压测 | 待压测 | 待压测 | ⭐⭐⭐⭐⭐ 原生中文 | ⭐⭐⭐⭐⭐ 多图编辑 |
| FLUX.1-schnell | ~12B | 官方声称 2-4s/4步 | 官方声称 12GB+ | 社区报告 4-5 并发/24GB | ⭐⭐⭐ 英文为主 | ⭐⭐ 基础 I2I |
| Kolors | ~5B | 社区报告 4-6s/25步 | 社区报告 8GB+ | 社区报告 2-3 并发/24GB | ⭐⭐⭐⭐⭐ 原生中文 | ⭐⭐⭐ 支持 LoRA |

**压测验收指标**（每个模型版本必须完成）：

```text
1. 推理耗时：P50、P95、P99（按 768×1344、1920×1080、1024×1024 分别测量）
2. 显存占用：峰值显存、稳定态显存（单并发与最大并发）
3. 成功率：100 次请求的成功率、失败类型分布
4. 质量评分：基准集人工打分（5 分制），涵盖中文语义、构图、细节、可用性
5. GPU 利用率：推理过程中的平均 GPU 利用率
6. 并发能力：在目标显存（24GB）下可稳定支持的最大并发数
```

### 1.4 资产到能力的映射

| 资产 | 主路径 | 输入 | 输出验收重点 | 失败降级 |
|------|--------|------|--------------|----------|
| 角色图 | 高质量层 → 一致性层 | 角色设定、角色参考图、风格约束 | 脸部/服装特征连续性、中文语义、9:16 构图 | 高质量层不可用时转人工审核或商业 API，不以普通草图模型静默替代 |
| 场景图 | 高吞吐层 | 场景描述、时代/天气/镜头约束 | 构图、空间关系、画风 | 高质量层或经批准的商业 API |
| 道具图 | 高吞吐层 | 道具描述、材质、视角 | 主体完整、材质、背景可抠图性 | 高质量层或经批准的商业 API |
| 海报/带文字画面 | 高质量层 | 中文文案、角色/场景参考 | 文本可读性、人物/品牌一致性 | 商业 API 或人工设计流程 |

### 1.5 模型准入记录

每个实际启用的 `model_version` 必须保存以下不可变元数据：

```text
model_id / version / weight_source_url / downloaded_at
license_url / license_snapshot_sha256 / commercial_review_status
runtime_image_digest / inference_parameters / gpu_profile_id
quality_benchmark_run_id / security_review_status
```

缺少 `commercial_review_status=APPROVED` 或 `quality_benchmark_run_id` 的版本不得进入生产路由。

## 二、推荐部署架构（三层队列与可降级路由）

### 2.1 数据流

```text
资产生成请求
  → Go 模型路由层
  → Redis 任务队列（按 quality / throughput / edit 分流）
  → GPU Worker（Qwen-Image、草图模型、编辑模型）
  → 临时产物校验与内容安全检查
  → MinIO 归档
  → 资产记录与任务状态回写
```

任务状态只允许单向推进：

```text
PENDING → QUEUED → RUNNING → VALIDATING → SUCCEEDED
                         └→ RETRYING → QUEUED
                         └→ FAILED
```

每个任务应携带幂等键、模型版本、输入参考图版本、种子与完整推理参数，以支持重放和质量追溯。

### 2.2 路由和降级规则

```text
角色 / 海报 / 编辑请求 → quality 或 edit 队列 → Qwen-Image 已准入版本
场景 / 道具的批量候选 → throughput 队列 → 已准入的 FLUX 或 Kolors 版本

质量层故障：保留任务并重试；达到重试上限后转人工审核或已批准商业 API。
吞吐层故障：可转质量层或已批准商业 API。
任何降级：必须在任务记录中写入 fallback_reason 与实际 model_version。
```

不得仅通过“是否含中文”决定模型；路由输入必须至少包含 `asset_type`、`quality_tier`、`reference_images`、`edit_mode` 和 `deadline`。

### 3.3 API Server实现（FastAPI）

创建 `deployment/kolors-inference/app/kolors_server.py`：

```python
from fastapi import FastAPI, HTTPException, BackgroundTasks
from pydantic import BaseModel, Field
import torch
from diffusers import KolorsPipeline
import base64
from io import BytesIO
from PIL import Image
import time
import logging

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

app = FastAPI(title="Kolors Inference API")

# 全局模型加载（启动时初始化）
pipe = None

@app.on_event("startup")
async def load_model():
    global pipe
    logger.info("Loading Kolors model...")
    pipe = KolorsPipeline.from_pretrained(
        "/models/kolors",
        torch_dtype=torch.float16,
        variant="fp16"
    ).to("cuda")
    
    # 启用优化
    pipe.enable_model_cpu_offload()  # 8GB显存可用
    pipe.enable_attention_slicing()
    logger.info("Model loaded successfully")

class GenerateRequest(BaseModel):
    prompt: str = Field(..., min_length=1, max_length=2000)
    negative_prompt: str = ""
    width: int = Field(default=1024, ge=512, le=2048)
    height: int = Field(default=1024, ge=512, le=2048)
    num_inference_steps: int = Field(default=25, ge=10, le=100)
    guidance_scale: float = Field(default=5.0, ge=1.0, le=20.0)
    seed: int = Field(default=-1, ge=-1)
    lora_weights: dict = {}  # {"lora_name": weight}

class GenerateResponse(BaseModel):
    image_base64: str
    seed: int
    inference_time_ms: int
    model: str = "Kolors"

@app.post("/v1/generate", response_model=GenerateResponse)
async def generate_image(req: GenerateRequest):
    if pipe is None:
        raise HTTPException(status_code=503, detail="Model not loaded")
    
    start_time = time.time()
    
    try:
        # 设置随机种子
        if req.seed == -1:
            seed = torch.randint(0, 2**32, (1,)).item()
        else:
            seed = req.seed
        
        generator = torch.Generator("cuda").manual_seed(seed)
        
        # 加载LoRA权重（人物一致性）
        if req.lora_weights:
            for lora_name, weight in req.lora_weights.items():
                lora_path = f"/models/loras/{lora_name}.safetensors"
                pipe.load_lora_weights(lora_path)
                pipe.fuse_lora(lora_scale=weight)
        
        # 生成图片
        image = pipe(
            prompt=req.prompt,
            negative_prompt=req.negative_prompt,
            width=req.width,
            height=req.height,
            num_inference_steps=req.num_inference_steps,
            guidance_scale=req.guidance_scale,
            generator=generator
        ).images[0]
        
        # 转base64
        buffered = BytesIO()
        image.save(buffered, format="PNG", optimize=True)
        img_base64 = base64.b64encode(buffered.getvalue()).decode()
        
        inference_time = int((time.time() - start_time) * 1000)
        
        logger.info(f"Generated image: {req.width}x{req.height}, "
                   f"steps={req.num_inference_steps}, time={inference_time}ms")
        
        return GenerateResponse(
            image_base64=img_base64,
            seed=seed,
            inference_time_ms=inference_time
        )
        
    except Exception as e:
        logger.error(f"Generation failed: {str(e)}")
        raise HTTPException(status_code=500, detail=str(e))

@app.get("/health")
async def health_check():
    if pipe is None:
        return {"status": "loading", "model": "Kolors"}
    return {
        "status": "ready",
        "model": "Kolors",
        "gpu": torch.cuda.get_device_name(0),
        "vram_allocated_gb": round(torch.cuda.memory_allocated(0) / 1024**3, 2)
    }

if __name__ == "__main__":
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8188, log_level="info")
```

        Height:            dims.Height,
        NumInferenceSteps: 25,
        GuidanceScale:     5.0,
        Seed:              req.Seed,
    }
    
    // 人物一致性LoRA（从character表的consistency_seed字段读取）
    if req.CharacterLoRA != "" {
        payload.LoraWeights = map[string]float64{
            req.CharacterLoRA: 0.8,
        }
    }
    
    body, _ := json.Marshal(payload)
    httpReq, err := http.NewRequestWithContext(ctx, "POST", k.BaseURL+"/v1/generate", bytes.NewReader(body))
    if err != nil {
        return nil, fmt.Errorf("create request: %w", err)
    }
    
    httpReq.Header.Set("Content-Type", "application/json")
    if k.APIKey != "" {
        httpReq.Header.Set("Authorization", "Bearer "+k.APIKey)
    }
    
    resp, err := p.client.Do(httpReq)
    if err != nil {
        return nil, fmt.Errorf("kolors request failed: %w", err)
    }
    defer resp.Body.Close()
    
    if resp.StatusCode == 429 {
        return nil, ErrRateLimited  // 触发Key切换
    }
    
    if resp.StatusCode != 200 {
        body, _ := io.ReadAll(resp.Body)
        return nil, fmt.Errorf("kolors returned %d: %s", resp.StatusCode, body)
    }
    
    var result kolorsResponse
    if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
        return nil, fmt.Errorf("decode response: %w", err)
    }
    
    // 上传到MinIO（调用 engine/asset 的 UploadBase64）
    imageURL, err := uploadBase64ToS3(ctx, result.ImageBase64, "png", "assets")
    if err != nil {
        return nil, fmt.Errorf("upload to s3: %w", err)
    }
    
    return &ImageResponse{
        ImageURL:  imageURL,
        ModelUsed: "Kolors",
        KeyID:     k.ID,
        Metadata: map[string]interface{}{
            "seed":            result.Seed,
            "inference_time":  result.InferenceTimeMs,
        },
    }, nil
}

func (p *KolorsProvider) Chat(ctx context.Context, k *KeyCredential, req *ChatRequest) (*ChatResponse, error) {

}

func (p *KolorsProvider) GenerateVideo(ctx context.Context, k *KeyCredential, req *VideoRequest) (*VideoResponse, error) {

// parseResolution 解析分辨率字符串到具体尺寸
func parseResolution(resolution, aspectRatio string) struct{ Width, Height int } {
    // 短剧平台常用尺寸映射
    resMap := map[string]map[string]struct{ Width, Height int }{
        "1K": {
            "R16_9": {Width: 1024, Height: 576},
            "R9_16": {Width: 576, Height: 1024},
            "R1_1":  {Width: 1024, Height: 1024},
        },
        "2K": {
            "R16_9": {Width: 1920, Height: 1080},
            "R9_16": {Width: 1080, Height: 1920},
            "R1_1":  {Width: 1536, Height: 1536},
        },
    }
    
    if dims, ok := resMap[resolution][aspectRatio]; ok {
        return dims
    }
    
    // 默认9:16短剧竖屏
    return struct{ Width, Height int }{Width: 768, Height: 1344}
}

// SelectProvider 根据任务类型和提示词智能选择Provider
func (r *Router) SelectProvider(ctx context.Context, req *ImageRequest) (*KeyCredential, Provider, error) {
    // 规则1：中文提示词优先Kolors
    if containsChinese(req.Prompt) {
        if key, err := r.getAvailableKey(ctx, "KOLORS", CapT2I); err == nil {
            return key, NewKolorsProvider(), nil
        }
    }
    
    // 规则2：角色图且需要人物一致性 → Kolors
    if req.AssetType == "CHARACTER" && req.CharacterLoRA != "" {
        if key, err := r.getAvailableKey(ctx, "KOLORS", CapT2I); err == nil {
            return key, NewKolorsProvider(), nil
        }
    }
    
    // 规则3：场景图/道具图 → FLUX（速度优先）
    if req.AssetType == "SCENE" || req.AssetType == "PROP" {
        if key, err := r.getAvailableKey(ctx, "FLUX", CapT2I); err == nil {
            return key, NewFluxProvider(), nil
        }
    }
    
    // 降级链：按优先级依次尝试
    providers := []string{"KOLORS", "FLUX", "LUXBANANA"}
    for _, providerName := range providers {
        if key, err := r.getAvailableKey(ctx, providerName, CapT2I); err == nil {
            return key, r.getProviderInstance(providerName), nil
        }
    }
    
    return nil, nil, ErrNoAvailableKey
}

func containsChinese(s string) bool {
    for _, r := range s {
        if r >= 0x4E00 && r <= 0x9FFF {
            return true
        }
    }
    return false
}

## 六、容量、成本与性能验收

本项目尚未在目标 GPU、目标分辨率、目标并发和真实提示词集上完成统一压测。因此不在设计文档中预设月租、单张成本、P50/P95、并发或质量提升百分比。

### 6.1 GPU 档位与部署目的

| 档位 | 适用目的 | 推荐队列配置 | 产能结论 |
|------|----------|--------------|----------|
| 单卡开发 | 接口联调、模型准入、少量人工验收 | 同一 GPU 上串行或低并发运行一个候选服务 | 仅用于确认功能与质量，不作为生产容量依据 |
| 中等生产 | 角色质量队列与场景吞吐队列分离 | 至少隔离高质量 Worker 与高吞吐 Worker | 以压测结果配置并发和自动扩缩阈值 |
| 多 GPU 生产 | 高质量队列横向扩容、批量任务削峰 | 按队列独立扩容；同一模型版本使用可复现容器镜像 | 以队列等待时间、SLO 和单位产出成本决定规模 |

实际显存由模型版本、精度、分辨率、参考图数量、编辑模式和并发共同决定。部署前必须以该版本官方文档为基础，再进行本地压测确认。

### 6.2 各模型服务器性能要求（最低 / 推荐）

> 以下配置基于各模型公开参数规模与社区部署实践整理，作为采购/租赁选型基线。**最终以本项目在目标分辨率、目标并发下的压测结果为准**；表内单张耗时为社区参考值，非承诺值。

| 项目 | Qwen-Image（约 20B） | FLUX.1-schnell（约 12B） | Kolors（约 5B + ChatGLM3 编码器） |
|------|----------------------|--------------------------|-----------------------------------|
| 权重体积 | bf16 ≈ 40GB；FP8 ≈ 20GB | bf16 ≈ 23.8GB | fp16 ≈ 9.2GB |
| **最低 GPU** | 单卡 24GB（RTX 4090/3090，需 FP8 量化） | 单卡 16GB（INT8 量化 + CPU offload，速度明显下降） | 单卡 8GB（fp16 + attention slicing + CPU offload） |
| **推荐 GPU** | 单卡 80GB（A100/H100/L40S）或双卡 24GB 张量并行 | 单卡 24GB（RTX 4090/3090/A5000） | 单卡 16GB（RTX 4080/A4000）；预算宽裕可 24GB |
| 最低系统内存 | 64GB | 32GB | 16GB |
| 推荐系统内存 | 128GB（≥ 显存 2 倍，用于加载中转与 offload） | 64GB | 32GB |
| CPU 核数 | 最低 8 核；推荐 16 核（影响模型加载与前后处理） | 最低 8 核；推荐 16 核 | 最低 4 核；推荐 8 核 |
| 磁盘（NVMe SSD） | ≥ 100GB | ≥ 80GB | ≥ 30GB |
| 单张耗时（1024×1024，参考） | 10-30s（视量化与并行方式） | 2-4s（4 步） | 4-8s（25 步） |
| 单卡并发（参考） | 2-4 并发 | 4-5 并发 | 2-3 并发 |

**最低配置**：仅用于功能验证、模型准入与少量人工验收，不建议承载生产流量；8-16GB 档还需接受显著变慢的单张耗时。
**推荐配置**：满足生产角色队列（Qwen-Image）与吞吐队列（FLUX/Kolors）的日常业务；具体并发数、P50/P95 以压测为准。

各模型补充说明：

- **Qwen-Image（约 20B）**：bf16 权重约 40GB，24GB 单卡必须采用 FP8 量化（社区实践）或 CPU offload；若不量化，需双卡 24GB 张量并行或单卡 48GB/80GB。文本编码器与视觉编码器同样计入显存。
- **FLUX.1-schnell（约 12B）**：T5-XXL 文本编码器约 9.5GB，可卸载至 CPU 换取单卡 16GB 可运行性，但每次推理需传回编码结果，速度显著下降；24GB 档无需卸载，4 步采样 2-4s/张。
- **Kolors（约 5B）**：ChatGLM3 编码器 + UNet + VAE 合计约 9.2GB（fp16）；8GB 档需启用 attention slicing 与 CPU offload，单张耗时从 4-8s 上升到约 15-30s；16GB 档可全量驻留显存。

#### 服务器整机基线（每台推理机）

```text
CPU：16 核（Xeon/EPYC 或同级）
内存：128GB（≥ 推荐 GPU 显存的 2 倍，用于模型加载中转与 CPU offload）
磁盘：NVMe SSD 2TB（模型权重 + LoRA + 临时输出 + 日志，容量按模型体积预留）
网络：内网 10Gbps（base64 图片传输 + MinIO 写入）
电源/散热：按 GPU TDP 预留（如 RTX 4090 需 ≥ 850W 电源、双槽以上散热）
系统：Ubuntu 22.04 LTS + NVIDIA 驱动 ≥ 535 + CUDA 12.x + Docker（nvidia-container-toolkit）
```

#### 部署组合建议

| 组合 | GPU 方案 | 适用 |
|------|----------|------|
| 最小开发 | 1 × 24GB（Kolors 与 FLUX 二选一） | 接口联调、模型准入、人工验收 |
| 标准生产 | 1 × 24GB（FLUX）+ 1 × 24GB（Qwen-Image FP8） | 吞吐队列与质量队列分离 |
| 推荐生产 | 1 × 80GB（Qwen-Image）+ 1 × 24GB（FLUX/Kolors） | 中文质量 + 高吞吐并行 |
| 多 GPU 生产 | N × 80GB（质量层）+ M × 24GB（吞吐层），按队列独立扩缩 | 批量任务削峰 |

80GB 单卡可借助 vLLM 等框架按队列显存隔离同时加载多个模型，但建议先各自独立部署以简化排障，待压测稳定后再评估合并部署。

### 6.3 压测与成本计算口径

基准集至少覆盖中文角色、古今场景、道具、含文字海报、单图编辑、多参考图一致性六类请求。一次基准运行固定以下变量：

```text
模型版本 + 容器镜像摘要 + GPU 型号 + 精度 + 分辨率 + 推理参数
+ 并发级别 + 提示词集版本 + 参考图集版本
```

记录指标：端到端成功率、排队时间、推理耗时 P50/P95、重试率、显存峰值、GPU 利用率、MinIO 写入失败率、人工质量评分与每张有效资产的完全成本。

```text
单位有效资产成本 = (GPU 实际占用成本 + 存储/网络成本 + 重试成本) / 通过质量验收的产物数量
```

只有同一基准集、同一质量门槛下的候选模型才可比较成本；失败、重试和人工返工必须计入。

### 6.4 不同模型的性能权衡

基于官方文档与社区实践的典型权衡（**实际以压测为准**）：

| 维度 | Qwen-Image | FLUX.1-schnell | Kolors | 权衡建议 |
|------|------------|----------------|--------|----------|
| 中文理解 | 原生支持，复杂语义准确 | 英文为主，中文需翻译或质量下降 | 原生支持，ChatGLM3 编码器 | 中文场景优先 Qwen-Image 或 Kolors |
| 编辑能力 | 多图编辑、参考图一致性强 | 基础 I2I | 支持 LoRA 微调 | 精细编辑选 Qwen-Image，风格迁移选 Kolors+LoRA |
| 推理速度 | 待实测 | 4 步快速采样，官方声称 2-4s | 25 步标准采样，4-6s | 批量草图优先 FLUX，质量优先 Qwen-Image |
| 显存占用 | 待实测 | ~12GB（官方声称） | ~8GB（社区报告） | 显存受限时考虑 Kolors；充足时选高质量模型 |
| 并发能力 | 待实测 | 社区报告 4-5 并发/24GB | 社区报告 2-3 并发/24GB | 高吞吐场景选 FLUX，高质量选 Qwen-Image |
| 文字渲染 | 官方强调复杂文字支持 | 一般 | 中文文字较好 | 海报、标题场景优先 Qwen-Image |
| 生态资源 | 阿里官方维护 | 社区活跃 | 魔塔社区 LoRA 丰富 | Kolors 适合快速接入现有 LoRA 资源 |

**推荐决策路径**：
1. **短剧角色定妆、海报**：优先 Qwen-Image（中文+编辑+文字）
2. **场景/道具批量候选**：优先 FLUX.1-schnell（速度+并发）
3. **显存受限环境**：Kolors（8GB 即可运行）
4. **需要风格 LoRA**：Kolors（生态资源丰富）

### 8.2 灰度策略实现

在 `engine/model/router.go` 添加灰度开关：

```go
// GrayReleaseConfig 灰度配置（从Redis读取，支持热更新）
type GrayReleaseConfig struct {
    OpenSourceRatio float64 // 0.0-1.0，开源模型流量占比
    EnabledUsers    []int64 // 白名单用户（强制走开源）
}

func (r *Router) SelectProviderWithGray(ctx context.Context, req *ImageRequest, userID int64) (*KeyCredential, Provider, error) {
    // 读取灰度配置（Redis缓存30秒）
    grayConfig := r.getGrayConfig(ctx)
    
    // 白名单用户强制走开源
    if contains(grayConfig.EnabledUsers, userID) {
        return r.selectOpenSourceProvider(ctx, req)
    }
    
    // 按比例随机分流
    if rand.Float64() < grayConfig.OpenSourceRatio {
        if key, provider, err := r.selectOpenSourceProvider(ctx, req); err == nil {
            return key, provider, nil
        }
        // 开源模型不可用，降级到商业API
    }
    
    // 商业API（LuxBanana2）
    return r.getAvailableKey(ctx, "LUXBANANA", CapT2I), NewLuxBananaProvider(), nil
}

func (r *Router) selectOpenSourceProvider(ctx context.Context, req *ImageRequest) (*KeyCredential, Provider, error) {
    // 中文提示词 → Kolors
    if containsChinese(req.Prompt) {
        if key, err := r.getAvailableKey(ctx, "KOLORS", CapT2I); err == nil {
            return key, NewKolorsProvider(), nil
        }
    }
    
    // 场景/道具 → FLUX
    if key, err := r.getAvailableKey(ctx, "FLUX", CapT2I); err == nil {
        return key, NewFluxProvider(), nil
    }
    
    return nil, nil, ErrNoAvailableKey
}
```

**灰度控制（Redis Key）**：

```bash
# 设置灰度比例（10%流量）
redis-cli SET "model:gray:opensource_ratio" "0.1"

# 添加白名单用户
redis-cli SADD "model:gray:whitelist_users" 12345 67890

# 查询当前配置
redis-cli GET "model:gray:opensource_ratio"
redis-cli SMEMBERS "model:gray:whitelist_users"
```

### 8.3 回滚预案

如果开源模型出现严重问题：

```bash
# 紧急回滚：灰度比例设为0
redis-cli SET "model:gray:opensource_ratio" "0"

# 或者：在数据库中禁用开源模型
UPDATE models SET enabled = false WHERE model_code IN ('kolors-v1', 'flux-1-schnell');

# 或者：停止推理服务容器
docker stop kolors-inference flux-inference
```

## 九、FAQ与边界

### Q1：为什么不直接以 Kolors 或混元 DiT 作为角色主模型？

角色资产的核心约束是参考图一致性和可编辑性，不只是中文提示词理解。所有候选均需通过同一基准集验证；当前优先验证 Qwen-Image 的中文生成与编辑能力。

### Q2：FLUX.1-schnell、FLUX.1-dev 如何选择？
先核对拟下载**具体版本**的官方许可证、模型卡和推理依赖，再以本项目基准集测量质量与吞吐。不得用模型系列名称推导商用资格，也不得将未获准版本加入生产降级链。

### Q3：低显存 GPU 能否运行？

可以作为研发探索的可能路径，但内存卸载、分辨率、精度、参考图数量及并发都会影响稳定性。仅以目标模型版本的本地启动与峰值显存压测结论配置生产档位。

### Q4：如何验证图片质量？

固定提示词和参考图基准集，双盲人工评分并记录失败类型。角色图评估一致性、构图、中文语义与可用性；场景/道具评估语义、主体完整性和后续制作可用性。每个模型版本的评分应关联 `quality_benchmark_run_id`。

### Q5：Wan2.1 是否在本次部署范围？

否。Wan2.1 是视频生成扩展方向。本方案仅覆盖 Step2 的静态角色、场景和道具资产；视频生成应建立独立的模型准入、队列和成本评估。

## 十、当前结论与后续工作

### 10.1 当前架构结论

| 维度 | 决策 |
|------|------|
| 高质量资产 | 优先验证 Qwen-Image 系列，承担中文角色、海报和编辑请求 |
| 批量资产 | 在许可与压测通过的 FLUX / Kolors 版本中选择高吞吐服务 |
| 一致性 | 以参考图和编辑链路为主；适配器类方案仅在兼容性验证后启用 |
| 集成边界 | Go 路由层负责模型选择、降级和审计；Redis 负责任务状态；MinIO 负责产物归档 |
| 上线门槛 | 许可证审查、基准质量、容量压测、内容安全与可观测性全部通过 |

### 10.2 下一阶段：Qwen-Image 准入验证

1. 从官方仓库或模型卡确定拟评估版本、权重地址、许可证原文与对应 commit/tag。
2. 使用固定容器环境启动 T2I、I2I 与编辑最小链路，记录 GPU/显存、参数和输出。
3. 以本方案的基准集比较 Qwen-Image、FLUX/Kolors 候选，并将通过版本写入模型注册表。
4. 在 Go 侧接入异步任务契约：幂等键、任务状态、产物 MinIO 地址、模型版本和降级原因。
