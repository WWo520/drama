# 按 LuxReal 设计对齐 —— 差距清单与实施策略

> 创建日期：2026-08-22
> 状态：待排期（仅记录，未实施）
> 依据：`docs/10 - 剧本skills/02 - LuxReal全流程执行过程与提示词调查报告.md`（含第九章分集机制专项调研）
> 背景：LuxReal 分集为「集=用户侧容器 + AI 主攻集内拆分」双轨制，拆分单次 LLM 调用出整树；本项目为「算法驱动 + 确定性后处理保底」。本清单列出对齐其设计所需的全部改动项。

---

## 一、差距总览

| # | 维度 | LuxReal 设计 | 我们现状 | 差距等级 |
|---|------|-------------|----------|---------|
| G1 | 集的产生方式 | 集是用户容器：`+新增剧集`按钮，按集粘贴剧本/命名/配时长预设 | 集完全由 LLM+后处理产出，无手动建集入口 | 🔴 大 |
| G2 | 每集时长预设 | 本集预设总时长下拉（自动/1分钟/1-2/2-3/3-5/5-10分钟），两级继承到单元 | 项目级单一 EpisodeDurationMin，集级无独立预设 | 🟡 中 |
| G3 | 拆分结果可编辑性 | 单元行内编辑（原文/标题/时长）、增删、拖拽排序 | 只能整项目重拆 | 🔴 大 |
| G4 | 重跑粒度 | 单叙事单元重新规划，不动全项目 | 整项目重拆（级联清空资产） | 🟡 中 |
| G5 | 历史版本 | 分镜/单元历史版本与回滚 | 无版本表 | 🟢 小（P2） |
| G6 | 提示词可配置 | 4-Tab 技能面板，模板全量公开可编辑可另存 | Go 硬编码 splitSystemPrompt + DB 技能种子 | 🟢 小（P2，观察） |
| G7 | 拆分输出契约 | 标记语法文本（【场景X：地点—时间】/▲/角色名（动作）：台词） | JSON schema + 枚举校验 | ⚪ 不对齐（我们更硬，保留） |
| G8 | 粒度控制 | 场景/连贯性判据 + 时长预设继承，无数学估时 | 4字/秒估时 + ≤30s/≤120字铁律 | ⚪ 不对齐（互补，保留） |

> G7/G8 为**有意保留的差异**：LuxReal 有人工精修兜底所以判据可以软；我们无精修 UI 时数学铁律+确定性后处理是唯一可靠选项。仅当 G3/G4 落地后才考虑放松。

## 二、改动项清单（按优先级）

### Q1【P0】手动新增剧集（对齐 G1）

**LuxReal 行为**：Step1 剧集栏底部 `+新增剧集` 按钮（`EpisodeSidebar-addEpisodeBtn_7b541`），自建项目弹出「剧本粘贴 + 集数命名 + 时长预设」配置弹窗；官方只读案例中按钮静默。

**落地要点**：
- 后端：新增 `POST /api/v1/projects/:id/episodes`（title、original_script_text、preset_duration），写入 episodes 表并重排 sort_order；该集可独立触发拆分（仅拆本集，不影响其他集）；
- 前端：Step1 剧集大纲栏（web-user 工作台左侧）底部加「+ 新增剧集」按钮 + 弹窗（集名输入/剧本粘贴/时长预设下拉）；
- 约束：手动新增的集走同一套拆分流程，但 minEpisodes 按 1 处理（集已人为确定，只拆集内单元）；
- 与现有后处理的兼容：`NormalizeEpisodeCount` 需跳过"用户手动指定集结构"的项目（加标记或按集数>1且均含原文判断），避免后处理把用户建的集重新均分。

**涉及文件（预估）**：`internal/handler/episode_handler.go`（新增）、`internal/service/*`、`apps/web-user/src` Step1 页面组件。

### Q2【P0】集级时长预设两级继承（对齐 G2）

**LuxReal 行为**：本集预设总时长下拉（自动/1分钟/1-2分钟/2-3分钟/3-5分钟/5-10分钟），单元继承集预设、可单独覆盖；episodes 表含 `preset_total_duration`（NULL=自动）。

**落地要点**：
- DB：episodes 表确认/新增 `preset_total_duration_sec INT NULL`（NULL=沿用项目级）；
- 拆分时 minUnits/目标时长按"集预设优先、项目级兜底"计算——即**逐集计算**而非全项目统一；
- 前端：每集卡片头部加时长预设下拉（对齐 LuxReal 的 6 档）；
- 注意：当前 `Execute` 里 minEpisodes/minUnits 是全项目一次算的，需改为按集参数化。

**涉及文件（预估）**：migration 新增列、`split_handler.go` 参数计算、episodes 模型与前端集卡片。

### Q3【P1】叙事单元行内编辑（对齐 G3）

**LuxReal 行为**：单元卡片可改剧本原文/标题/时长，点击上/下增加新叙事单元，右上角设置时长、删除单元——拆分结果全部行内可精修，无需重拆。

**落地要点**：
- 后端：narrative_units 的 PATCH（title/duration_sec/script_original_text）、POST 插入（指定 sort_order）、DELETE（级联清理关联资产引用与镜头）；
- 校验：编辑后时长仍受 ≤30s 铁律约束（或放宽——人工编辑的值可豁免自动校验，需决策）；
- 前端：单元卡片行内编辑 + 增删按钮 + 拖拽排序（P2 可先做上下移动按钮）；
- 编辑后资产一致性：原文/时长变更是否触发该集资产重提取——LuxReal 有「重新提取本集资产」按钮，对应 Q6。

### Q4【P1】单叙事单元重拆（对齐 G4）

**LuxReal 行为**：单单元重新规划弹窗，仅重跑该单元的分镜/镜头，不动全项目、不级联清空其他集资产。

**落地要点**：
- 后端：新增单单元拆分任务类型（复用 SCRIPT_SPLIT 的提示词但输入仅该单元原文，输出仅 shot_groups），任务表 generation_tasks 加 target 粒度字段（project_id → narrative_unit_id）；
- 与现有 reaper/重试机制兼容：单单元任务失败只回滚该单元；
- 前端：单元卡片「重新生成镜头」入口。

### Q5【P2】历史版本与回滚（对齐 G5）

**LuxReal 行为**：Step3 分镜历史版本、单元重新规划后可回滚（M1 里程碑功能 beat_versions 表）。

**落地要点**：narrative_units/shot 层加快照表（unit_id、version、payload JSON、created_at），重拆前自动快照；前端版本列表+回滚。成本高，建议 Q3/Q4 稳定后再做。

### Q6【P1】重新提取本集资产（配套 G3/G4）

**LuxReal 行为**：剧本修改后一键重跑该集资产提取，不必重走全流程。

**落地要点**：集级资产重提取接口（删除该集旧资产引用 → 重跑资产提取任务）；与 Q3 编辑动作联动（编辑原文后提示"是否需要重新提取资产"）。

### Q7【P2】提示词模板可配置化（对齐 G6）

**LuxReal 行为**：Tab2「生成逻辑/预期镜头格式」双槽位、模板可另存共享。

**落地要点**：splitSystemPrompt 的"规则部分"抽入 DB 技能表（已有技能种子机制），管理端可编辑；保留 JSON 结构契约不可改。**建议等技能数量 >20 或有第二个拆分场景再做**（报告 8.1 已列为不建议照搬项）。

## 三、实施顺序建议

```
第一批（P0，集容器化）：Q1 手动新增剧集 → Q2 集级时长预设
    └ 完成后：分集机制与 LuxReal 双轨制对齐（算法自动 + 手动容器并存）
第二批（P1，精修能力）：Q3 行内编辑 → Q4 单单元重拆 → Q6 集级资产重提取
    └ 完成后：人工介入点对齐，可考虑放松数学铁律（G8 转为判据主导）
第三批（P2，增强）：Q5 历史版本 → Q7 提示词模板化
```

## 四、关键决策点（实施前需确认）

1. **手动建集与自动分集的共存规则**：项目已有自动拆分结果时，手动新增的集追加在末尾还是插入排序？（建议：追加末尾，sort_order 顺延）
2. **手动建的集是否也过确定性后处理**：建议不过（集数是用户意志），但集内单元仍走 SplitOversizedUnits/覆盖率校验；
3. **行内编辑的时长豁免**：人工手填的 duration_sec 是否豁免 ≤30s 校验？（建议：豁免但前端警告，因为人工编辑意味着用户自担粒度责任）
4. **单单元重拆的计费**：是否单独扣积分（LuxReal 跨集复用不重复扣费，单单元重跑的计费口径需定）。
