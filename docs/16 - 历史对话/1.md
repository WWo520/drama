# web-user（React+Vite 用户前端）结构总结

## 一、路由结构（src/router.tsx）

文件：`d:\develop\a_work\duanju\apps\web-user\src\router.tsx`

使用 `createBrowserRouter`（react-router-dom v6），共 12 条路由，`RequireAuth` 守卫包裹所有登录后页面：

| 路径 | 页面 | 说明 |
|---|---|---|
| `/login` | LoginPage | 唯一公开路由，无守卫 |
| `/` | HomePage | 创作入口首页 |
| `/projects` | ProjectListPage | 作品列表 |
| `/projects/:projectId` | Step1Page | 直接进入项目 Step1 |
| `/projects/:projectId/step/:step` | StepRouter → Step1~4Page | Step 分发路由 |
| `/points` | PointsPage | 积分充值中心 |
| `/spaces` | SpaceManagePage | 空间/团队管理 |
| `/canvas` | CanvasPage | 自由画布 |
| `/timeline` | TimelinePage | 多轨剪辑 |
| `/feed` | FeedPage | 发现/作品广场 |
| `/notifications` | NotificationsPage | 消息中心 |
| `/tasks` | TasksPage | 任务接单 + 模板集市 |
| `/admin` | AdminPage | 管理端（指标/用户/内容/审核/开发者） |

关键机制：
- `RequireAuth`（router.tsx 第 22-33 行）：读取 `authStore.accessToken`，无 token 则 `<Navigate to="/login">`；有 token 时挂载全局 `GlobalWS`（WebSocket 连接）再渲染子页面。
- `StepRouter`（router.tsx 第 36-48 行）：按 URL 参数 `step` 分发到 Step2/3/4 页面，默认 Step1Page。
- 步进锁定不在此处做，而是由 `useStepState` hook 根据后端项目状态控制。

- 埋点/统计域为 `actionstat.kujiale.com`、`actiontrack.kujiale.com:8888`、`mc.kujiale.com:8880`，静态资源走 `qhstaticssl.kujiale.com`，业务接口均在 `www.luxreal.com/render/*` 下。

实测结果出来了。真相是：**LuxReal 也有限流，只是正常操作根本触发不到**。

## LuxReal 该页面的实测数据（浏览器观察 90 秒）

| 指标 | LuxReal 实测 |
|---|---|
| 首屏请求量 | 约 30 个 XHR |
| 90 秒总请求 | 87 个（含约 18 个**埋点**上报，走独立域名 `actionstat.kujiale.com`） |
| 业务接口重复调用 | 仅在组件重挂载时毫秒级并发（2~3 次），**非定时轮询** |
| 轮询 / WebSocket | **无**周期性轮询；任务状态依赖推送/一次性查询 |
| 429 / 限流响应 | 未触发，探测接口全 200 |

按此用量换算，业务请求约 40~50 次/分钟——正好卡在它的 **60/min** 阈值内。它的限流不是没有，而是**阈值按真实用户最坏用量标定，正常人永远碰不到**。

## 为什么我们容易触发（核心差异在前端请求模式）

| 对比项 | LuxReal | 本项目现状 |
|---|---|---|
| 重复请求去重 | SWR 3s dedupe（同 key 3s 内只发一次） | 无去重，页面加载即并发 4~8 个 |
| 任务进度 | WS 推送 + 一次性查询 | **5s 定时轮询** + 多处轮询 |
| 埋点/统计 | 独立域名，不占业务配额 | 无独立埋点 |
| 实际请求密度 | ~50/min 业务请求 | 轮询叠加后轻松 >120/min |

所以结论是：
- **限流本身是对的**（防刷、防烧模型成本），LuxReal 同样在限流
- 我们被误伤，是因为**前端请求模式低效**（轮询代替推送、无缓存去重），把请求量顶到了阈值
- 我们的 120/min（登录）其实比 LuxReal 的 60 还宽松，仍被打满，说明问题不在阈值而在请求量
