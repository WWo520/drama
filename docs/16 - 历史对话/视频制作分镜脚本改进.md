## 三、剧本拆分（SCRIPT_SPLIT）任务类型与流程

### 3.1 触发链路

1. 前端 `Step1Page.tsx` → `splitApi.triggerSplit`（`packages\api-client\src\api\split.ts` L57）→ `POST /projects/:project_id/split-script`，参数含 `force / script_text / episode_duration_min / split_skill_code`（拆分技能来自全局 agent_skills 库，`GET /skills?kind=SCRIPT_SPLIT`，技能选择弹窗为 `AgentSkillModal.tsx`）。
2. 后端路由：`duanju-backend\internal\domain\creation\handler.go` L50。
3. Worker 侧执行器：`duanju-backend\internal\engine\agent\split_handler.go`（`cmd\worker\main.go` L101 注册，split 角色）。

### 3.2 SplitHandler 执行流程（split_handler.go）

```
读剧本（参数空则回退 projects.source_script_text）
→ 计算 minUnits / minEpisodes 下限（4字/秒语速折算）
→ ① 拆分 LLM（splitSystemPrompt，双 LLM 之一；坏 JSON/集数不足/摘录不完整自动重试 maxTry=4，
   MaxTokens=16384，JSONMode，NoThinking）
→ ①.5 确定性后处理：SplitOversizedUnits / NormalizeEpisodeCount（splitter.go）
→ ②.5 AI 扩写资产提示词 optimizeAllAssets（角色≥80字/场景≥100字/道具≥40字，失败不阻塞）
→ ③ 逐镜头润色 polishAll → prompt_refined（LuxReal 8 字段结构化格式，失败回退 luxShotPrompt）
→ ④ SaveSplitResult 事务入库 → 项目状态 SCRIPT_SPLITTING → PARTIAL_ASSETS
```

一次性产出**四层结构**：`episodes → narrative_units → shot_groups → shots`（8 字段：duration_sec/shot_size/camera_movement/camera_angle/subject/background/light/dialogue/ambient_sound）+ 集级资产 `characters/scenes/props`。

### 3.3 入库与资产建链（`internal\repository\split_store.go`）

`SaveSplitResult`（L50 起）事务写入：集/单元/块/镜头 + `narrative_unit_versions` v1 快照 + 角色/场景/道具（ON CONFLICT upsert）+ **资产自动建链（U5/F10，"18-视频制作"阶段一已实现）**：单元/镜头文本实体匹配 → 写 `nu_asset_links` + `shot_asset_refs` + `shots.linked_assets_json`（L217-226，`LinkAssetsInTx`，定义在 `internal\repository\asset_link.go`），供视频生成注入参考图。失败回滚 `MarkSplitFailed`（状态 → SCRIPT_SPLIT_FAILED 可重拆）。

### 3.4 相关辅助

- `internal\engine\agent\splitter.go`：`SplitResult/EpisodeSplit/NarrativeUnit/ShotGroup/Shot` 结构定义、枚举校验（景别 ECU/CU/MCU/MS/FS/LS/ELS/TWO_SHOT/OTS、运镜 18 种、视角 10 种）、`ParseAndValidate`、`ValidateExcerptCoverage`（原文摘录覆盖率校验）、`SplitOversizedUnits`、`NormalizeEpisodeCount`。
- 排查工具：`scripts\` 下有 verify-split-complete.go、check-split-params.go、resplit-verify.ps1、troubleshoot-split*.md 等。

# LuxReal「分镜镜头 → 视频」实现机制调研结论

## 问题 1：分镜脚本（8字段）如何转化为视频生成提示词？——两阶段机制：先自动拼接，再可选 LLM 润色

**转化链路为"字段自动拼接 → prompt_original →（可选）Lux Gem 3.0 润色 → prompt_refined → 送视频模型"：**

| 环节 | 实现方式 | 依据 |
|------|---------|------|
| ① 分镜脚本生成 | **Lux Chat 5.2**（自研LLM）按时长预设将剧本原文转换为含详细镜头描述的分镜脚本；Tab2 有「智能扩写」开关（推荐开启），可优化为更适合视频生成的镜头描述 | 03号 §G/059条 Tab2；06号 §B/103、105条 |

| ③ 提示词拼接 | `prompt_original` = "润色前提示词（**由上面几个字段自动拼接**给视频模型）"，即 8 字段（景别/运镜/视角/主体/背景/光影/台词/环境音）机械拼装，非 LLM 生成 | 10号 §C/ShotDetailDTO `prompt_original` 字段描述；08号 §D2/11 shots 表 `prompt_original`"润色前原始提示词(字段组合)" |

## 问题 3：@资产引用如何解析和替换？——双模式：隐式自然语言匹配 + 显式 @ 指定

> "功能优化：不用@资产，描述即可生效。当需要发挥模型的创造力时，可以选择不在文本框@素材；当需要更好地控制生成结果，可以使用@指定素材的用途"

| 模式 | 机制 | 语义 |
|------|------|------|
| **简化模式（隐式引用）** | 自然语言描述中**提到角色名/场景名即可生效，模型自动匹配引用**（如正文写"沈青禾"自动关联资产卡） | 适合发挥模型创造力；降低新用户学习成本 | 
| **精准模式（显式@）** | 用户使用 `@` 显式指定素材用途（如 `陆言-市井说书装`），更可控 | 适合精确控制生成结果 |

**解析落地的数据结构**（08号 §D2/11 shots 表 `linked_assets_json`；10号 §C/ShotDetailDTO）：
- 每镜头持久化 `linked_assets_json: {char_variant_ids:[...], scene_id, prop_ids:[...]}`，即"@绑定详情"
- 生成视频前校验绑定非空（空则 10号 §E/6.2 错误码 6002 阻断，引导回 Step2）
- 参考图数组中的 `asset_ref`/`asset_id` 字段即 @ 引用解析后的资产 UUID 回填（如 `character-variant-cv-xxx`），用于 Step3「资产绑定确认」弹窗展示
